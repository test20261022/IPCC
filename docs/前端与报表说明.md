# 第一部分：权限驱动的路由与菜单

## 1.1 三层权限落地

权限码的**唯一事实来源在后端**（`backend/app/core/permissions.py`，63 个码）。前端只做"隐藏入口"，不做真正的鉴权。三层分工：

| 层 | 位置 | 作用 | 越过的后果 |
|---|---|---|---|

| 页面级 | [routes.ts](file:///e:/company%20project/frontend/src/router/routes.ts) 的 `meta.permission` | 过滤路由与菜单，无权限**页面根本不注册** | 手输 URL 会落到 404（路由不存在） |

## 1.2 路由分两类

[constantRoutes](file:///e:/company%20project/frontend/src/router/routes.ts#L19-L42)：无需权限，**在 `createRouter` 时就注册**，共 3 条：

| path | name | 说明 |
|---|---|---|
| `/login` | Login | `meta.hidden = true` |
| `/404` | NotFound | 绕过权限直接看 404 页 |
| `/:pathMatch(.*)*` | CatchAll | **兜底渲染**（不是 redirect，见 1.3） |

[asyncRoutes](file:///e:/company%20project/frontend/src/router/routes.ts#L48-L188)：需要权限，**登录后动态注册**。全部 18 条 `meta.permission` 分布：

| 分组 | 页面数 | 权限码 |
|---|---|---|
| 首页 `/dashboard` | 1（无 `permission`） | 登录即可访问 |
| 智能外呼 `/outbound` | 12 | `outbound:type:list`、`scene:list`、`number:list`、`task:list`（任务与执行记录**共用**）、`list:list`、`agent:list`、`session:list`、`ivr:list`、`callback:list`、`monitor:view`、`report:list` |
| 对话质检 `/qc` | 6 | `qc:task:list`、`qc:review:work`、`qc:conversation:list`、`qc:case:list`、`qc:report:list`、`qc:reviewer:list` |

> 注意 `outbound:task:list` 被**两个页面复用**（外呼任务 `/outbound/tasks` 与执行记录 `/outbound/records`）——权限码是"能力"，不是"页面"，一个能力可以开多个入口。这是设计上刻意保留的粒度。

`RouteMeta` 的类型是通过**模块增强**声明的（[routes.ts#L3-L16](file:///e:/company%20project/frontend/src/router/routes.ts#L3-L16)），所以写 `meta.permission` 时有类型提示、写错字段名会报错：

```ts
declare module 'vue-router' {
  interface RouteMeta {
    title?: string        // 菜单与页签标题
    icon?: string         // Element Plus 图标组件名
    permission?: string   // 访问所需权限码（§59），为空表示登录即可访问
    hidden?: boolean      // 是否在菜单中隐藏
    alwaysShow?: boolean  // 分组路由即使只有一个子路由也保持子菜单形态
  }
}
```

## 1.3 兜底路由为什么不能写 `redirect`

[routes.ts#L33-L41](file:///e:/company%20project/frontend/src/router/routes.ts#L33-L41) 有一条很关键的注释，这是**真实踩过的坑**：

> 兜底路由直接渲染 404 组件，**不能**用 redirect。原因：路由记录上的 redirect 由 vue-router 在处理跳转时（**早于 `beforeEach`**）执行，会把尚未注册的动态路由（如 `/`、`/outbound/types`）提前改写成 `/404`，导致守卫失效。这里只做「兜底渲染」：未匹配路径显示 404，动态路由注册后静态路径优先级更高，仍能正常命中。

也就是说：**`redirect` 在路由匹配阶段执行，早于全局前置守卫**。如果兜底写 `redirect: '/404'`，那么"直接访问 `/`"会在守卫还没机会注册动态路由时就被改写成 `/404`，动态路由永远注册不上。

## 1.4 前置守卫：完整流程

[router/index.ts#L60-L89](file:///e:/company%20project/frontend/src/router/index.ts#L60-L89)：

```ts
router.beforeEach(async (to) => {
  const userStore = useUserStore()
  const menuStore = useMenuStore()

  // ① 无 token：白名单放行，其余跳登录并带上原地址
  if (!userStore.token) {
    if (WHITE_LIST.includes(to.path)) return true
    return { path: '/login', query: { redirect: to.fullPath } }
  }

  // ② 已登录却要去登录页：回首页
  if (to.path === '/login') return { path: '/' }

  // ③ 首次进入或刷新后 userInfo 为空：拉一次 /auth/me；失败则清空并跳登录
  if (!userStore.userInfo) {
    try {
      await userStore.loadUserInfo()
    } catch {
      userStore.reset()
      return { path: '/login', query: { redirect: to.fullPath } }
    }
  }

  // ④ 路由只注册一次
  if (!menuStore.ready) {
    menuStore.setRoutes(addDynamicRoutes((code) => userStore.hasPermission(code)))
    return { path: to.path, query: to.query, hash: to.hash, replace: true }
  }

  return true
})
```

### 关键点：第 ④ 步为什么返回 `{ path: to.path, ..., replace: true }` 而不是 `true`

源码注释写得很清楚，这是**第二个真实踩过的坑**：

> 路由刚添加，需按 path 重新匹配一次当前地址。注意：**不能返回 `{ ...to }`**，因为首次导航命中的是兜底路由，展开后会带上 `name`，而 vue-router **优先按 name 解析**，会再次落到兜底路由（表现为页面 404）。

拆开讲：
- `addRoute` 之后，当前这次导航的 `to` 是**在动态路由注册前**匹配出来的——直接访问 `/qc/tasks` 时命中的是 `CatchAll`，所以 `to.name === 'CatchAll'`。
- 如果返回 `{ ...to }`，会把 `name: 'CatchAll'` 一起带回去，vue-router **优先按 name 解析**，于是又匹配到 404。
- 所以必须**只保留 path/query/hash**（把 name 丢掉），让它按路径重新匹配一次；`replace: true` 是为了不在浏览器历史里留下一条中间记录（否则用户按"后退"会回到 404）。

## 1.5 递归过滤 + 空分组剔除

[filterRoutesByPermission](file:///e:/company%20project/frontend/src/router/index.ts#L23-L41)：

```ts
for (const route of routes) {
  if (!hasPermission(route.meta?.permission)) continue   // ① 自身无权限：整个子树剔除

  if (!route.children || route.children.length === 0) {
    result.push(route)                                    // ② 叶子路由：直接收
    continue
  }

  const children = filterRoutesByPermission(route.children, hasPermission)  // ③ 递归
  if (children.length === 0) continue                     // ④ 子路由全没了 → 整组剔除
  result.push({ ...route, children })
}
```

**④ 是重点**：分组路由（`/outbound`、`/qc`）自己**没有** `meta.permission`，靠子路由决定去留。如果某个用户只有 `qc:review:work`，那 `/outbound` 组下 12 个子路由全被过滤，`children.length === 0` → **整个外呼分组被剔除**，菜单里不会出现一个点不开的空目录。

`pushes({ ...route, children })` 用展开运算符而不是直接改 `route.children`，是**不污染原数组**——`asyncRoutes` 是模块级常量，下次登录还要用。

## 1.6 注册与回收

```ts
const addedRouteNames: string[] = []   // 记录动态添加的路由名，登出时用于清理

function addDynamicRoutes(hasPermission): RouteRecordRaw[] {
  const accessible = filterRoutesByPermission(asyncRoutes, hasPermission)
  accessible.forEach((route) => {
    router.addRoute(route)
    if (route.name) addedRouteNames.push(String(route.name))
  })
  return accessible
}

export function resetDynamicRoutes(): void {
  addedRouteNames.forEach((name) => {
    if (router.hasRoute(name)) router.removeRoute(name)
  })
  addedRouteNames.length = 0
}
```

`router.addRoute` 添加的路由**不会自动消失**。如果登出时不清理，换一个权限更低的账号登录，旧账号的路由还留在路由表里——用户手输 URL 就能进入不该看到的页面（**这就从"隐藏入口"退化成"前端可见"**）。所以登出必须清理。

登出链路的完整顺序（[HeaderBar.vue#L53-L59](file:///e:/company%20project/frontend/src/layout/components/HeaderBar.vue#L53-L59)）：

```ts
await userStore.logout()   // ① 调登出接口（失败也继续）+ 清 token/userInfo
resetDynamicRoutes()       // ② 移除动态路由
menuStore.reset()          // ③ 清空菜单 + ready = false
await router.replace('/login')
```

顺序不能乱：先清 token 再清路由，且 `menuStore.reset()` 把 `ready` 置回 `false`，这样**下一个账号登录时第 ④ 步会重新注册**。

## 1.7 菜单是怎么来的

菜单**不是**独立维护的一份配置，而是**直接用过滤后的路由**（[menu.ts](file:///e:/company%20project/frontend/src/stores/menu.ts)）：

```ts
export const useMenuStore = defineStore('menu', () => {
  const routes = ref<RouteRecordRaw[]>([])   // 过滤后的可访问路由
  const ready = ref(false)
  function setRoutes(value) { routes.value = value; ready.value = true }
  function reset() { routes.value = []; ready.value = false }
  return { routes, ready, setRoutes, reset }
})
```

渲染在 [SidebarMenu.vue](file:///e:/company%20project/frontend/src/layout/components/SidebarMenu.vue)：`<MenuItem v-for="item in menuStore.routes" ... />`，`el-menu` 开 `router` 模式（点击即导航）。

[MenuItem.vue](file:///e:/company%20project/frontend/src/layout/components/MenuItem.vue) 递归渲染，处理了三种形态：

| 形态 | 条件 | 效果 |
|---|---|---|
| 单个菜单项 | `singleChild`（只有 1 个可见子路由，且该子路由没有下一级，且父级未设 `alwaysShow`） | 直接渲染 `el-menu-item`，**避免出现只含一项的子菜单** |
| 子菜单 | `visibleChildren.length > 0` | `el-sub-menu` + 递归 |
| 普通项 | 有 `title` 的叶子 | `el-menu-item` |

`hidden` 的路由在模板第一行就被挡掉：`<template v-if="!item.meta?.hidden">`。`resolvePath` 负责把相对子路径拼成绝对路径（`path.startsWith('/') ? path : base + '/' + path`）。

## 1.8 `hasPermission` 与后端行为一致

[stores/user.ts#L15-L20](file:///e:/company%20project/frontend/src/stores/user.ts#L15-L20)：

```ts
function hasPermission(code?: string): boolean {
  if (!code) return true                              // ① 未声明权限 = 登录即可访问
  if (isSuperuser.value) return true                  // ② 超管直接放行
  return permissions.value.has(code)                  // ③ 其余按权限码集合判断
}
```

三条规则**与后端 `require_permission` 完全一致**（后端也是 `if current_user.is_superuser: return current_user`，且无权限码的接口不做校验）。前端不发明自己的规则，是"前后端一致"最重要的一条：**不一致会造成"菜单能看见但点进去 403"或"有权限但菜单不显示"**。

权限集合用 `computed(() => new Set(...))` 缓存，判断是 O(1)；`permission_codes` 来自 `/auth/me` 的返回。

# 第二部分：Axios 统一封装

## 2.1 实例与 token 存取

[request.ts#L48-L51](file:///e:/company%20project/frontend/src/api/request.ts#L48-L51)：

token 存取是**三个纯函数**，与 store 解耦，便于任何地方调用：

```ts
const ACCESS_TOKEN_KEY = 'cp_access_token'
const REFRESH_TOKEN_KEY = 'cp_refresh_token'

export function getAccessToken(): string { return localStorage.getItem(ACCESS_TOKEN_KEY) ?? '' }
export function setTokens(access, refresh): void { /* 写两个 key */ }
export function clearTokens(): void { /* 删两个 key */ }
```

## 2.2 请求拦截器：注入 token

```ts
service.interceptors.request.use((config) => {
  const token = getAccessToken()
  if (token) {
    config.headers.Authorization = `Bearer ${token}`
  }
  return config
})
```

每次请求**实时从 localStorage 读**，而不是在模块加载时读一次存到变量里——这样多标签页场景下另一个标签页登录/登出后，本页下一次请求就会用上新 token。没有 token 时不写头（让后端返回 401，走统一处理）。

## 2.3 响应拦截器：两条分支

```ts
service.interceptors.response.use(
  (response) => {
    const body = response.data as ApiResponse | undefined
    // 统一响应体：code !== 0 视为业务失败
    if (body && typeof body.code === 'number' && body.code !== 0) {
      const message = body.message || '请求失败'
      ElMessage.error(message)
      return Promise.reject(new ApiError(message, body.code, response.status))
    }
    return body as never          // 成功：返回整个响应体（不是 response.data.data）
  },
  (error) => { /* HTTP 层错误，见 2.4 */ },
)
```

这是**"HTTP 200 但业务失败"的处理点**。项目的统一响应体是 `{code, message, data}`，成功码 `0`；失败时 HTTP 状态可能仍是 200（或 4xx），所以必须同时判两层：

| 层 | 判定依据 | 处理 |
|---|---|---|
| 业务层 | `body.code !== 0` | `ElMessage.error(message)` + reject `ApiError(message, code, status)` |
| HTTP 层 | axios 抛错 | 见下一节 |

注意**返回值是 `body`（整个 `ApiResponse`）而不是 `body.data`**，所以调用方写的是：

```ts
const { data } = await getQcReportOverview({ ... })   // 取出 data 字段
```

这样调用方**仍然能拿到 `code`/`message`**，需要时可以做更细的处理（而不是被拦截器"吃掉"元信息）。

## 2.4 401 处理：三个细节

```ts
const status: number | undefined = error?.response?.status
const url: string = error?.config?.url ?? ''
const isLoginRequest = url.includes('/auth/login')

if (status === 401 && !isLoginRequest) {
  clearTokens()
  if (!redirecting) {
    redirecting = true
    ElMessage.error('登录已失效，请重新登录')
    const current = `${window.location.pathname}${window.location.search}`
    window.location.href = `/login?redirect=${encodeURIComponent(current)}`
  }
} else {
  ElMessage.error(message)
}
```

三个细节都是有原因的：

1. **登录接口豁免**（`isLoginRequest`）。用户输错密码时后端返回 401，这属于"账号或密码错误"，**不该**清 token、也不该跳转（他已经在登录页了）。源码注释直接写了这一点。
2. **`redirecting` 去重标志**（模块级 `let redirecting = false`）。一个页面同时发 5 个请求、token 全过期时，会收到 5 个 401。如果不去重，就会弹 5 次「登录已失效」并触发 5 次跳转。用标志位保证**只提示、只跳转一次**。
3. **带 `redirect` 参数回跳**。跳转前记录 `pathname + search`（含查询参数），登录成功后可以跳回原页面，不会丢失用户正在做的事。

用 `window.location.href` 而不是 `router.push`，是为了**整页刷新**——彻底清掉内存里的 Pinia 状态和已注册的动态路由，避免残留权限。

## 2.5 `ApiError` 与全局静音

响应拦截器**已经弹过 `ElMessage`** 了，所以页面里 `await xxx()` 未捕获时再抛一次只是噪音。[request.ts#L9-L32](file:///e:/company%20project/frontend/src/api/request.ts#L9-L32) 定义了专门的错误类型：

```ts
export class ApiError extends Error {
  readonly code: number | null    // 业务码
  readonly status: number | null  // HTTP 状态码
}
export function isApiError(reason: unknown): reason is ApiError {
  return reason instanceof ApiError
}
```

[main.ts#L19-L29](file:///e:/company%20project/frontend/src/main.ts#L19-L29) 用两个钩子把它静音：

```ts
// ① Vue 组件内未捕获的异常
app.config.errorHandler = (error) => {
  if (!isApiError(error)) console.error(error)
}

// ② 未处理的 Promise rejection
window.addEventListener('unhandledrejection', (event) => {
  if (isApiError(event.reason)) event.preventDefault()
})
```

**只静音 `ApiError`，其它异常照常 `console.error`**——这是关键取舍：如果无脑 `event.preventDefault()`，真正的代码 bug（`TypeError`、`undefined.foo`）也会被吞掉，排查时一片沉默。用"自定义错误类型 + 精确静音"既保证界面不刷红，又不丢真实异常。这与 §79 的要求（统一提示、避免噪音）一致。

## 2.6 薄封装 `http`

```ts
async function request<T>(config: AxiosRequestConfig): Promise<ApiResponse<T>> {
  return (await service.request(config)) as unknown as ApiResponse<T>
}

export const http = {
  get: <T>(url, params?) => request<T>({ url, method: 'get', params }),
  post: <T>(url, data?) => request<T>({ url, method: 'post', data }),
  put: <T>(url, data?) => request<T>({ url, method: 'put', data }),
  delete: <T>(url) => request<T>({ url, method: 'delete' }),
}
```

四个方法，`<T>` 是**响应体 `data` 的类型**（`ApiResponse<T>` 由 `types/api.ts` 定义）。所有 `api/**/*.ts` 文件都只做两件事：声明接口类型 + 调 `http.xxx<T>(...)`，例如：

```ts
export const getQcDailyCompletion = (params: QcDailyCompletionQuery) =>
  http.get<QcDailyCompletion>('/qc/reports/daily-completion', params as unknown as Record<string, unknown>)
```

> 这里有个**类型小坑**（本会话真实修过）：`as Record<string, unknown>` 会因接口不够宽而报 TS 错，需要 `as unknown as Record<string, unknown>` 先过桥。修完后 `npm run type-check`（`vue-tsc --noEmit`）与 `vite build` 均通过。

## 3.2 `useEcharts`：生命周期三件事

[utils/useEcharts.ts](file:///e:/company%20project/frontend/src/utils/useEcharts.ts)：

```ts
export function useEcharts(el: Ref<HTMLDivElement | undefined>) {
  const chart = shallowRef<ChartInstance | null>(null)

  /** 更新图表数据（整体替换配置，避免残留上一次的系列） */
  function render(option: EChartsOption): void { chart.value?.setOption(option, true) }
  function resize(): void { chart.value?.resize() }

  onMounted(() => {
    if (!el.value) return
    chart.value = echarts.init(el.value)
    window.addEventListener('resize', resize)
  })

  onBeforeUnmount(() => {
    window.removeEventListener('resize', resize)   // ① 必须移除监听
    chart.value?.dispose()                          // ② 必须销毁实例
    chart.value = null
  })

  return { chart, render, resize }
}
```

四个设计点：

1. **`shallowRef` 而不是 `ref`**。ECharts 实例是**有复杂内部结构的巨型对象**，用 `ref` 会触发 Vue 的深度响应式代理，既浪费性能又可能干扰 ECharts 内部逻辑。`shallowRef` 只追踪引用本身，是正确的选择。
2. **`setOption(option, true)` 第二个参数 `true`**（`notMerge`）。**整体替换**而不是合并——否则上次的数据系列会残留在图上（比如先查 3 天、再查 14 天，旧柱子还在）。
3. **`window.addEventListener('resize', resize')`**：ECharts 的 canvas 不会自动跟随容器变化，必须手动 `resize()`。**卸载时必须 `removeEventListener`**，否则组件销毁后监听器还在，会持续调用已销毁实例的 `resize()` → 报错 + 内存泄漏。
4. **`dispose()` + 置 `null`**：释放 canvas 与内部缓存。

这个 Hook 被 `views/qc/report`、`views/outbound/report`、`views/outbound/monitor` **三处复用**，避免各自写一套 init/resize/dispose。

还有一个共用的格式化工具：

```ts
export function formatDuration(seconds: number | null | undefined): string
// 45 → "45 秒"；90 → "1 分 30 秒"；3660 → "1 小时 1 分"
```

## 3.4 时间分桶与补零：前后端职责划分

### 质检：按"报表时区自然日"分桶

**分桶在 SQL 里做**（[qc_report_repository.py#L80-L107](file:///e:/company%20project/backend/app/repositories/qc/qc_report_repository.py#L80-L107)）：

```python
local_reviewed = func.timezone(settings.QC_REPORT_TIMEZONE, QcReviewResult.reviewed_at)
bucket = func.date_trunc("day", local_reviewed).label("bucket")
start = datetime.combine(date_from, time.min)
end = datetime.combine(date_to + timedelta(days=1), time.min)
```

**"先 `timezone` 再 `date_trunc`"这个顺序是必须的**，文件头注释解释了原因：

> 按天分桶：以 `qc_review_results.reviewed_at` 为依据，必须先用 `timezone(tz, reviewed_at)` 换算到报表时区再 `date_trunc('day', ...)`，否则**跨零点错位**（`reviewed_at` 存 UTC）。

举例：`QC_REPORT_TIMEZONE = "Asia/Shanghai"`（UTC+8）。一条明细在**北京时间 2026-03-01 07:00** 提交，存的 UTC 是 `2026-02-28 23:00`。如果直接 `date_trunc('day', reviewed_at)`，它会被算进 **2 月 28 日**；先 `timezone('Asia/Shanghai', ...)` 变成 `2026-03-01 07:00`，才正确落到 **3 月 1 日**。少一步就是"跨零点那 8 小时的数据全部错位一天"。

区间用**半开** `[start, end)`：

```python
local_reviewed >= start, local_reviewed < end
```

`end` 是 `date_to + 1 天` 的 00:00。半开区间不会漏掉 `23:59:59.999`，也不会把 `date_to` 当天的 `00:00:00` 重复计入——闭区间是分桶统计里最常见的 off-by-one 来源。

### 补零在服务层做（Python，不是 SQL）

SQL 聚合出来的是**稀疏结果**（没有数据的日期根本没有行）。补零在 [report_service.py#L68-L74](file:///e:/company%20project/backend/app/services/qc/report_service.py#L68-L74)：

```python
buckets = {self._bucket_key(row["bucket"]): {...} for row in rows}   # ① 稀疏结果做成字典

items = []
cursor = date_from
while cursor <= date_to:                                              # ② 逐日遍历
    key = cursor.isoformat()
    counts = buckets.get(key, {"total": 0, "excellent": 0, "pass": 0, "fail": 0})  # ③ 缺就补零
    items.append({"bucket": key, **counts})
    cursor += timedelta(days=1)
```

为什么**不在 SQL 里用 `generate_series` 左连接**？三个理由：

1. **`generate_series` 是 PostgreSQL 方言**，写进去就把查询锁死在 PG 上（项目测试环境虽也是 PG，但仓储层一直保持方言可移植的习惯）。
2. **补零是"展示逻辑"，不是"数据逻辑"**——它关心的是"给前端一条连续的时间轴"，放在服务层语义更清楚，也更好测（`daily_completion` 是纯函数式的一段循环）。
3. **字典查找 + 循环是最直白的实现**，14 天就是 14 次循环，性能无关紧要。

产物保证是**连续自然日序列**，前端可以直接 `items.map(item => item.bucket)` 当 x 轴，不会出现"跳过没数据的那天导致时间轴等距失真"。

前端拿到后直接画（[qc/report/index.vue#L282-L297](file:///e:/company%20project/frontend/src/views/qc/report/index.vue#L282-L297)），注释也写明了这一点：

```ts
/** 每日完成量柱状图：后端已补齐无数据日（补零），逐日画出柱子 */
```

### 实时监控：按"分钟"分桶

[outbound/report_repository.py#L212](file:///e:/company%20project/backend/app/repositories/outbound/report_repository.py#L212) 用的是 `date_trunc("minute", CallHistory.started_at)`——**监控看的是"最近 N 分钟"的走势，粒度自然是分钟**。这里没有做时区换算（桶是相对时间窗，不涉及"自然日"边界），前端负责把桶格式化成 `HH:mm`：

```ts

  new Date(item.bucket).toLocaleTimeString('zh-CN', { hour: '2-digit', minute: '2-digit' }),

```

**这就是"何时需要时区换算"的判断标准**：按**自然日/自然月**分桶（报表）必须换算；按**相对时间窗**分桶（监控）不需要。

### 前端只负责"选区间"

[qc/report/index.vue#L127-L155](file:///e:/company%20project/frontend/src/views/qc/report/index.vue#L127-L155)：

```ts

function defaultRange(): [Date, Date] {
  const end = new Date()
  const start = new Date()
  start.setDate(end.getDate() - 13)   // 含今天共 14 天
  return [start, end]
}

/** Date → YYYY-MM-DD（本地时区，不用 toISOString 避免 UTC 偏移） */
function formatDate(value: Date): string {
  const year = value.getFullYear()
  const month = String(value.getMonth() + 1).padStart(2, '0')
  const day = String(value.getDate()).padStart(2, '0')
  return `${year}-${month}-${day}`
}
```

`formatDate` **手写而不是用 `toISOString().slice(0,10)`**，因为 `toISOString` 会先转 UTC——北京时间凌晨选"今天"，`toISOString` 可能给出昨天，区间就整体偏一天。`getFullYear/getMonth/getDate` 取的是本地日历值，与用户在日期选择器上看到的日期一致。

## 3.5 一个真实的字段名坑：`pass`

[qc/report.ts#L23-L34](file:///e:/company%20project/frontend/src/api/qc/report.ts#L23-L34)：

```ts
export interface QcDailyCompletionItem {
  bucket: string
  total: number
  excellent: number
  /**
   * 及格数。后端 JSON 字段名为 `pass`（Python 保留字，无法直接作为字段名），
   * 故 TS 侧以 `pass_count` 承载；读取时需兼容 `row.pass`（页面用 passOf 收敛）。
   */
  pass_count: number
  fail: number
}
```

后端聚合列名 `pass`（`func.count().filter(...).label("pass")`），**`pass` 在 Python 里是保留字**，所以 TS 侧用 `pass_count` 承载；页面上用一个函数把两种形态收敛掉，避免图表逻辑里到处写断言：

```ts
function passOf(row: QcDailyCompletionItem): number {
  return row.pass_count ?? (row as { pass?: number }).pass ?? 0
}
```

> 这是一个"跨语言命名冲突"留下的兼容层。更干净的做法是后端在序列化时统一改名为 `pass_count`（`populate_by_name` 或响应模型别名），项目目前用前端收敛，如实记录。

# 第四部分：面试问答

## A. 路由与权限（11 题）

**A1. 动态路由是怎么实现的？`addRoute` 在什么时机调用？**

在全局前置守卫 `beforeEach` 里。流程：有 token → 若无 `userInfo` 先调 `/auth/me` 拿权限码 → 若 `menuStore.ready === false`，用 `filterRoutesByPermission(asyncRoutes, hasPermission)` 过滤出可访问路由 → 逐条 `router.addRoute` 并记录路由名，然后**返回 `{path, query, hash, replace: true}` 触发一次重新匹配**。`ready` 标志保证只注册一次。

**A2. 为什么注册完要返回 `{ path: to.path, ..., replace: true }` 而不是 `true`？**

因为这次导航的 `to` 是**动态路由注册前**匹配出来的，直接访问 `/qc/tasks` 时命中的是兜底路由，`to.name === 'CatchAll'`。如果返回 `{ ...to }`，会把 `name` 一起带回去，而 **vue-router 优先按 name 解析**，于是又匹配回 404。所以必须只保留 path/query/hash 让它重新按路径匹配；`replace: true` 避免在历史里留下这条中间记录（否则用户点"后退"会看到 404）。这是项目真实踩过的坑，源码里有注释。

**A3. 兜底路由为什么不能用 `redirect`？**

`redirect` 由 vue-router 在**路由匹配阶段**执行，**早于 `beforeEach`**。如果写 `redirect: '/404'`，那么"直接访问 `/`"会在守卫还没机会注册动态路由时就被改写成 `/404`，动态路由永远注册不上。所以兜底路由只做**兜底渲染**（`component` 指向 404 组件），动态路由注册后静态路径优先级更高，仍能正常命中。

**A4. 某个分组下所有子路由都被过滤掉时怎么处理？**

`filterRoutesByPermission` 里递归后判断 `if (children.length === 0) continue`——**整组剔除**，否则菜单里会出现一个点不开的空目录。因为 `/outbound`、`/qc` 这两个分组路由自己**没有** `meta.permission`，去留完全由子路由决定。

**A5. 菜单是怎么生成的？和路由是什么关系？**

菜单**直接复用过滤后的路由**，不另维护一份配置：`menuStore.routes` 存的就是 `addDynamicRoutes` 的返回值（过滤后、已注册的路由数组），`SidebarMenu` 遍历它渲染 `MenuItem`。好处是"路由能进 = 菜单能显示"永远一致，不会出现两处配置不同步。

**A6. 前端做了权限过滤，后端还要做吗？**

**必须做。** 前端过滤只能"隐藏入口"：用户可以手改 URL、可以直接发请求、可以改 localStorage 里的权限码。所以后端每个接口都有 `require_permission`，返回 403/40301，这才是权威判定。前端的价值是**体验**（不给用户看点了会失败的按钮），不是安全。指令源码里也写了"真正的鉴权始终以后端为准（§63）"。

**A7. `hasPermission` 为什么要对超管直接返回 `true`？**

为了与后端**行为一致**。后端 `require_permission` 里第一句就是 `if current_user.is_superuser: return current_user`——超管绕过所有权限码检查。如果前端还让超管按权限码集合判断，就会出现"超管有权限却被菜单藏起来"的不一致。一致性比"前端独立实现"重要。

**A8. 登出时为什么要清理动态路由？不清理会怎样？**

`router.addRoute` 添加的路由**不会自动消失**。不清理的话，换一个权限更低的账号登录，上一个账号的路由还在路由表里——用户手输 URL 就能进入不该看到的页面（**从"隐藏入口"退化成"前端可见"**）。所以登出链路是 `userStore.logout()` → `resetDynamicRoutes()` → `menuStore.reset()` → `router.replace('/login')`，且 `menuStore.reset()` 把 `ready` 置回 `false`，保证下个账号会重新注册。

**A9. 刷新页面后动态路由不是没了吗？为什么还能正常访问？**

因为守卫里的注册是**幂等且每次都会补**：刷新后 Pinia 是空的（`userInfo` 为 null、`menuStore.ready` 为 false），守卫第 ③ 步发现没有 `userInfo` 就去调 `/auth/me`，第 ④ 步发现 `ready` 为 false 就重新过滤 + `addRoute`。所以刷新等于"重新走一遍注册流程"，不需要持久化路由表。

**A10. 单子路由为什么要"折叠"？`alwaysShow` 是干什么的？**

`MenuItem` 里，如果分组只有 1 个可见子路由、且该子路由没有下一级、且父级没设 `alwaysShow`，就直接渲染成一个 `el-menu-item`。否则菜单里会出现"点开只有一项"的无意义子菜单。`alwaysShow: true` 是**反向开关**（如 `/outbound`、`/qc` 都设了），表示"即使只有一项也保持子菜单形态"——用于保持一级分组的视觉层级。

**A11. `RouteMeta` 是怎么获得类型提示的？**

用**模块增强**（module augmentation）：在 `routes.ts` 里 `declare module 'vue-router' { interface RouteMeta { title?: string; permission?: string; ... } }`。这样写 `route.meta.permission` 有类型提示，写错字段名（比如 `permisson`）会直接报 TS 错误，而不是静默 `undefined`——**把"拼错字段名导致权限失效"这类问题提前到编译期**。

## B. Axios 封装（11 题）

**B1. token 为什么存 localStorage 而不是 Cookie？有什么风险？**

`localStorage` 存 `cp_access_token` / `cp_refresh_token`，好处是**简单、不参与跨域自动携带、前后端分离下不需要 CSRF 防护**（因为不是自动携带，攻击者无法通过表单提交触发）。风险是**XSS 可读**——一旦有 XSS，token 直接被偷。Cookie 方案（`HttpOnly` + `Secure` + `SameSite`）能防 XSS 读取，但要处理 CSRF 与跨域，还要后端配合。本项目选了 localStorage 的简单性，实际生产中应配合严格的 CSP 与 XSS 防护。

**B2. 请求拦截器做了什么？为什么每次请求都重新读 token？**

读 `localStorage` 的 access token，有则写入 `config.headers.Authorization = 'Bearer ' + token'`。每次请求**实时读**而不是模块加载时读一次：多标签页场景下，另一个标签页登录/登出/刷新 token 后，本页下一次请求会自动用上最新值，不需要刷新页面。没有 token 时不写头，让后端返回 401，交给统一处理。

**B3. 响应拦截器怎么区分"业务失败"和"HTTP 失败"？**

两个回调分别处理：**成功回调**里判统一响应体 `body.code !== 0`（HTTP 可能是 200 但业务失败）→ `ElMessage.error` + reject `ApiError(message, code, status)`；**失败回调**里处理 axios 抛出的错误（网络异常、4xx/5xx），从 `error.response.data.message` 取后端文案。两层都要有，因为后端**业务失败不一定用非 200 状态码**。

**B4. 为什么登录接口的 401 不触发跳转？**

用户输错密码时后端返回 401，这属于"账号或密码错误"，语义上不是"登录态失效"。如果也清 token + 跳转，会出现"在登录页输错密码 → 被踢到登录页 + 提示登录已失效"的荒谬体验。所以拦截器里先判 `const isLoginRequest = url.includes('/auth/login')`，是登录请求就走普通错误分支，只弹后端给的文案。

**B5. 一个页面同时发 5 个请求，token 都过期了，会跳转 5 次吗？**

不会，用了一个模块级标志位 `let redirecting = false`：第一个 401 进来时置 `true` 并跳转，后续 401 只走到 `clearTokens()` 就返回，不再弹提示、不再跳转。这是**并发错误去重**的经典手法。注意标志位**不重置**——因为紧接着就是 `window.location.href` 整页刷新，模块会被重新加载，标志位自然归零。

**B6. 登录失效后怎么让用户回到原来要去的页面？**

跳转前把当前位置塞进 query：`window.location.href = '/login?redirect=' + encodeURIComponent(pathname + search)`。用 `pathname + search`（**带上查询参数**）而不是只记 path，否则筛选条件、分页状态会丢。登录成功后读 `redirect` 回跳。

**B7. 为什么拦截器已经 `ElMessage` 提示了，还要封装一个 `ApiError`？**

为了**让全局静音变得精确**。`ElMessage` 只负责"给用户看"，但 Promise 还是会 reject，页面里没 try/catch 就会产生"未处理的 rejection"控制台报错。用自定义 `ApiError` 标记"这个错误已经提示过了"，`main.ts` 就能**只吞掉这一类**，其它异常照常输出。如果不做类型区分，只能无脑 `preventDefault()`，那就把真正的 bug 也吞了。

**B8. `main.ts` 里两个钩子分别拦什么？**

`app.config.errorHandler` 拦 **Vue 组件生命周期/渲染/事件里未捕获的异常**；`window.addEventListener('unhandledrejection')` 拦 **未处理的 Promise rejection**（`await` 失败且没 catch，多发生在 async onMounted 里）。两者都只对 `isApiError` 静音，非 `ApiError` 走 `console.error`。

**B9. 拦截器返回的是 `response.data` 还是 `response`？为什么调用方写 `const { data } = await xxx()`？**

拦截器返回的是 **`response.data`（即整个 `ApiResponse`）**，不是 axios 的 response，也不是 `ApiResponse.data`。所以调用方拿到的是 `{code, message, data}`，`const { data } = await xxx()` 是从**统一响应体**里解构业务数据。这样设计的好处是调用方**仍然能拿到 `code`/`message`**——需要对特定业务码做特殊处理时不会因为拦截器"吃掉"元信息而无从下手。

**B10. 超时设了多久？为什么一定要设？**

`timeout: 15000`（15 秒）。不设超时的话，网络异常/后端 hang 住时请求会一直挂着，用户的按钮一直 loading，体验上像"卡死"；而且连接池会被占满。15 秒的取舍是：报表类聚合查询（10 万条分桶）需要余量，又不能长到用户以为页面死了。

**B11. 为什么 `http` 要包一层泛型而不是直接用 axios？**

`http.get<T>(url, params): Promise<ApiResponse<T>>` 把"后端统一响应体"这个契约写进类型系统。每个 `api/**/*.ts` 只要声明一次接口类型（如 `QcDailyCompletion`），后续 `const { data } = await getQcDailyCompletion(...)` 里 `data` 就是**有字段提示的强类型**，字段名写错立刻编译报错。这比裸用 axios + 到处手写 `as SomeType` 可靠得多。

## C. ECharts 与报表（12 题）

**C1. 为什么要按需注册 ECharts？整包多大？**

ECharts 整包约 **1MB**（min 后），但项目只用了 Bar/Line/Pie 三种图 + Grid/Legend/Title/Tooltip 四个组件 + Canvas 渲染器。按需注册后打包体积大幅下降（这是前端首屏优化里"性价比最高"的一类改动：改一个文件、零业务逻辑风险）。代价是**新增图表类型必须回 `utils/echarts.ts` 补注册**，否则运行时报错——用"一处集中维护"换"包体积"。

**C2. 图表实例为什么用 `shallowRef` 而不是 `ref`？**

ECharts 实例是内部结构极其复杂的巨型对象。用 `ref` 会被 Vue 的 `reactive()` **深度代理**：既浪费性能（递归遍历整个实例），又可能干扰 ECharts 内部对自身对象身份的判断。`shallowRef` 只追踪引用本身的变化，不深入代理——这是官方推荐做法。

**C3. `setOption(option, true)` 的第二个参数是什么？不传会怎样？**

是 `notMerge` 参数，`true` 表示**整体替换**而非合并。不传（默认合并）时，上一次的系列会残留在图上：例如先查 3 天再查 14 天，"每日完成量"图里旧的 3 根柱子还在，看起来像数据错乱。项目在 `useEcharts.render` 里统一传 `true`，从根上避免这类问题。

**C4. 窗口缩放时图表为什么不跟着变？怎么处理？**

canvas 的尺寸是 ECharts 初始化时按容器算的固定值，容器变宽变窄它不会自动重算。做法是监听 `window.resize` 调 `chart.resize()`。**关键是卸载时必须 `removeEventListener`**：否则组件销毁后监听器仍然存在，会持续调用已 `dispose` 的实例 → 报错 + 内存泄漏。`useEcharts` 的 `onBeforeUnmount` 里 `removeEventListener` + `dispose()` + 置 `null` 三件套齐全。

**C5. 完成率是怎么画的？**

项目里完成率是**"数字卡片 + 环形图"**的组合：卡片直接显示 `completion_rate` 的百分比文本（`(value * 100).toFixed(2) + '%'`），环形图（`radius: ['40%', '68%']`）显示"已完成 / 未完成"的占比。**如实说明：这不是 ECharts 的 gauge 指针仪表盘**，`utils/echarts.ts` 里也没有注册 `GaugeChart`。用环形图的理由：它和同一页的"等级分布"视觉一致，且饼图/环形图在"占比"表达上比 gauge 更直观（gauge 更适合"当前值 vs 阈值"的单指标场景）。

**C6. 没有数据时图表会怎样？怎么兜底？**

全 0 数据时 ECharts 渲染成空白，用户会以为页面坏了。两处饼图都做了兜底：数据全为 0 时替换成 `[{ name: '暂无数据', value: 0 }]`（完成率图用 `items.some(item => item.value > 0)` 判定，话务状态图用 `data.length` 判定）。柱状图和折线图不需要兜底——空数组会正常显示空坐标系，x 轴刻度仍在。

**C7. 按天分桶为什么要"先 `timezone` 再 `date_trunc`"？顺序反了会怎样？**

因为 `reviewed_at` 存的是 **UTC**。一条明细在北京时间 `2026-03-01 07:00` 提交，UTC 是 `2026-02-28 23:00`——直接 `date_trunc('day', reviewed_at)` 会把它算进 **2 月 28 日**，跨零点那 8 小时的数据**整体错位一天**。正确顺序是先 `timezone('Asia/Shanghai', reviewed_at)` 把时间戳换算成目标时区的"墙上时间"，再 `date_trunc('day', ...)` 取自然日。这是报表类需求最容易踩、也最难发现的坑（数据量小时几乎看不出来）。

**C8. 补零在哪一层做？为什么不用 SQL 的 `generate_series` 左连接？**

在**后端服务层**用 Python 循环做（`while cursor <= date_to`，字典查不到就补零）。不在 SQL 里用 `generate_series`：① 它是 **PostgreSQL 方言**，会破坏仓储层的可移植性；② 补零是**展示逻辑**不是数据逻辑；③ 服务层实现更直白、更好测。产物是"连续自然日序列"，前端可直接当 x 轴，避免"跳过无数据日导致时间轴等距失真"。

**C9. 实时监控的趋势为什么用"分钟"桶，而不是"天"桶？**

因为监控看的是**最近 N 分钟的走势**（`window_minutes`），粒度自然是分钟。这里用 `date_trunc('minute', started_at)`，且**不做时区换算**——桶是相对时间窗，不涉及"自然日"边界，前端用 `toLocaleTimeString('zh-CN', {hour, minute})` 格式化成 `HH:mm`。**判断标准**：按自然日/自然月分桶（报表）必须换算时区；按相对时间窗分桶（监控）不需要。

**C10. 时间区间为什么用半开 `[start, end)`？**

`end` 取 `date_to + 1 天` 的 `00:00`，条件是 `>= start AND < end`。用闭区间（`<= end`）的话：`end` 是 `date_to 00:00`，会**漏掉 date_to 当天 00:00 之后的全部数据**；如果取 `date_to 23:59:59`，又可能漏掉 `23:59:59.5` 这类小数秒。半开区间两头都干净，是分桶统计里避免 off-by-one 的标准做法。

**C11. 前端选日期为什么手写 `formatDate` 而不用 `toISOString`？**

`toISOString()` 会**先转成 UTC** 再格式化。北京时间凌晨选"今天"（比如 `2026-03-01 08:00` 之前），UTC 还是 `2026-02-28`，`toISOString().slice(0,10)` 会给出 `2026-02-28`，**整个查询区间偏一天**。改用 `getFullYear()/getMonth()+1/getDate()` 取本地日历值再 `padStart` 补零，与用户在日期选择器上看到的日期一致。这是一个"看起来等价、实际差一天"的经典坑。

**C12. 一个页面里多个图表，实例是怎么管理的？**

每个图表容器一个 `ref`，各自调一次 `useEcharts(el)`，得到各自的 `render`（[qc/report/index.vue#L143-L148](file:///e:/company%20project/frontend/src/views/qc/report/index.vue#L143-L148) 连调三次）。三个实例互相独立：独立 init、独立 resize 监听、独立 dispose。数据监听上，完成率图与等级分布图都 `watch(overview)`，但因为 `render` 闭包绑定的是各自的实例，不会互相干扰。这样比"一个大 Hook 管所有图"更简单——Hook 保持单一职责（只管一个容器）。

## D. 综合（4 题）

**D1. 这套前端权限方案的安全边界在哪里？**

只能防"误操作"和"信息暴露"，**不能防恶意用户**。可以绕过的点：手改 localStorage 里的 `permissions`（前端会显示菜单，但一请求就被后端 403）、直接调接口（同上，被 `require_permission` 拦）、手输 URL（动态路由没注册会落到 404）。真正不可绕过的只有后端。所以定位是"体验层"，安全层在后端（详见 `docs/数据模型与RBAC权限说明.md`）。

**D2. 如果报表数据量再大 10 倍，前端要改什么？**

三个方向：① **后端分页/降采样**——按天分桶最多 365 个点，本身不是问题，但话务流水那种明细表要控制 `page_size`（项目 `PageParams` 上限 200）；② **图表懒加载**——当前三个图表在 `onMounted` 里全部初始化，数据大时可按需渲染（滚动到可视区再 init）；③ **大数据量用 `large: true` / `sampling: 'lttb'`**——ECharts 的折线降采样模式，但需要在 option 上显式开启（项目当前数据量小，未启用，如实说明）。

**D3. 前后端的"统一响应体"契约是怎么保证的？**

后端所有接口返回 `{code, message, data}`（成功码 0，`PageData` 包装分页），由全局异常处理器保证失败时也是同样结构。前端在**拦截器一处**按 `code !== 0` 判定业务失败，`http.get<T>` 用泛型把 `data` 的类型传给调用方。契约的落实靠两件事：**拦截器只有一个地方判 `code`**（不会到处手写判断），**类型强约束 `ApiResponse<T>`**（字段写错编译期就报错）。

**D4. 这套前端里你最想强调的一条经验？**

**"约定集中在一处，且只在一处。"** 具体四个例子：权限码的判定只在 `hasPermission` 一个函数（超管放行规则只有一处，与后端一致）；业务失败的判定只在响应拦截器一个地方（页面里不再写 `if (res.code !== 0)`）；图表的 init/resize/dispose 只在 `useEcharts`（三个页面复用）；时区与补零只在一处（仓储层 `timezone → date_trunc`，服务层补零）。集中之后，改规则是"改一处"，出问题也是"看一处"——这是这份代码里最值钱的部分。
