# 第一部分：APScheduler 5 个定时任务

## 1.1 为什么是 APScheduler

[app/tasks/scheduler.py](file:///e:/company%20project/backend/app/tasks/scheduler.py#L1-L4) 的文件头写明了定位与边界：

> APScheduler 定时任务（§22 超时回收 / §21 重试派发）。
> MVP 为单机调度（§76 不做分布式调度）；多实例部署时需叠加分布式锁或独立 worker。

选型理由：

| 方案 | 为什么不用 / 为什么用 |
|---|---|
| **APScheduler**（选用） | 纯 Python 库，**与应用同进程**，零外部依赖（不需要 Redis broker / 额外进程），配置极简。对一个"周期扫描 + 幂等服务调用"的诉求完全够用 |
| Celery | 需要 broker（Redis/RabbitMQ）+ worker 进程 + 监控，运维成本高；本项目要的是"定时触发"，不是"分布式任务编排" |
| 系统 cron | 与业务代码分离、无法复用 SQLAlchemy 会话与配置、日志分散、本地开发不可用 |
| 独立 worker 进程 | §76 明确 MVP 不做分布式调度，属于演进项而非当前需求 |

用 `BackgroundScheduler`（**后台线程**）而不是 `BlockingScheduler`（阻塞主线程）或 `AsyncIOScheduler`（需要事件循环）：FastAPI 的 `lifespan` 运行在异步上下文，但它**不能阻塞**——`BlockingScheduler.start()` 会卡住事件循环；`AsyncIOScheduler` 则要求任务是协程，而本项目的 service 层是**同步 SQLAlchemy**，用后台线程跑同步代码最自然（`BackgroundScheduler` 每个 job 在独立线程执行，不会阻塞 uvicorn 的请求处理）。

## 1.2 启动与关闭

[main.py#L44-L51](file:///e:/company%20project/backend/app/main.py#L44-L51)：

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    get_redis()          # 预热缓存连接；不可用时自动降级
    start_scheduler()    # §22 超时回收 / §21 重试派发
    logger.info("%s 启动完成，版本 %s", settings.APP_NAME, settings.APP_VERSION)
    yield
    shutdown_scheduler()
    logger.info("%s 已关闭", settings.APP_NAME)
```

用 `lifespan`（而非已废弃的 `@app.on_event("startup")`）的三个好处：**启动与清理写在同一处**（`yield` 前是启动、后是清理，不会漏写关闭逻辑）、**支持 async 上下文**、**与测试的 `with TestClient(app)` 天然配合**（进入上下文触发启动、退出触发关闭）。

`start_scheduler` 自身是**幂等**的，且不启用时安静返回：

```python
def start_scheduler() -> BackgroundScheduler | None:
    global _scheduler
    if not settings.SCHEDULER_ENABLED:
        logger.info("定时任务未启用（SCHEDULER_ENABLED=false）")
        return None
    if _scheduler is not None:
        return _scheduler          # 已启动：直接返回，避免重复注册
    ...
```

## 1.3 五个任务的统一骨架

五个任务函数的结构**完全同构**，这是刻意保持的一致性：

```python
def _timeout_recycle_job() -> None:
    with session_scope() as db:                    # ① 自己开会话（不依赖请求会话）
        try:
            OutboundTimeoutService(db).recycle()   # ② 调一个 service 方法，逻辑不在任务里
        except Exception:  # noqa: BLE001 - 定时任务不允许因单次异常退出
            logger.exception("超时回收任务执行失败")   # ③ 吞掉异常 + 记完整堆栈
```

三个共性设计各有原因：

1. **`session_scope()` 自开会话**：定时任务没有请求上下文，不能复用 `get_db` 依赖。`session_scope` 保证异常时回滚、结束时关闭。
2. **任务体只有"调用"没有"逻辑"**：真正的业务逻辑全在 service 层。好处是**同一段逻辑既能被定时任务调、也能被手动接口调**（例如回呼派单 `dispatch_due` 就是"定时任务与手动入口共用"，见 [callback_service.py#L346-L347](file:///e:/company%20project/backend/app/services/outbound/callback_service.py#L346-L347)）。任务文件因此永远不会变胖。
3. **`try/except Exception` + `logger.exception`**：APScheduler 默认行为是 job 抛异常时记日志后继续调度，但**异常信息可能被 APScheduler 的 logger 吞掉或格式不便排查**。这里显式捕获并 `logger.exception`（带完整堆栈）后**不外抛**——保证"一次失败不终止后续调度"，同时留下可排查的证据。`# noqa: BLE001` 是显式声明"这里宽泛捕获是故意的"，避免被 ruff 的 `BLE` 规则误报。

## 1.4 五个任务详解

### ① 超时回收 `timeout_recycle`（§22）

| 项 | 内容 |
|---|---|
| id / 间隔 | `timeout_recycle` / **30 秒**（`TIMEOUT_RECYCLE_INTERVAL_SECONDS`） |
| 服务方法 | `OutboundTimeoutService(db).recycle()`（默认 `limit=100`） |
| 扫描什么 | 状态为 `ASSIGNED`/`CALLING` 且 `timeout_at < now` 的执行记录 |
| 处理动作 | 标记 `TIMEOUT` → 写 `CallHistory`（保持与正常呼叫一致的可追溯性）→ **释放坐席预占** → 收尾会话 → 走失败重试阶梯 |
| 幂等保证 | `lock_by_id`（`SELECT ... FOR UPDATE`）+ **锁内复核** `status` 与 `timeout_at` |
| 事务粒度 | **每条记录一个事务**（`self.db.commit()` 在循环内） |
| 返回值 | `{scanned, recycled, skipped}`，另有 `task_completed`（见下） |
| 测试 | [test_outbound_execution.py::TestTimeoutRecycle](file:///e:/company%20project/backend/tests/api/test_outbound_execution.py#L636-L745)（回收、幂等、终态保留、跳过非超时、释放预占，共 5 个用例） |

源码里的四步"实现要点"注释（[timeout_service.py#L1-L8](file:///e:/company%20project/backend/app/services/outbound/timeout_service.py#L1-L8)）值得完整引用：

```
必须幂等：同一条记录被重复扫描只能产生一次有效回收。
实现要点：
1. SELECT ... FOR UPDATE 加锁；
2. 锁内复核状态与超时时间（幂等关键）；
3. 标记 TIMEOUT、写 CallHistory、释放坐席预占、收尾会话；
4. 走失败重试阶梯，让数据重新进入可执行队列。
```

**第 4 点很关键**：超时不是"死掉"，而是"按失败处理"——如果任务配了重试且次数没用完，记录会变成 `RETRY_WAITING` 并写入 `next_retry_at`，等 `retry_dispatch` 把它捡回来。**这就是两个任务之间的衔接**：超时回收负责"发现 + 定性"，重试派发负责"复活"。

**第 3 点里的"释放坐席预占"**：记录超时了，但占用它的坐席可能还挂着 `RESERVED`。回收时顺带释放（`_release_assignments`），否则坐席会一直显示"忙碌"。

还有一个**收尾动作**（[timeout_service.py#L64-L73](file:///e:/company%20project/backend/app/services/outbound/timeout_service.py#L64-L73)）：

```python
# 规则 2：回收后继续按任务检查，全部记录到终态的任务自动完成
completed = 0
for task_id in {candidate.task_id for candidate in candidates}:
    task = self.task_repo.get_by_id(task_id)
    if task is not None and maybe_complete_task(self.db, task, now=now):
        completed += 1
```

即：**回收让某些记录进入终态后，可能整批记录都到终态了 → 任务自动置为 COMPLETED**。用集合推导 `{candidate.task_id ...}` 去重，同一个任务只检查一次。

### ② 重试派发 `retry_dispatch`（§21）

| 项 | 内容 |
|---|---|
| id / 间隔 | `retry_dispatch` / **60 秒**（`RETRY_DISPATCH_INTERVAL_SECONDS`） |
| 服务方法 | `OutboundExecutionService(db).execute_due_retries(task_limit=20, record_limit=20)` |
| 扫描什么 | `list_running_ids(limit=20)` —— **运行中任务**（不是"到期的记录"） |
| 处理动作 | 对每个任务调 `execute_task(task_id, limit=20)`，由执行引擎按 `next_retry_at <= now` 挑出到期记录重新呼叫 |
| 返回值 | `{tasks, processed, success}` |
| 测试 | [test_outbound_execution.py](file:///e:/company%20project/backend/tests/api/test_outbound_execution.py)（重试链路）+ [test_outbound_task.py::TestRetryLimits](file:///e:/company%20project/backend/tests/api/test_outbound_task.py#L747) |

**"扫任务而不是扫记录"是有意为之**：执行引擎 `execute_task` 已经封装了"按任务配置的号码顺序逐个尝试"（§20）、按策略选取主叫号码并**原子扣减次数**（§13/§14）等逻辑。如果定时任务直接扫记录去拨号，就要把这些逻辑复制一份——那就变成"两套执行路径"。所以这里只做**任务级调度**，记录级筛选与执行全部交给同一个引擎。

重试阶梯集中在 [retry_policy.py](file:///e:/company%20project/backend/app/services/outbound/retry_policy.py#L44-L54)（被**执行流程与超时回收共用**，注释写明"避免执行与回收两处各写一份"）：

```python
def apply_failure_ladder(record, task, *, now, permanent=False) -> RecordStatus:
    if permanent or task.max_retry_count <= 0:
        mark_terminal(record, RecordStatus.FAILED)      # ① 永久失败 / 未配重试
    elif can_retry(record, task):
        schedule_retry(record, task, now=now)           # ② RETRY_WAITING + next_retry_at
    else:
        mark_terminal(record, RecordStatus.EXHAUSTED)   # ③ 重试已耗尽
    return record.status
```

`next_retry_at = now + timedelta(seconds=max(task.retry_interval, 0))`——**下一次可执行时间由任务配置的间隔决定**，用 `max(..., 0)` 防止配成负数导致时间倒退。终态集合 `TERMINAL_STATUSES = {SUCCESS, FAILED, EXHAUSTED, TIMEOUT}` 同时被用来同步名单行状态（`sync_name_list_status`）。

### ③ 预占释放 `reservation_expire`（§35）

| 项 | 内容 |
|---|---|
| id / 间隔 | `reservation_expire` / **30 秒**（`RESERVATION_EXPIRE_INTERVAL_SECONDS`） |
| 服务方法 | `OutboundAssignmentService(db).expire_reservations(limit=100)` |
| 扫描什么 | `list_expired_reservations(now=now, limit=100)` —— 状态为 `RESERVED` 且 `expires_at < now` 的坐席预占 |
| 处理动作 | `_release_assignment(assignment, reason=RELEASE_REASON_EXPIRED, expired=True)` |
| 幂等保证 | **复核三条件**：`status == RESERVED` 且 `expires_at is not None` 且 `expires_at < now` |
| 事务粒度 | 每条一个事务 |
| 返回值 | `{scanned, released, skipped}` |
| 测试 | [test_outbound_assignment.py::TestExpireReservations](file:///e:/company%20project/backend/tests/api/test_outbound_assignment.py#L465-L510)（过期释放一次 / 未过期不动） |

**背景**：坐席被"预占"（`RESERVED`）是派单里的关键状态——一个坐席同时只能被一个任务预占（由部分唯一索引在数据库层保证）。但预占是有**租约**的：`RESERVATION_TIMEOUT_SECONDS = 60` 秒。如果坐席一直没接受（`ACCEPTED`）或没开始呼叫，60 秒后必须自动释放，否则坐席会被"困"在预占态，整个派单链路堵死。

幂等的复核逻辑（[assignment_service.py#L186-L202](file:///e:/company%20project/backend/app/services/outbound/assignment_service.py#L186-L202)）：

```python
for candidate in candidates:
    assignment = self.agent_repo.get_assignment(candidate.id)
    # 复核状态，保证并发/重复扫描只释放一次（幂等）
    if (assignment is None
            or assignment.status != AssignmentStatus.RESERVED
            or assignment.expires_at is None
            or assignment.expires_at >= now):
        result["skipped"] += 1
        self.db.commit()
        continue
    self._release_assignment(assignment, reason=RELEASE_REASON_EXPIRED, now=now, expired=True)
    result["released"] += 1
    self.db.commit()
```

**"扫描"与"复核"是两次查询**（`candidates` 来自扫描，`get_assignment` 是复核）。看起来冗余，但这是幂等的核心：扫描到进入循环之间有时间差，期间坐席可能已经被别人释放/接受了。**复核通过才动手**。

### ④ 回呼派单 `callback_dispatch`（§46）

| 项 | 内容 |
|---|---|
| id / 间隔 | `callback_dispatch` / **60 秒**（`CALLBACK_DISPATCH_INTERVAL_SECONDS`） |
| 服务方法 | `CallbackService(db).dispatch_due(limit=settings.CALLBACK_DISPATCH_BATCH_SIZE)`（默认 **50**） |
| 扫描什么 | `list_due(now=now, limit=50)` —— 到 `scheduled_at` 的待回呼任务 |
| 处理动作 | 有指定坐席 → 校验（离线则视为无坐席）；无坐席 → `_pick_idle_agent` 挑一个空闲坐席；置 `agent_id` + `assigned_at` + `status = ASSIGNED` |
| 容错 | **单条 try/except**："单条失败不影响其余任务" |
| 事务粒度 | **整批一个事务**（循环外一次 `self.db.commit()`） |
| 返回值 | `{scanned, assigned, skipped}` |
| 测试 | [test_outbound_callback.py::TestAssignAndDispatch](file:///e:/company%20project/backend/tests/api/test_outbound_callback.py#L503-L580) |

这个任务的逻辑最"业务"：**到期 → 找人 → 派单**。两个细节：

```python
agent_id = task.agent_id
if agent_id is not None:
    agent = self.ref.get_agent_by_id(agent_id)
    if agent is None or agent.status == AgentStatus.OFFLINE:
        agent_id = None            # 指定的坐席离线了 → 视为没指定，改走自动挑人
if agent_id is None:
    agent = self._pick_idle_agent(tenant_id=task.tenant_id)
    if agent is None:
        skipped += 1               # 没有空闲坐席：跳过，下个周期再试
        continue
```

- **"指定的坐席离线 → 降级为自动挑人"**，而不是直接失败。业务上"客户该回呼了"比"必须由某个人回呼"更重要。
- **没有空闲坐席不是错误，是 `skipped`**。任务保持 `PENDING`，60 秒后下个周期再试——**"暂时做不到"不需要报警，"永远做不到"才需要**。

这里**没有**逐条提交（与其它四个不同），因为整批是一个自然的业务动作，且每条的处理很轻（只改三个字段）。容错靠循环内的 `try/except` 而不是事务粒度。

### ⑤ 质检回收 `qc_item_recycle`

| 项 | 内容 |
|---|---|
| id / 间隔 | `qc_item_recycle` / **300 秒**（`QC_ITEM_RECYCLE_INTERVAL_SECONDS`） |
| 服务方法 | `QcReviewService(db).recycle_timeout_items()`（默认 `DEFAULT_RECYCLE_BATCH`） |
| 扫描什么 | `list_timeout_items(now=now, limit)` —— `status = REVIEWING` 且 `timeout_at < now` 的质检明细 |
| 处理动作 | `repo.recycle(item_id, now=now)` → 退回 `PENDING`，清空 `locked_at`/`timeout_at`（**保留 `reviewer_id`**，不改归属） |
| 幂等保证 | 仓储层**行锁 + 锁内复核**（服务层 docstring 明确写了） |
| 事务粒度 | 每条一个事务（"避免长事务持锁"） |
| 返回值 | `{scanned, recycled, skipped}` |
| 测试 | [test_qc_review_flow.py::TestTimeoutRecycle](file:///e:/company%20project/backend/tests/api/test_qc_review_flow.py#L257-L300)（退回 PENDING / 幂等） |

服务层 docstring（[review_service.py#L146-L150](file:///e:/company%20project/backend/app/services/qc/review_service.py#L146-L150)）就是完整的实现说明：

```
把超时未提交的明细退回 PENDING（定时任务调用）。

幂等：仓储层用行锁 + 锁内复核，重复扫描不会产生副作用；
每条一个事务，避免长事务持锁。
```

**为什么间隔是 300 秒而不是 30 秒？** 因为租约本身就长：`QC_ITEM_LOCK_TIMEOUT_SECONDS = 1800`（30 分钟）。回收精度相对租约长度取 1/6（300s），既保证"过期后最多 5 分钟被释放"，又不会每 30 秒扫一遍大表做无用功。**间隔应与超时时长匹配，而不是越短越好**——这是定时任务调参的一条基本原则（超时回收 30s / 租约 60s，质检回收 300s / 租约 1800s，两处的比例是一致的）。

## 1.6 每个 job 的四个注册参数

五个 `add_job` 调用**参数完全一致**，只换函数、间隔、id：

```python
scheduler.add_job(
    _timeout_recycle_job,
    "interval",
    seconds=settings.TIMEOUT_RECYCLE_INTERVAL_SECONDS,
    id="timeout_recycle",
    max_instances=1,
    coalesce=True,
    replace_existing=True,
)
```

| 参数 | 含义 | 不设的后果 |
|---|---|---|
| `id` | 任务唯一标识 | 无法按 id 查询/暂停，且重复注册会叠加 |
| `max_instances=1` | **同一 job 最多 1 个实例并发** | 上一轮还没跑完（比如扫了 100 条慢记录）下一轮又开始，**同一批记录被两个线程同时扫**——虽然锁内复核能兜住正确性，但会浪费大量重复查询 |
| `coalesce=True` | 错过多次只**合并执行一次** | 应用挂起恢复后，错过的 10 次触发会**补跑 10 次**（每次都全量扫描），造成瞬时压力尖峰 |
| `replace_existing=True` | 同 id 已存在则**替换** | 重复调用 `start_scheduler` 会抛 `ConflictingIdError` |

> 注：`start_scheduler` 已有 `if _scheduler is not None: return _scheduler` 的守卫，`replace_existing=True` 是**第二层保险**（例如将来改成按配置热重载任务时不会冲突）。

`BackgroundScheduler(timezone="UTC")`：调度器内部时间基准统一 UTC，而业务时间（`timeout_at`、`next_retry_at`、`expires_at`）也全部是 `timestamptz`（UTC）。**全局只有一个时间基准，不出现"调度器用本地时间、数据库用 UTC"的隐性错位**。

## 1.7 五个任务共用的一套幂等范式

五个任务形态各异，但幂等做法是同一个套路：

```
扫描（宽松条件挑一批） → 加锁/复核（严格条件再判一次） → 动作 → 逐条 commit
```

| 任务 | "扫描"条件 | "复核"条件 |
|---|---|---|
| 超时回收 | 记录 `ASSIGNED/CALLING` 且 `timeout_at < now` | `SELECT FOR UPDATE` 后重判 status + timeout_at |
| 预占释放 | 预占 `RESERVED` 且 `expires_at < now` | 重新 `get_assignment` 重判 status + expires_at |
| 质检回收 | 明细 `REVIEWING` 且 `timeout_at < now` | `SELECT FOR UPDATE` 后重判 status + timeout_at |
| 重试派发 | 任务 `RUNNING` | 引擎内按 `next_retry_at <= now` 重判记录 |
| 回呼派单 | 回呼任务到 `scheduled_at` | 循环内 `try/except` + 状态机 `ASSIGNED` 边界 |

**为什么"扫描"要宽松、"复核"才严格？** 因为扫描是大范围 SQL（走索引批量取），复核是拿到锁之后的单条判断。扫描的目标是"别漏"，复核的目标是"别重复"。把两者混成一条严格 SQL 也能实现，但那样一旦漏判就永久错过；分成两步后，最坏情况是"扫进来又判出去"（`skipped`），**不会漏**。

> 这与 `docs/状态机与并发控制说明.md` 第二部分讲的 `claim/submit` 是同一思想：**能做幂等复核的地方就做，能靠数据库原子性判定的就不靠应用层时序**。

## 2.2 为什么必须用真实 PostgreSQL（§98）

[conftest.py#L1-L5](file:///e:/company%20project/backend/tests/conftest.py#L1-L5) 的 docstring 第一段就是这个决定：

> 并发相关能力（SELECT FOR UPDATE / 部分唯一索引 / JSONB）依赖真实 PostgreSQL，
> 因此测试库与开发库同为 PostgreSQL，不使用 SQLite 替代（§98 禁止假测试）。

三个**只有真实 PG 才能测**的能力：

| 能力 | 用在哪 | SQLite 下会怎样 |
|---|---|---|
| `SELECT ... FOR UPDATE` | 超时回收、质检回收的锁内复核 | SQLite 不支持行级锁，语句要么报错要么**被忽略**——测试"通过"了，但什么都没验证 |
| 部分唯一索引（`WHERE is_deleted = false`） | `ON CONFLICT` 的匹配目标、软删除后可复用名字 | SQLite 的 `ON CONFLICT` 语义与 PG 不同，**行为不一致** |
| `JSONB` / `AT TIME ZONE` / `date_trunc` | 操作日志详情、报表分桶 | 类型与函数都不存在或语义不同 |

用 SQLite 的代价是"**假通过**"——测试全绿但线上挂。这是 §98「禁止假测试」的直接落地。

### （1）用环境变量注入测试配置，且必须在导入 app 之前

[conftest.py#L11-L16](file:///e:/company%20project/backend/tests/conftest.py#L11-L16)：

### （3）会话级夹具跑 `upgrade head`，且复用同一个 Engine

```python
@pytest.fixture(scope="session")
def engine() -> Iterator[Engine]:
    _ensure_database_exists()
    os.environ["ALEMBIC_DATABASE_URL"] = settings.TEST_DATABASE_URL
    alembic_config = AlembicConfig(str(Path(BASE_DIR) / "alembic.ini"))
    alembic_config.set_main_option("script_location", str(Path(BASE_DIR) / "alembic"))
    command.upgrade(alembic_config, "head")
    eng = create_engine(settings.TEST_DATABASE_URL, pool_pre_ping=True, future=True)
    yield eng
    eng.dispose()
```

- `scope="session"`：**整个测试会话只建一次库、只迁移一次**（迁移有成本，不应每个用例跑一遍）。
- `ALEMBIC_DATABASE_URL`：让迁移脚本指向测试库而不是开发库——**这是"测试不动开发库"的关键一步**。
- `pool_pre_ping=True`：连接前先探活，避免长会话中被数据库断开连接而报错。

### （4）每个用例一个外层事务，结束整体回滚

```python
@pytest.fixture
def db_session(engine: Engine) -> Iterator[Session]:
    """每个用例一个外层事务，结束时整体回滚，保证用例互不影响。"""
    connection = engine.connect()
    transaction = connection.begin()
    session = sessionmaker(
        bind=connection, join_transaction_mode="create_savepoint", expire_on_commit=False
    )()
    try:
        yield session
    finally:
        session.close()
        transaction.rollback()      # ← 关键：数据从未真正落库
        connection.close()
```

这是**最快、最干净的隔离方式**：不需要每个用例去 `TRUNCATE` 几十张表（那会很慢，还要处理外键顺序），而是"在事务里干完所有事、最后回滚"。用例之间天然互不影响。

`join_transaction_mode="create_savepoint"` 是 SQLAlchemy 2.0 的能力：**当被测代码调用 `session.commit()` 时，实际上是"释放一个 SAVEPOINT"而不是提交外层事务**。这非常重要——因为被测的 service 层代码里到处是 `self.db.commit()`（比如超时回收的逐条提交）。如果没有 savepoint 语义，service 一 commit，外层事务就真的提交了，回滚夹具就失效了。

`expire_on_commit=False`：commit 后不要让 ORM 把对象标记为过期（否则夹具里持有的对象在 commit 后访问属性会触发一次额外查询，甚至报错）。

### （5）接口与用例共用同一个会话

```python
@pytest.fixture
def client(db_session: Session) -> Iterator[TestClient]:
    """覆盖 get_db，使接口与用例共用同一事务会话。"""
    def _override_get_db() -> Iterator[Session]:
        yield db_session
    app.dependency_overrides[get_db] = _override_get_db
    with TestClient(app) as test_client:
        yield test_client
    app.dependency_overrides.clear()
```

**这是整个测试体系最巧妙的一处**。正常情况接口会通过 `get_db` 依赖自己开一个会话——那个会话看不到用例里"尚未提交"的数据（因为用例在事务里）。用 `dependency_overrides` 把 `get_db` 换成"返回用例的会话"，就实现了：

- 用例里 `db_session.add(某条任务)` + `flush()` → 接口查询**能看见**它；
- 用例结束时整体回滚 → **什么都不留下**。

于是"造数据"和"调接口"在同一个事务里，既真实又干净。`with TestClient(app)` 用上下文管理器是为了触发 `lifespan`（虽然测试里 `SCHEDULER_ENABLED=false`，但 Redis 预热等逻辑仍需走一遍，且保证与生产一致的启动路径）。

### 附加：屏蔽操作日志

```python
@pytest.fixture(autouse=True)
def _silence_operation_log(monkeypatch: pytest.MonkeyPatch) -> None:
    """操作日志中间件走独立会话，测试中屏蔽以免污染开发库。"""

```

`autouse=True` 全局生效。原因写在注释里：**操作日志中间件用的是独立会话**（因为它要 `run_in_threadpool` 异步写，不能复用请求会话），**不会被用例的外层事务回滚覆盖** → 每个非 GET 接口测试都会往库里插一条操作日志。用 `monkeypatch` 换掉这个函数，测试就干净了。

## 2.6 唯一的真并发用例

[test_outbound_number_concurrency.py](file:///e:/company%20project/backend/tests/integration/test_outbound_number_concurrency.py#L56-L78)：

```python
CONCURRENCY_ATTEMPTS = 24
CONCURRENCY_WORKERS = 8
USAGE_LIMIT = 5

def test_concurrent_consume_never_exceeds_limit(engine, committed_number) -> None:
    """24 次并发扣减、上限 5：成功次数必须正好等于 5，且 used_count 不回退。"""
    with ThreadPoolExecutor(max_workers=CONCURRENCY_WORKERS) as pool:
        results = list(pool.map(
            lambda _: _consume_in_own_connection(engine, number_id),
            range(CONCURRENCY_ATTEMPTS),
        ))
    successes = sum(1 for affected in results if affected == 1)
    assert successes == USAGE_LIMIT
    assert failures == CONCURRENCY_ATTEMPTS - USAGE_LIMIT
```

三个设计点值得注意：

1. **不用事务回滚夹具**。文件头注释说明："本用例不使用事务回滚夹具，而是用独立连接真实提交数据并并发扣减"——因为**并发必须真实提交**（回滚的事务对其它连接不可见，测不出锁竞争）。所以用了一个自建夹具 `committed_number`：**独立会话真实提交**，测试结束再**物理删除**（`delete(OutboundNumber)` + `delete(Tenant)`）。
2. **每次扣减一个独立连接 + 独立事务**（`_consume_in_own_connection`），这才是"模拟真实并发调用"。
3. **断言"恰好 5 次成功"而不是"不超过 5 次"**。后者是弱断言——如果所有并发请求都失败（成功 0 次），`<= 5` 也成立，测试形同虚设。**断言精确值才能真正锁住"既不过扣也不漏扣"**。

验证的是 `OutboundNumberRepository.consume_atomically`——与质检 `claim` 同一套"带条件原子 UPDATE + rowcount"手法（§13/§73）。

> 完整说明：**目前只有这一处是真并发**。质检的 `claim/submit`、超时回收、预占释放等并发写路径，验证方式是"串行调用 + 断言 `rowcount` 语义与状态条件"，**不是真并发压测**。机制相同（都是条件原子 UPDATE），但风险分布不同——号码扣减是全员共享的热点行，质检明细是人各一条，前者才值得付线程池的成本。

## 2.7 ruff 作为提交前门槛

[pyproject.toml](file:///e:/company%20project/backend/pyproject.toml) 全部配置：

```toml
[tool.ruff]
line-length = 100
target-version = "py310"
exclude = ["alembic/versions"]

[tool.ruff.lint]
select = ["E", "F", "I", "B", "UP"]
# B008：FastAPI 的 Depends/Query 惯用法，属正常写法
ignore = ["B008"]

[tool.ruff.lint.per-file-ignores]
# conftest 需要在导入 app 之前注入测试环境变量（如 BCRYPT_ROUNDS）
"tests/conftest.py" = ["E402"]

[tool.pytest.ini_options]
testpaths = ["tests"]
```

逐项解读：

| 配置 | 值 | 含义 |
|---|---|---|
| `line-length` | 100 | 单行上限 100 字符（比黑默认 88 宽，适合有中文注释与较长类型注解的代码） |
| `target-version` | `py310` | 按 Python 3.10 语法分析——`UP` 规则据此建议"这个写法在 3.10 有更现代的替代" |
| `exclude` | `alembic/versions` | **迁移文件是自动生成的**（含大量固定格式代码），格式化它们没有收益还会造成无意义 diff |
| `select` | `E,F,I,B,UP` | 见下表 |
| `ignore` | `B008` | 见下 |
| `per-file-ignores` | `tests/conftest.py: E402` | 见下 |

**五个规则集分别管什么**：

| 规则集 | 名称 | 管什么 | 例子 |
|---|---|---|---|
| `E` | pycodestyle errors | 基础风格：行宽、空行、空格、缩进 | 行超过 100 字符 |
| `F` | Pyflakes | **真 bug**：未使用导入/变量、未定义名字、f-string 缺占位符 | `import os` 后没用到；`f"值={x}"` 写成 `f"值=x"` |
| `I` | isort | **导入排序与分组**（标准库 / 三方 / 本项目） | 导入顺序错乱 |
| `B` | flake8-bugbear | 常见陷阱与反模式 | 可变默认参数、循环里 `except` 太宽、`assert` 用于运行时逻辑 |
| `UP` | pyupgrade | **语法现代化** | `Optional[int]` → `int \| None`；`Dict` → `dict` |

选这五个的理由：**覆盖"能自动改的格式（E/I/UP）+ 能发现真 bug 的检查（F/B）"，同时避开"纯主观偏好"的规则集**（没选 `C90` 圈复杂度、没选 `N` 命名风格、没选 `D` docstring 格式——这些噪音大、争议多，容易让人为了过检查而写废代码）。

**为什么 `ignore = ["B008"]`**：`B008` 报的是"函数调用作为默认参数值"（`def foo(x=[]):` 那种陷阱）。但 FastAPI 的惯用法就是这样的：

```python
def tenant_scope_optional(
    tenant_id: int | None = Query(default=None, gt=0, ...),   # ← B008 会报这个
    current_user: User = Depends(get_current_user),           # ← 以及这个
)
```

`Depends()` / `Query()` 作为默认值**是框架设计的一部分**（它们返回的是"参数声明对象"而非实际值）。全局忽略 `B008` 而不是逐行 `# noqa`——因为**全项目每一处依赖注入都长这样**，逐行加注释会把代码淹掉。代码注释里也写明了这个理由。

**为什么 `tests/conftest.py` 豁免 `E402`**：`E402` 是"模块级导入不在文件顶部"。conftest 必须在 `import app` 之前执行 `os.environ.setdefault(...)`（见 2.3 第 1 点），所以**结构上必然违反 E402**。这是"规则与需求的真实冲突"，用 per-file-ignores 精确豁免一个文件，而不是放宽全局规则。

**"提交前门槛"怎么落地**：`pyproject.toml` 只定义规则，执行靠命令——

```bash
cd backend
ruff check app tests      # 检查（本会话实测：全通过）
ruff format --check app tests   # 可选：格式检查
```

它出现在开发流程里的位置（`docs/项目说明.md` 的"开发固定动作"）是：**改完代码 → `ruff check` → `pytest` → 提交**。ruff 的定位是**最快的过滤器**：Rust 实现、整个仓库通常在眨眼间跑完，能拦住"未使用导入、行太长、导入顺序乱、拼错名字"这类**低级但高频**的问题，让人不必把 CI 时间浪费在这些上面。

# 第三部分：面试问答

## A. 定时任务（15 题）

**A1. 为什么选 APScheduler，而不是 Celery / cron / 独立 worker？**

需求是"周期扫描 + 调用一个幂等的 service 方法"，不是"分布式任务编排"。APScheduler 是纯 Python 库、**与 FastAPI 同进程**、零外部依赖（不需要 broker 和 worker 进程），配置只有几行。Celery 要 broker + worker + 监控，运维成本远大于收益；cron 无法复用 SQLAlchemy 会话与项目配置、本地开发不可用；独立 worker 属于 §76 明确排除的演进项。**够用就选最轻的**。

**A2. `BackgroundScheduler` / `BlockingScheduler` / `AsyncIOScheduler` 有什么区别？为什么用第一个？**

`BlockingScheduler` 会在调用线程里阻塞（`start()` 不返回），放在 FastAPI 的 `lifespan` 里会**卡死事件循环**。`AsyncIOScheduler` 要求任务是协程，而项目 service 层是**同步 SQLAlchemy**，改造成本高。`BackgroundScheduler` 用**后台线程池**执行 job，`start()` 立即返回，天然适配"同步 service + 异步 Web 框架"的组合。

**A3. 为什么用 `lifespan` 而不是 `@app.on_event`？**

三个理由：① `on_event` 已被 FastAPI 标记为废弃；② `lifespan` 把**启动与清理写在同一处**（`yield` 前启动、后清理），结构上不会漏写 `shutdown`；③ 支持 async 上下文，且与测试的 `with TestClient(app)` 天然配合（进出上下文即触发启动/关闭）。

**A4. `max_instances=1`、`coalesce=True`、`replace_existing=True` 分别解决什么？**

- `max_instances=1`：防止上一轮还没跑完（比如扫了 100 条慢记录）下一轮又启动，导致**同一批记录被两个线程同时扫**。正确性上锁内复核能兜住，但会浪费大量重复查询。
- `coalesce=True`：应用挂起/重启恢复后，**错过的多次触发合并成一次**。否则会补跑 N 次全量扫描，造成瞬时压力尖峰。
- `replace_existing=True`：同 id 的任务已存在时替换而不是抛 `ConflictingIdError`，是"重复注册"的第二层保险。

**A5. 任务里为什么要自己 `try/except` 把异常吞掉？**

APScheduler 默认会在 job 抛异常时记日志并继续调度，但**异常日志可能被打到 APScheduler 自己的 logger 里、格式不便于排查**。显式捕获后 `logger.exception`（带完整堆栈）能保证：① 一次失败不会终止后续调度；② 留下可定位的证据。`# noqa: BLE001` 是显式声明"这里的宽泛捕获是故意的"，避免被 ruff 的 `BLE` 规则误判为疏漏。

**A6. 为什么每个任务自己开 `session_scope()`，而不复用请求的 `db`？**

定时任务**没有请求上下文**，拿不到 `Depends(get_db)`。而且它需要**独立、可控的事务边界**：`session_scope()` 保证"异常回滚、正常提交、结束关闭"。如果硬塞一个全局会话，任务之间会互相污染。

**A7. 为什么超时回收、预占释放、质检回收是"逐条 commit"，而回呼派单是"整批 commit"？**

逐条提交是因为这些任务**每条都是一次独立的业务裁决**（一条记录超时、一个预占过期、一条明细超时），互不依赖，且单条处理可能涉及多张表（记录 + 呼叫历史 + 会话 + 坐席预占），逐条提交能**避免长事务长时间持锁**，也让"处理到第 50 条时崩了"不会丢掉前 49 条的成果。回呼派单每条只改三个字段、整批是一个自然的业务动作，一次提交更简洁，容错靠循环内的 `try/except`。

**A8. 定时任务的幂等是怎么保证的？**

统一范式：**扫描（宽松）→ 加锁/复核（严格）→ 动作 → 提交**。三个"回收类"任务都是先按宽松条件选出候选，然后在**拿到锁之后重新判断一次严格条件**（status 是否还是预期值、超时时间是否真的到了）。重复扫描最坏结果是 `skipped`，不会产生第二次副作用。调用方返回的 `{scanned, recycled, skipped}` 也让幂等**可被测试断言**——第二次扫描 `recycled == 0`。

**A9. 多实例部署时这些任务会怎样？现在怎么处理？**

会**重复触发**（每个实例的 APScheduler 都会跑）。文件头注释明确写了"多实例部署时需叠加分布式锁或独立 worker"。不过目前**后果可控**：所有任务都是幂等的（行锁 + 锁内复核 + 每条 `rowcount` 判定），重复触发只会得到 `recycled = 0` 之类的空结果，不会产生错误数据。代价只是**重复的数据库查询**。要彻底解决需要引入分布式锁（Redis `SET NX`）或选主/独立 worker——属于 §76 之后的演进项，**如实说明：当前未实现**。

**A10. 为什么调度器时区是 UTC？**

全局只有一个时间基准。业务时间字段（`timeout_at`、`next_retry_at`、`expires_at`）都是 `timestamptz`（内部存 UTC），调度器也用 UTC，**不存在"调度器按本地时间算、数据库按 UTC 比"的隐性错位**。反之如果用 `Asia/Shanghai`，跨时区部署或多地机房时会引入难查的错位。

**A11. 重试派发为什么扫"运行中的任务"，而不是扫"到期的记录"？**

因为记录级执行逻辑（按号码顺序逐个尝试、按策略选主叫号码并**原子扣减次数**、失败收尾走重试阶梯）已经完整封装在 `execute_task` 里。定时任务如果直接扫记录去拨号，就得把这套逻辑复制一份，变成"两套执行路径"——**必然出现行为不一致**。所以定时任务只做**任务级调度**，记录级筛选交给同一个引擎。

**A12. 重试阶梯有哪三种去向？**

`apply_failure_ladder`（被**执行流程与超时回收共用**）：① **永久性失败**（如无可呼叫号码）或任务未配重试（`max_retry_count <= 0`）→ `FAILED`；② 还有重试机会（`retry_count < max_retry_count`）→ `RETRY_WAITING` + `next_retry_at = now + retry_interval`；③ 否则（重试已耗尽）→ `EXHAUSTED`。抽成独立模块的注释写明理由："避免执行与回收两处各写一份"。

**A13. `next_retry_at` 为什么用 `max(task.retry_interval, 0)`？**

防止配置成负数导致 `next_retry_at` 落到过去，记录会被立刻反复重试（退化成忙等）。`max(..., 0)` 保证至少是"现在"，即"立刻可重试"而不是"时间倒退"。

**A14. 定时任务的间隔为什么不是越短越好？**

间隔应与**超时时长**匹配。质检的租约是 `QC_ITEM_LOCK_TIMEOUT_SECONDS = 1800`（30 分钟），回收间隔 300 秒（1/6），含义是"过期后最多 5 分钟内被释放"；外呼超时租约 60 秒、回收间隔 30 秒（1/2），含义是"过期后最多 30 秒被回收"。两处比例一致。间隔过短只会在大多数轮次里扫到"没有过期项"，白白消耗数据库。

**A15. 测试里怎么处理定时任务？**

`conftest.py` 在导入 app 之前注入 `SCHEDULER_ENABLED=false`，测试进程内**根本不启动调度器**。用例需要验证回收/派发逻辑时**直接调 service 方法**（如 `OutboundTimeoutService(db).recycle()`）。这样时刻完全可控——否则后台线程会在不确定的时刻修改数据，用例随机失败。**"关掉调度、手动触发"是可复现测试的关键。**

## B. 测试体系（13 题）

**B1. 为什么用真实 PostgreSQL 而不是 SQLite？**

因为要验证的恰恰是 PG 的特性：`SELECT ... FOR UPDATE`（行锁）、**部分唯一索引**（`WHERE is_deleted = false`，也是 `ON CONFLICT` 的匹配目标）、`JSONB`、`AT TIME ZONE` / `date_trunc`。SQLite 不支持行级锁（语句被忽略或报错）、`ON CONFLICT` 语义不同、函数缺失——结果是**测试全绿但线上挂**。conftest 的 docstring 直接引了 §98「禁止假测试」。

**B2. 用例之间怎么隔离的？**

每个用例一个**外层事务**：`connection.begin()` → 用例内所有操作（含 service 里的 `commit()`）都在这个事务里 → 结束时 `transaction.rollback()`。数据从未真正落库，用例之间天然互不影响。比"每个用例 TRUNCATE 几十张表"快得多，也不用处理外键删除顺序。

**B3. `join_transaction_mode="create_savepoint"` 是干什么的？**

**这是这套隔离方案能成立的关键**。被测 service 代码里大量调用 `session.commit()`（比如超时回收的逐条提交）。默认情况下，`commit()` 会把外层事务也一起提交——用例结束时的 `rollback()` 就变成空操作，隔离失效。`create_savepoint` 让每次 `session.commit()` 实际是"释放一个 SAVEPOINT"，外层事务依然掌握在夹具手里，最后整体回滚。

**B4. 接口测试怎么看到用例里尚未提交的数据？**

用 `dependency_overrides` 把 `get_db` 换成"返回用例的 `db_session`"：

```python
app.dependency_overrides[get_db] = lambda: iter([db_session])
```

正常情况下接口会自己开会话、看不到用例事务里未提交的数据。覆盖后接口与用例**共用同一会话**，于是"用例造数据 → 调接口"在同一个事务里完成，既真实又干净（结束时一起回滚）。

**B5. 为什么 `db_session` 要设 `expire_on_commit=False`？**

默认 `expire_on_commit=True` 会在 commit 后把 ORM 对象标记为"过期"，下次访问属性会触发额外查询（且如果会话已关闭会直接报错）。夹具里持有的对象（如 `tenant`）在 service 内部 commit 后可能被用例再次访问（例如断言 `tenant.id`），设为 `False` 避免这种意外查询。

**B6. 为什么要 `monkeypatch` 掉操作日志的写入？**

因为操作日志中间件用的是**独立会话**（它要 `run_in_threadpool` 异步写，不能复用请求会话）。独立会话**不受用例外层事务的回滚保护**——每个非 GET 接口测试都会真的往库里插一条日志。用 `autouse=True` 的夹具把 `app.main._write_operation_log` 换成 `noop` 就干净了。这个夹具反过来也揭示了一个边界：**凡绕过请求会话的写入，都不受回滚隔离保护**。

**B7. 为什么环境变量要在 `import app` 之前注入？**

因为 `settings` 是**模块级单例，在 import 时就读环境变量并固化**。放在 `import app` 之后注入完全无效（此时 `settings.BCRYPT_ROUNDS` 已经是 12 了）。所以 conftest 里用 `os.environ.setdefault(...)` 顶在文件最前面，也因此 `pyproject.toml` 给这个文件单独豁免了 `E402`（导入不在顶部）。

**B8. `BCRYPT_ROUNDS=4` 是什么考虑？**

bcrypt 的计算量随 rounds **指数增长**。测试里有大量登录用例（`user_token` 夹具每次登录一次），用生产值 12 会让整个套件慢几分钟；4 在测试环境足够（我们验的是"密码校验逻辑正确"，不是"哈希强度"）。用 `setdefault` 所以 CI 仍可覆盖。

**B9. `ALEMBIC_DATABASE_URL` 为什么要单独设？**

让迁移指向**测试库**而不是开发库。测试会话开始时 `engine` 夹具执行 `command.upgrade(config, "head")`——如果 URL 没改，这一步就会把迁移跑到开发库上。这是"测试不动开发库"的关键一步。

**B10. 真实并发用例是怎么写的？**

`ThreadPoolExecutor(max_workers=8)` + 24 次任务，**每次扣减用独立连接、独立事务**（`_consume_in_own_connection` 里 `sessionmaker(bind=engine)()`），模拟真实并发调用。断言**成功次数恰好等于上限（5）**——这是关键：弱断言 `<= 5` 在"全部失败"时也成立，形同虚设；精确断言才能同时锁住"不过扣"与"不漏扣"。

**B11. 为什么并发用例不用事务回滚夹具？**

因为**并发必须真实提交**：回滚的事务对其它连接不可见，拿不到行锁竞争，测不出并发行为。所以该用例自建夹具 `committed_number`——独立会话**真实提交**数据，测试结束后**物理删除**（`delete` 号码与租户）做清理。文件头注释写明了这个取舍。

**B12. 状态机测试为什么放在 `unit/` 且不依赖数据库？**

因为状态机是**纯规则**（`dict[状态, frozenset[状态]]`），不需要数据库就能完整验证。放在 unit 意味着毫秒级、无外部依赖、失败定位到单条边。如果把状态机和 DB 搅在一起，验证"某条边非法"要付一次数据库连接的成本，得不偿失。**分层原则：纯逻辑放 unit，需要真实环境的放 integration。**

**B13. 整套用例有多少、跑多久？覆盖了哪些重点？**

本会话一次完整运行：**756 passed in 33.43s**（**前置条件：PostgreSQL 在运行**，因为测试库是真实 PG；Docker 未启动时整套跑不起来）。目录上：`api/` 20 个文件、`unit/` 12 个、`integration/` 2 个。重点覆盖：状态机（4 个纯内存文件）、分批派发与幂等、乐观锁与 `rowcount` 语义、报表分桶补零、RBAC 与数据范围、真实并发扣减。

## C. ruff 与质量门槛（7 题）

**C1. ruff 是什么？为什么不用 flake8 + isort + black 组合？**

ruff 是 **Rust 实现**的 Python linter + formatter，把 flake8、isort、pyupgrade、flake8-bugbear 等几十个工具的能力**合并到一个工具**里，速度快一两个数量级（整个仓库通常眨眼间跑完）、**配置集中在一处**（`pyproject.toml`）、不需要维护一堆插件版本。代价是规则实现上与各原工具可能有细微差异，但对本项目够用。

**C2. 选了哪五个规则集？分别管什么？**

`E`（pycodestyle：行宽/空格/空行等基础风格）、`F`（Pyflakes：**真 bug**——未使用导入、未定义名字、f-string 缺占位符）、`I`（isort：导入排序与分组）、`B`（flake8-bugbear：常见陷阱，如可变默认参数、过宽的 except）、`UP`（pyupgrade：语法现代化，如 `Optional[int]` → `int | None`）。组合覆盖了"能自动改的格式"+"能发现真 bug 的检查"。

**C3. 为什么没选更多规则集（比如复杂度、命名、docstring）？**

因为那些规则**噪音大、争议多**（`N` 命名风格、`D` docstring 格式、`C90` 圈复杂度阈值都是主观的），容易逼着人为了过检查写废代码或堆 `# noqa`。**门槛的意义在于"拦住真问题且让人愿意遵守"**，规则越多不等于质量越高。

**C4. 为什么 `ignore = ["B008"]`？**

`B008` 报"函数调用作为默认参数值"（`def f(x=[]):` 那种可变默认值陷阱）。但 FastAPI 的惯用法就是这样：`tenant_id: int | None = Query(default=None, gt=0)`、`current_user: User = Depends(get_current_user)`。这是**框架设计的一部分**（这些调用返回"参数声明对象"而非实际值）。项目**每一处依赖注入都长这样**，逐行 `# noqa` 会淹掉代码，所以全局忽略并写注释说明理由。

**C5. 为什么排除 `alembic/versions`？**

迁移文件是**自动生成的**，含大量固定格式样板代码（`sa.Column(...)`、`op.create_table(...)`），格式化它们没有收益，反而会制造与 Alembic 生成器不一致的**无意义 diff**（下次 autogenerate 又改回来）。

**C6. 为什么单独给 `tests/conftest.py` 豁免 `E402`？**

`E402` 是"模块级导入不在文件顶部"。conftest **必须在 `import app` 之前**执行 `os.environ.setdefault("BCRYPT_ROUNDS", "4")` 等注入（因为 `settings` 在 import 时就固化了配置），结构上必然违反 `E402`。这是"规则与需求的真实冲突"，用 `per-file-ignores` **精确豁免一个文件**，而不是放宽全局规则（放宽全局会让别处真正的"导入位置错误"漏过）。

**C7. "ruff 作为提交前门槛"具体怎么落地？**

`pyproject.toml` 只定义规则，执行靠命令：`ruff check app tests`。它出现在开发流程里的位置是 **改完代码 → `ruff check` → `pytest` → 提交**。定位是**最快的过滤器**：Rust 实现、几乎瞬时完成，拦住"未使用导入、行太长、导入顺序乱、名字拼错"这类**低级但高频**的问题，避免把 CI 时间浪费在它们身上。本会话实测 `ruff check app tests` **全通过**。

## D. 综合（3 题）

**D1. 定时任务、状态机、乐观锁这三者是怎么协作的？**

以"外呼记录超时"为例串起来：定时任务 `timeout_recycle`（调度层）触发 `OutboundTimeoutService.recycle`（业务层）→ 用 `SELECT FOR UPDATE` + 锁内复核（并发层，与乐观锁同一思想）确保幂等 → 通过**状态机**的合法性约束把记录从 `ASSIGNED/CALLING` 置为 `TIMEOUT`（规则层）→ 走**重试阶梯**决定是 `RETRY_WAITING` 还是 `EXHAUSTED`（策略层）→ 下一个定时任务 `retry_dispatch` 把它捡回来。**四层各管一件事，互不越界。**

**D2. 如果让你改进这套工程与质量体系，你会先做什么？**

按性价比排三个：① **引入 CI 流水线**（当前 ruff 与 pytest 是"人工门槛"，靠人记得跑；应在 CI 里对每个 MR 强制跑 `ruff check` + `pytest`，附 PostgreSQL service）；② **补一个"质量数据"看板**（当前 756 个用例、覆盖率数字未纳入自动化度量，应加 `pytest-cov` 并把覆盖率趋势记录下来）；③ **给并发路径补真并发用例**（目前只有号码扣减一处的 `ThreadPoolExecutor` 用例，质检 `claim/submit`、超时回收的并发正确性靠"串行 + rowcount 语义"验证——机制相同，可以按 `Barrier` 对齐起跑时刻再补几个）。**如实说明：这三项当前均未实现。**

**D3. 这套体系里你最想强调的一条经验？**

**"把不确定性从测试里赶出去。"** 四个具体做法：**关掉后台调度**（`SCHEDULER_ENABLED=false`，改由用例手动触发）、**固定外部 Provider 为 mock**（`ASR_PROVIDER=mock`）、**降低无关成本但保留被测语义**（`BCRYPT_ROUNDS=4` 砍的是哈希强度不是校验逻辑）、**用事务回滚而不是清库**（隔离且快）。这四条的共同点是：**让失败只可能来自被测代码，而不是来自环境**——测试的可靠性比测试的数量重要得多。
