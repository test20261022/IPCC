## 封面与导读

**一句话定位**：一套面向企业的**呼叫中心一体化平台**——两大业务域并行：**智能外呼**（名单导入 → 建任务 → 选号码 → 坐席派单/自动呼叫 → 结果回写 → 重试/超时回收 → 会话小结 → IVR/回呼 → 报表监控）与**对话质检**（客服对话导入 → ASR 语音转写 → 批量派发 → 专家领取评分 → 案例库沉淀 → 完成率报表）。后端用 **FastAPI + Router–Service–Repository 三层架构 + PostgreSQL 16**，前端 **Vue3 + TypeScript + Element Plus**，认证授权收敛为**一条依赖注入链**，并发正确性靠**数据库而非应用锁**保证。

## 第 1 章 项目全景（3W2H）

> 本章按 What / Why / Who / How / How much 五个维度完整介绍系统；**§1.6** 以「通俗理解」小节补上大白话类比与白话模块说明。**模块级实现细节与代码路径详见第 2 章**，本章只做架构级概述。

### 1.1 What —— 这是一个什么项目

这是一套**呼叫中心一体化平台**，对外名称「企业管理平台」。它把「打电话」这件事全流程管起来，再把「客服服务质量」这件事量化管起来。

它完整地做了四件事：

1. **外呼执行**：把客户名单（Excel/CSV）导入系统，建外呼任务，从号码池里挑主叫号码，派给坐席或自动拨打，把网关回调的呼叫结果写回，失败的按策略重试，超时的自动回收。
2. **坐席调度**：管理坐席状态（空闲/预占/忙碌/暂停/离线），坐席一示闲就自动把最该打的单子预占给他，预占 60 秒不接就自动释放。
3. **对话质检**：把客服聊天记录或通话录音收进来，录音先经 ASR 转写成「说话人 + 文本 + 时间戳」的分段消息，再派发给质检专家打分，沉淀优秀案例，出完成率报表。
4. **平台底座与服务化**：RBAC 权限体系、多租户隔离、统一响应契约、操作审计日志、OpenAPI 文档、Vue3 前端 21 个页面、Docker Compose 本地编排。

**规模盘点（可核对）**：**38 张业务表**、**8 个 Alembic 版本**、**144 个 HTTP 端点**（认证 4 / 外呼 103 / 质检 37）、**63 个 RBAC 权限码**（外呼 40 / 质检 23）、**21 个前端页面**、**5 个定时任务**、**39 个测试文件 / 756 条用例**（需 PostgreSQL 在运行）。

> **大白话**：说白了就四件事——① 把名单倒进来、逐个打电话；② 让坐席不空转，一闲下来立刻有活干；③ 把客服的聊天/录音拿来打分；④ 把权限、租户、日志、接口文档这些「物业设施」配齐。规模上是 38 张表、144 个接口、21 个页面的中大型项目。

#### 1.1.1 两大业务域的边界

| 维度 | 智能外呼 | 对话质检 |
| --- | --- | --- |
| 关心的核心问题 | 「电话有没有打出去、打没打通」 | 「客服说得好不好」 |
| 主体对象 | 任务 / 名单 / 记录 / 会话 / 呼损 | 对话 / 消息 / 质检任务 / 质检明细 / 结果 |
| 时间特征 | 实时、高频、强并发（10 万级派发） | 批量、准实时（报表按天/按分钟聚合） |
| 代码包 | `models/outbound`、`services/outbound`、`repositories/outbound` | `models/qc`、`services/qc`、`repositories/qc` |

> **为什么分成两个包**：外呼关注「打出去」、质检关注「说得怎么样」，是**不同的限界上下文**。质检有独立的模型/服务/仓储/校验，只在基础设施层（`db/session`、`core`、`utils`、`providers`）复用，避免把外呼 22 张表的语义搅浑。

> **大白话**：外呼管「电话打没打通」，质检管「话说得好不好」，两门生意逻辑根本不同，所以代码分两个抽屉放——改质检不会碰坏外呼，就像财务和仓库各记各的账。

### 1.2 Why —— 为什么做、为什么这样选技术

#### 1.2.1 业务动因：为什么需要这个系统

呼叫中心的痛点集中在三处，这套系统的设计正是围绕它们展开：

1. **人工拨号效率低、容易漏**：名单几千上万条，靠人一个个拨既慢又容易重复拨、漏拨。
2. **并发场景极易出错**：多个坐席同时抢单、同时抢号码、批量派发同时触发——「先查再改」的写法必然出现重复领取、次数超发。
3. **服务质量无法量化**：客服到底说得好不好，靠抽查几分钟录音，既主观又覆盖不到。

> **大白话**：痛点就三条——人拨号又慢又漏；一群人同时抢一件事必然乱（重复领、次数超发）；客服干得好不好全凭主管随手听几分钟，主观且覆盖不到。

#### 1.2.2 方法论动因：为什么选 PostgreSQL 而不是 MySQL

| 能力诉求 | PostgreSQL（本项目） | MySQL 替代方案 |
| --- | --- | --- |
| 软删除后名字可复用 | **部分唯一索引**（`WHERE is_deleted = false`） | 无，需应用层查重 |
| 10 万条派发幂等 | `INSERT … SELECT … ON CONFLICT DO NOTHING` | 需应用层去重 + 分批插入 |
| 超时回收并发安全 | `SELECT … FOR UPDATE` 行锁 | 需应用层分布式锁 |
| 结构化明细存储 | `JSONB`（导入失败明细 / 评分明细） | JSON 类型功能弱 |
| 时间一致性 | `timestamptz`（统一 UTC） | `datetime` 需自行约定时区 |

结论：项目最危险的几个并发操作都是靠「**一条 SQL 原子搞定**」来保证正确性的，这些写法是 PG 特有的。换 MySQL 等于把保险箱换成普通锁，还得自己盯着。

> **大白话**：选 PG 不是赶时髦——项目里最危险的几个动作（一次派 10 万条、多人抢同一条、并发回收）都得靠数据库「一条语句就锁死」。这些写法别的数据库要么没有、要么得自己在代码里加锁，等于把保险箱换成普通锁，还得自己盯着。

#### 1.2.3 一条贯穿全局的设计基调

**并发与幂等靠数据库而不是应用锁**：
- 批量派发 → `INSERT … SELECT` + `ON CONFLICT DO NOTHING`；
- 领取 / 提交 → 带状态条件的原子 `UPDATE` + `rowcount`（乐观锁）；
- 超时回收 → `SELECT … FOR UPDATE` + 锁内复核（悲观锁）；
- 一坐席一活跃预占 → 部分唯一索引（数据库最终防线）。

> **大白话**：整条系统的安全底线就一句——**别指望代码小心翼翼**。四类危险动作分别交给数据库四招：冲突就跳过、按着状态改、先锁住再看、唯一索引兜底。

### 1.3 Who —— 谁在用它，各自能做什么

系统按角色划分权限，权限由**后端统一控制**（前端只做显隐）：

| 角色 | 典型使用者 | 可用能力 |
| --- | --- | --- |
| **超级管理员** | 系统负责人 | 全部权限（`require_permission` 里短路放行），用户/角色/权限管理 |
| **运营人员** | 外呼运营 | 名单导入、任务管理、号码与技能队列、场景与类型、派单、报表监控 |
| **坐席** | 电话客服 | 改坐席状态（示闲/暂停）、查看自己的待呼名单、接单、发起呼叫、查看通话历史 |
| **质检管理员** | 质检组长 | 建质检任务、维护专家组、批量派发、查看完成率报表、维护案例库 |
| **质检专家** | 质检员 | 领取质检明细、提交评分结果 |
| **总监 / 查看者** | 管理者 | 只读报表与监控 |
| **系统自身** | 后台服务 | 5 个定时任务（超时回收/重试派发/预占释放/回呼派单/质检回收） |

> 权限模型：**5 张 RBAC 基线表**（`users`、`roles`、`user_roles`、`permissions`、`role_permissions`）。**63 个权限码的唯一来源**是 `core/permissions.py`，由 `scripts/init_db.py` **幂等**同步入库并授予内置 admin 角色。前端路由 `meta.permission`（共 18 条）与 `v-permission` 指令用同一批码——**一处定义、后端校验、前端菜单/按钮三处生效**；但真正鉴权始终在后端。

> **大白话**：用这套系统的一共 7 种人，能干什么**由后端说了算**（前端只负责把没权限的菜单藏起来，藏不住也没用）。63 个权限码只写在**一个文件**里，数据库和前端菜单都从这一处对齐——避免「三处各写一份、改一处漏两处」。

### 1.4 How —— 系统怎么实现和运行

#### 1.4.1 总体架构（四层）

```
┌──────────────────────────────────────────────────────────────────┐
│  接入层   FastAPI(REST) + Vue3 SPA(外呼 12 页 / 质检 6 页 / 登录)   │
├──────────────────────────────────────────────────────────────────┤
│  应用层   Router（只做 HTTP 层）→ Service（业务规则 + 事务归属）     │
│           ├─ 外呼：TaskService / ExecutionService / AssignmentService│
│           │        TimeoutService / CallbackService / ReportService │
│           └─ 质检：ConversationService / TranscribeService           │
│                    TaskService / ReviewService / QcReportService     │
├──────────────────────────────────────────────────────────────────┤
│  能力层   Provider(工厂+抽象)：Call / Phone / Ivr / Asr / Tts        │
│           StateMachine(5 个) · RetryPolicy · NumberSelector          │
│           ImportParser · IvrStrategy · Grading · AsyncBridge         │
├──────────────────────────────────────────────────────────────────┤
│  存储层   Repository（只写 SQLAlchemy 查询）→ PostgreSQL 16 + Redis  │
└──────────────────────────────────────────────────────────────────┘
```

> **大白话**：四层就像一家公司——门口（接入层）接客、业务员（应用层）谈事、专业工具（能力层，打电话/转写引擎这类）干活、账房（存储层）记账。分层最大的好处是「**换工具不用换业务员**」：把打电话的引擎从测试版换成真实版，业务代码一行都不用改。

#### 1.4.2 两条主数据流

**（A）外呼执行流程（在线，从名单到通话）** —— 模块级实现细节见 [第 2 章 · 模块一](#模块一--智能外呼执行链路)。

1. **导入名单**：Excel/CSV → 表头别名归一化 → 逐行验号码 → 按 `(user_id, order_id)` 去重 → 失败行单独记录；批次落 `SUCCESS / PARTIAL_FAILED / FAILED`。
2. **建任务**：选场景/类型/技能队列、配号码来源顺序、重试策略、`call_timeout_seconds`；`DRAFT → READY → RUNNING`。
3. **选号码**：从号码池挑主叫号码，**带条件的原子 UPDATE 扣次数**（不用「先读后写」）。
4. **派单 / 呼叫**：坐席示闲 → 系统预占一单 → 多被叫号码逐个尝试 → 调 Provider 呼叫 → 写 `call_histories`。
5. **结果回写**：网关回调（HMAC 签名 + 时间戳容差防重放）→ 幂等更新记录/会话。
6. **兜底**：失败走重试阶梯；超时回收；预占超时释放。

**（B）质检流程（准实时，从对话到报表）** —— 详见 [第 2 章 · 模块三](#模块三--对话质检qc)。

1. **对话入库**：手工录入或批量导入聊天记录；语音对话在 `qc_conversations` 只存 `recording_path`（**不存二进制**）。
2. **ASR 转写**：`POST .../transcribe` → Provider 转成 `AsrSegment` 列表（role + text + start_ms/end_ms）→ **先清旧 ASR 消息再写入新的**（幂等）→ 置 `SUCCESS`。
3. **建质检任务 + 专家组**：配置专家组成员与配额，`DRAFT → DISPATCHED`。
4. **批量派发**：一条 `INSERT … SELECT` + `row_number()` 取模均分（ROUND_ROBIN / AVERAGE）+ `ON CONFLICT DO NOTHING`，分批提交。
5. **领取 / 提交**：专家 `claim`（乐观锁）→ 打分（`grade` 落在窄表 `qc_task_items`）→ `submit`（四步一起提交）。
6. **报表与案例库**：完成率、每日完成量（**先换时区再切天 + 服务层补零**）；优秀对话沉淀为案例。

**（C）兜底流程（5 个定时任务）**：超时回收 / 重试派发 / 预占释放 / 回呼派单 / 质检回收——统一「宽松扫描 → 加锁复核 → 动作提交」幂等范式。

> **大白话**：系统就两条主要流水线。一条是「名单 → 电话」：每打一通都记档，打不通自动排队重试，太久没结果由值班任务收回。另一条是「对话 → 分数」：录音先转成「谁说的、第几秒」，再分给专家打分。第三条不算流水线，是「五个夜班值班员」，专门收拾各种卡住不动的单子。

#### 1.4.3 状态机（5 个）

| 对象 | 状态数 | 状态 |
| --- | --- | --- |
| 外呼任务 | 6 | `DRAFT / READY / RUNNING / PAUSED / COMPLETED / CANCELLED` |
| 坐席 | 5 | `OFFLINE / IDLE / RESERVED / BUSY / PAUSED` |
| 回呼任务 | 6 | `PENDING / ASSIGNED / CALLING / SUCCESS / FAILED / CANCELLED` |
| 质检任务 | 5 | `DRAFT / DISPATCHED / REVIEWING / COMPLETED / CANCELLED` |
| 质检明细 | 4 | `PENDING / REVIEWING / COMPLETED / TIMEOUT` |

统一模式：`XXX_TRANSITIONS: dict[状态, frozenset[状态]]` + `can_transition` / `ensure_transition`（非法抛 `StateNotAllowed` → 40902）/ `allowed_targets` + 集合守卫（`EDITABLE_STATUSES` / `DELETABLE_STATUSES` / `FINISHED_STATUSES` / `TERMINAL_STATUSES`…）。

> **诚实边界**：状态机单测是「合法边逐条列举 + 非法边逐条列举 + 守卫按状态全遍历 + 覆盖性断言」，**不是 6×6 笛卡尔积穷举**——外呼 6 态理论 30 条非同态边，用例列了 21 条，是覆盖性的、不是数学完备的。

> **大白话**：五个业务对象各有一张「通关表」，写明「现在在第几关、下一步只能去哪几关」，不在表里的跳法一律报错——这样状态就不会稀里糊涂地在代码各处被改乱。要说明的是：单测是把「合法路 + 不能走的路」一条条点名验证，**不是把所有组合（6×6=36 种）全跑一遍**。

#### 1.4.4 存储结构

| 存储 | 作用 | 关键内容 |
| --- | --- | --- |
| **PostgreSQL 16** | 事实源 | 38 张表：RBAC 5 + 审计 2 + 租户 3 + 外呼配置 5 + 任务名单 4 + 执行会话 5 + IVR 3 + 回呼 2 + 质检 9 |
| **Redis 7** | 登出黑名单 | 按 `jti` 写入，TTL 取 refresh 的 7 天（天然自清理）；**不可用时降级放行** |
| **本地文件存储** | `storage/` | 名单导入原始文件、通话录音——**数据库只存路径不存二进制** |

**三个数据层设计点**：① **软删除 + 部分唯一索引**（全库 **24 个**部分唯一索引，`WHERE is_deleted = false`，删除后名字可复用）；② **枚举一律 `VARCHAR(32)`**（`enum_type()`，`native_enum=False`，避免原生 ENUM 增删值要跑迁移）；③ **时间统一 `timestamptz`（UTC）**，只在报表层按 `QC_REPORT_TIMEZONE`（默认 Asia/Shanghai）换算分桶。

> **大白话**：数据存三处——① 数据库是「正本」，38 张表；② Redis 只干一件事：记住「谁已经登出了」，而且定位是「记不住也不耽误用」；③ 录音和导入的原文件放磁盘，数据库里只写「文件在哪」，**绝不把几个 G 的音频塞进数据库**。

#### 1.4.5 前端页面与主要接口

**页面路由（21 个页面）**：`/login` · `/dashboard` 首页 · `/404`；外呼 12 页：任务、名单、号码、场景、类型、坐席与分配、会话/工作台、记录、IVR、回呼、报表、实时监控；质检 6 页：对话管理、质检任务、专家组、**质检工作台**、质检报表、案例库。

**核心接口**（服务默认按 `.env` 配置，前缀 `/api/v1`）：

| 类别 | 代表接口 | 权限码 |
| --- | --- | --- |
| 认证 | `POST /auth/login`、`POST /auth/refresh`、`POST /auth/logout`、`GET /auth/me` | 部分免登录 |
| 外呼任务 | `/outbound/tasks/*` | `outbound:task:*` |
| 名单导入 | `/outbound/lists/import`、`/outbound/import-batches/*` | `outbound:list:*` |
| 号码与技能队列 | `/outbound/numbers/*` | `outbound:number:*` |
| 坐席与派单 | `PUT /outbound/agents/{id}/status`、`/outbound/assignments/*` | `outbound:agent:*` / `outbound:assignment:*` |
| 会话与呼叫 | `GET /outbound/agents/{id}/worklist`、`POST /outbound/records/{id}/call` | `outbound:session:*` |
| 网关回调 | `POST /outbound/callbacks/*`（**HMAC 签名，不走 JWT**） | 签名校验 |
| 报表监控 | `/outbound/reports/*` | `outbound:report:*` |
| 质检对话 | `/qc/conversations/*`、`POST /qc/conversations/{id}/transcribe` | `qc:conversation:*` |
| 质检任务 | `/qc/tasks/*`（含批量派发） | `qc:task:*` |
| 质检作业 | `/qc/review/*`（领取/提交）、`/qc/reviewers/*` | `qc:review:*` |
| 质检报表 / 案例 | `/qc/reports/*`、`/qc/cases/*` | `qc:report:*` / `qc:case:*` |

> **大白话**：前端一共 21 个页面（登录、首页、外呼 12 个、质检 6 个）。接口按业务分块，每块配一个权限码——**你能看到哪些菜单，取决于你手里有哪几个码**。

#### 1.4.6 权限与安全设计

- **密码存储**：bcrypt（成本因子 12；测试环境下调到 4 加速用例）。
- **令牌**：PyJWT(HS256)，access 30 分钟 + refresh 7 天，载荷五件套 `sub / type / jti / iat / exp`；`decode_token` 用 `expected_type` 防**令牌混淆**（refresh 不能当 access 用）。
- **登出**：`jti` 进 Redis 黑名单；Redis 挂了**降级放行**（可用性优先）。
- **回调**：不用 JWT（真实网关没有登录态），用 **HMAC-SHA256 签名 + 时间戳容差 300s 防重放**，`hmac.compare_digest` 常数时间比对。
- **统一响应**：所有出口 `{code, message, data}`，业务码与 HTTP 状态码解耦。
- **审计**：`login_logs`（登录成功/失败，**失败日志单独 commit**）+ `operation_logs`（中间件异步写非 GET 请求）。
- **超管保护**：`require_permission` 短路放行，但**超管操作同样被审计记录**；`require_superuser` 已定义但当前无路由使用。

> **大白话**：安全上有三个「想清楚了」的地方——① 密码加盐哈希，不存明文；② 登录发两张票（短票 30 分钟、长票 7 天），并明确「长票不能当短票用」；③ 网关回调这条外部通道没有登录态，改用「带密钥的签名 + 邮戳时间」防伪造和重放。另外，管理员也不是「没人管」——他做了什么照样记账。

#### 1.4.7 如何运行

```bash
docker compose up -d                              # 起 PostgreSQL 16 + Redis 7
cd backend
python -m scripts.init_db                         # 建表 + 迁移 + 初始化权限码/超管
uvicorn app.main:app --reload                     # 启动后端
cd ../frontend && npm install && npm run dev      # 启动前端
# admin / Admin@123456（首次执行 init_db 创建）
```

> **诚实边界**：`docker-compose.yml` 里**只有数据库和 Redis，没有后端自己的 Dockerfile**（后端与前端目前都在宿主机直接跑）。

> **大白话**：起项目就四步——起数据库和 Redis → 建表初始化 → 起后端 → 起前端。要注意的是：容器里**只装了数据库和 Redis**，后端和前端还是直接跑在电脑上，所以仓库里没有应用本身的 Docker 镜像。

### 1.5 How much —— 投入、规模与效果

#### 1.5.1 关键规模与参数（全部来自 `core/config.py`，可核对）

| 维度 | 取值 |

> **大白话**：这些数字决定了系统的手感——一页最多 200 条、登录票 30 分钟、一次派发 2000 条一批、专家领了单 30 分钟不交就收回、名单文件上限 10MB、对话一次最多 10 万条。本质上都是「**防止一次操作把系统拖垮**」的保险丝。

#### 1.5.2 成本构成

- **一次性开发成本**：外呼执行链路 + 坐席调度 + 质检全链路 + 平台底座 + 前端 21 页。
- **运行成本**：主要是 **ASR 转写费**（按音频时长计费）与 **数据库算力**（10 万级派发、批量聚合）。
- **降本手段**：批量派发**一条 SQL 完成**（避免逐行 10 万次网络往返）；转写结果落库缓存（重转前先删旧，不重复累积）；报表聚合**落在窄表** `qc_task_items.grade`（避免扫 Text/JSONB 大列）。

> **大白话**：成本主要两块——转录音频（按分钟花钱）和数据库干活（一次派 10 万条、报表天天算）。省钱靠两个思路：**能一次批处理的就别一条条发**；**报表只数「短表」，别去翻长文本**。

#### 1.5.3 质量与性能指标

- **并发正确性**：号码扣减有**真并发用例**（8 线程 × 24 次扣减，`USAGE_LIMIT=5`，断言**恰好成功 5 次**）；批量派发幂等（重复派发不产生重复明细）；一坐席一活跃预占（部分唯一索引兜底）。
- **可用性**：Redis 挂了登出降级放行；ASR 失败置 `FAILED` 并抛业务错误，不影响其它对话；操作日志写失败只记异常、不阻断业务。
- **工程化**：`ruff` 作为提交前门槛；pytest 用**真实 PostgreSQL**（禁用 SQLite）；`test_openapi_docs.py` 守文档规范（每个 operation 必须有 summary/description/security/examples）。

> **大白话**：能证明「确实没出并发问题」的证据有三个——号码扣减那儿真有 8 个线程同时抢、断言「正好成功 5 次」；派发重复执行不会多出数据；一个坐席抢不出第二条活单（数据库拦住）。另外，Redis 挂了系统还能用，日志写失败也不影响用户办事。

#### 1.5.4 已知取舍与改进方向（详情见第 5 章附录 B）

1. **定时任务是单机 APScheduler** → 多实例部署需分布式锁或独立 worker（§76 MVP 明确不做分布式调度，靠幂等兜底）。
2. **ASR / IVR / TTS / Phone 的阿里云与三方实现为模拟** → 真实接入替换 HTTP 调用即可（契约不变）。
3. **脱敏函数 `mask_phone` / `mask_id_card` 写了但未接入链路** → 需显式调用或加日志 Filter 兜底。
4. **行级租户隔离无全局强制** → 靠每个路由声明 `Depends(tenant_scope_*)`，建议加规范测试扫描守门。
5. **转写没有独立 `TRANSITIONS` 状态机** → 与其它 5 个状态机做法不一致。
6. **"重转清旧消息"缺专门幂等用例** → 应补「同一对话转两次，消息数不翻倍」断言。
7. **前端未接 refresh token 静默续期** → access 到期即跳登录。
8. **无应用 Dockerfile**；**首页模块进度表为静态硬编码**。
9. **`max_concurrency` 未在执行层强制**（用 `EXECUTE_BATCH_SIZE` 控制）。
10. **预测外呼只输出建议，无自动拨号闭环**。

> **大白话**：这 10 条就是「我知道、但暂时没做」的清单——值班员只有一个（多台机器会重复巡场）、阿里云那些引擎还是彩排、脱敏买了没装到门上、租户隔离靠每个接口自觉挂门禁、转写没有自己的状态机……**面试主动交代，比被追问出来强**。

### 1.6 通俗理解（大白话全景）

#### 1.6.1 一句话：这系统到底干嘛的

一家公司要给客户打几千个电话（催单、回访、通知），再顺便检查一下客服的服务质量。**这套系统就是「自动电话调度中心 + 考官阅卷室」**：前半段帮你把电话有条不紊地打出去、打不通自动重排、坐席闲着就立刻塞一单；后半段把客服跟客户的对话（或录音转成的文字）拿来给质检专家打分，最后出一张「这周质检完成率多少」的报表。

关键点就一句：**同一件事不能被两个坐席同时干，同一个号码的次数不能被扣超——这两件事不是靠「小心翼翼」保证的，是靠数据库一条语句原子地锁死。**

#### 1.6.2 一个类比：把它想成一个「夜班值班的呼叫中心」

- **名单怎么进来**：Excel 传上来，系统一行行安检（号码合不合法、有没有重复），不合格的记进「失败名单」。
- **谁去打电话**：坐席们。**坐席一「示闲」，系统立刻从最急的任务里抽一条最该打的客户，塞到他手里（预占）**；他一接单就开始拨，拨完立刻被塞下一条。
- **号码次数怎么算**：主叫号码像「餐券」，扣一张少一张——**扣券和检查「还有没有券」必须在同一步做完**，不然两个坐席会同时把最后一张券用掉。
- **打不通怎么办**：给三次机会，到点自动再打；打出去太久没结果，值班员（定时任务）把它收回来标记超时、还能重试就重排。
- **录音怎么变成能质检的文字**：录音是一整段音频，**光有文字没法判断「谁在骂人」**——所以要转成「**这句话是坐席说的、第 12 秒说的**」这种分段格式（说话人 + 文本 + 时间戳）。
- **阅卷怎么分**：10 万条明细不能一条条派，得**让数据库一条语句按序号取模均分给 10 个专家**，重复派也不会派两遍。

#### 1.6.3 四大模块，用大白话说

> 完整技术版模块说明见 [第 2 章](#第-2-章-四大模块在项目中是什么)；此处只给最直白的理解。

**模块一：智能外呼执行链路（把电话打出去）**

1. **收名单**：Excel/CSV 传上来 → 表头认别名（`姓名`/`用户姓名` 都认）→ 逐行验号码 → 重复的按「用户+订单」去重 → 不合格的单独记下来。
2. **建任务**：选场景、类型、技能队列，配「先打订单号还是先打用户号」的号码顺序、配重试次数和呼叫超时。
3. **挑号码**：从号码池拿主叫号码，**原子扣次**——「还有次数吗」和「扣掉一次」是一个动作，只让一个人成功。
4. **派单**：坐席示闲 → 系统按「技能队列匹配 → 任务优先级 → 名单优先级」挑一条 → 建 60 秒预占 → 坐席收到。
5. **呼叫**：被叫号码逐个试，每个号码选个主叫号拨出去；接通就记成功，全失败就走重试。
6. **收尾**：打完释放坐席 → **立刻派下一单**；网关回调写回结果（用签名防伪造）。

**模块二：坐席分配与并发控制（保证不抢不乱）**

1. **一条链说清楚**：`IDLE → 挑任务 → 建预占(60秒) → 记录 ASSIGNED → 建会话 → 坐席 RESERVED → 接单/直接打 → 打完释放 → 立刻派下一单`。
2. **三把锁防乱**：状态机告诉你能不能这么转（非法直接报错）；数据库不让同一坐席有两条活预占（部分唯一索引）；值班任务收拾漏网的超时单。
3. **三条并发路径**：10 万条派发用「一条 SQL 取模均分 + 冲突就跳过」；领取/提交用「带状态条件的原子 UPDATE + 看改了几行」；超时回收用「行锁 + 锁内再看一眼」。
4. **踩过的坑**：psycopg3 下 `INSERT … SELECT` 的 `rowcount` 返回 **-1**（不是真实行数），所以计数必须改用 `RETURNING`——否则会出现「派发只写了 3 行就停」「首次提交被误判成已提交」。

**模块三：对话质检（QC）**

1. **对话进来**：手工录或批量导；语音对话在库里**只存录音文件路径，不存音频本身**。
2. **转写**：调 ASR 引擎把录音转成「说话人 + 内容 + 起止毫秒」的消息列表；**先按来源删掉旧的 ASR 消息再写新的**，所以同一段录音转两次，消息数不会翻倍。
3. **派发**：建质检任务 → 建专家组（每人配额）→ 一条 SQL 按取模均分派 10 万条明细，冲突就跳过。
4. **领取与打分**：专家领一条（原子 UPDATE 抢，只有一人成功）→ 打分（分值落在窄表，报表聚合只扫短列）→ 提交（写结果、改状态、任务完成数 +1、条件完成，四步一起提交）。
5. **兜底与沉淀**：专家领了 30 分钟不交，值班任务把它放回待领；优秀对话沉淀进案例库。
6. **报表**：完成率、每日完成量——**先把 UTC 时间换成上海时间、再按天切桶**（顺序反了跨零点就错位），没有数据的那天补 0。

**模块四：服务与部署（怎么对外提供服务、怎么搭起来）**

1. **三层分工像餐厅**：前台（Router）只接单、后厨（Service）做菜并决定什么时候「结账」（提交事务）、仓库（Repository）只取货（写 SQL）。
2. **四道关**：验票（token 有效没登出）→ 认人（账号存在且启用）→ 看门禁（权限码，超管放行）→ 划范围（只能看自己租户的数据）。
3. **统一应答**：不管哪个角落出错，出口都用同一句话术 `{code, message, data}`；HTTP 状态码给网关和监控看，业务码给前端做语义判断。
4. **前端**：Vue3 单页站，**菜单和路由都由权限码长出来**，所以不会出现「菜单看得见、点进去进不了」。
5. **一键搭建**：Docker Compose 起 PostgreSQL + Redis（**只有数据层**，后端前端在宿主机跑）。
6. **能测**：pytest + 真实 PostgreSQL（**不用 SQLite 顶替**，因为要验的正是 PG 的行锁和部分唯一索引）。

#### 1.6.4 两条数据旅程（串起来看）

**外呼旅程**：

```
Excel 名单
   → 表头归一化、验号码、去重（失败单独记）
   → 建任务（场景/类型/队列/重试策略/超时）
   → 坐席示闲 → 挑任务 → 60 秒预占 → 记录 ASSIGNED → 建会话
   → 坐席接单 → 多被叫号码逐个试 → 选主叫号原子扣次
   → 调网关呼叫（Provider 抽象）→ 写 call_histories
   → 网关回调（HMAC 签名）写回结果
   → 失败的按阶梯重试 / 超时的被回收 / 打完释放坐席 → 立刻派下一单
```

**质检旅程**：

```
聊天记录 / 通话录音（库里只存路径）
   → ASR 转写：说话人 + 文本 + 时间戳（清旧写新，幂等）
   → 建质检任务 + 专家组（配额）
   → 一条 SQL 取模均分派 10 万条明细（冲突跳过）
   → 专家原子领取（只有一人成功）→ 打分 → 提交（四步一体）
   → 领了 30 分钟不交 → 值班任务放回待领
   → 优秀对话进案例库
   → 报表：先换时区再切天 + 补零 → 完成率 / 每日完成量
```

### 模块一 · 智能外呼执行链路

#### 它是什么

一条把「客户名单」变成「一通通电话记录」的在线流水线：

```
导入名单 → 建任务 → 坐席派单/自动执行 → 选主叫号码(原子扣次) → 呼叫 → 写通话历史
                                                          → 网关回调写回结果
                                                          → 失败重试 / 超时回收
```

- **名单导入**（`services/outbound/import_parser.py`）：文件校验（≤10MB、仅 `xlsx`/`csv`）→ **表头别名归一化**（去空白/下划线/横线/括号转小写）→ 逐行 `is_valid_phone` 校验 → 按 `(user_id, order_id)` 去重 → `bulk_insert` → 批次落 `SUCCESS / PARTIAL_FAILED / FAILED`；失败明细按 `MAX_IMPORT_FAILURE_DETAIL=500` 截断（**计数仍真实**），可导出 CSV（带 BOM）。
- **任务生命周期**（`task_state.py`）：6 态状态机；进 `READY` 前必须至少 1 个启用号码；进 `RUNNING` 写 `started_at`，进终态写 `finished_at`；`maybe_complete_task` 在「运行中 + 有记录 + 无未终态记录」时置 `COMPLETED`。
- **号码管理**（`number_service.py` / `number_selector.py`）：主叫号码带 `usage_limit` / `used_count`，扣减是**带条件的原子 UPDATE**（`WHERE status='ENABLED' AND (usage_limit IS NULL OR used_count + step <= usage_limit)`），返回 `rowcount`（§13 禁止读改写）。四种选取策略。
- **执行引擎**（`execution_service.py`）：**每条记录一个事务**；一条记录内「遍历所有被叫号码 → 每个号码选主叫并原子扣次 → 建 `call_histories` → 调 Provider → 回写」。全失败才走重试阶梯。
- **结果回写**（`api/v1/outbound/callbacks.py`）：**不用 JWT**，用共享密钥 HMAC-SHA256（`X-Callback-Timestamp` + `X-Callback-Signature`，容差 300 秒防重放）；回调幂等——已有终态直接忽略。
- **重试与回收**（`retry_policy.py` / `timeout_service.py`）：三档阶梯（不可重试→`FAILED`；还能重试→`RETRY_WAITING` + `next_retry_at`；次数用完→`EXHAUSTED`）；超时回收用 `SELECT … FOR UPDATE` + 锁内复核。

> **大白话**：这条流水线就是把「一列名字」变成「一通通有记录的电话」：名单进来先过安检（号码合不合法、有没有重复），任务配好「打哪个号、打几次、多久算失败」；真要拨号时，号码次数的扣减是「**原子**」的；结果由网关回信；打不通就排队重试，太久没结果被值班任务收回。

#### 关键实现点

| 关注点 | 做法 |
| --- | --- |
| 幂等导入 | 接口按 URL / `(user_id, order_id)` 查重，已存在返回 `skipped`；批次可重跑 |
| 号码扣减 | 条件原子 `UPDATE` + `rowcount == 1`（真并发用例钉死：8 线程 × 24 次、断言恰好成功 5 次） |
| 回调防伪 | HMAC-SHA256 签名 + 时间戳容差；`hmac.compare_digest` 常数时间比对 |
| 回调幂等 | 已有终态直接忽略；`provider_call_id` 索引用于匹配 |
| 重试阶梯 | `apply_failure_ladder` 执行 / 回调 / 回收**三处共用一套**，避免逻辑漂移 |
| 超时回收 | `FOR UPDATE` + 锁内复核（「先读后判」型复合操作用悲观锁），**每条独立 commit** |

> **大白话**：这张表的中心思想只有一句：**凡是可能重复、可能并发的地方，都交给数据库一条语句解决**——导入靠查重跳过、扣次数靠带条件的 UPDATE、回调靠签名 + 「已是终态就忽略」、超时靠行锁内再复核一次。

#### 面试可能追问的「诚实边界」

> ① **`max_concurrency` 未在执行层强制**——实际并发由 `EXECUTE_BATCH_SIZE=20` 控制，任务配置的 `max_concurrency` 目前不参与限流。
> ② **预测外呼只输出建议**（`prediction_service.py`），**没有自动拨号的闭环**。
> ③ **会话状态有定义了但没写入点的枚举**（`CONNECTED` / `RELEASED`），实际只走 `CREATED/ASSIGNED → CALLING → ENDED|TIMEOUT`。
> ④ 名单批次枚举里 `IMPORTING` 之外的三个中间态，实际只落 `SUCCESS / PARTIAL_FAILED / FAILED`。

### 模块二 · 坐席分配与并发控制

#### 它是什么

坐席不是「去抢单」，而是**示闲那一刻被系统预占一单**：

```
坐席示闲(IDLE)
  → 门禁①坐席存在 ②状态==IDLE ③无活跃预占
  → 挑任务：技能队列匹配 → 任务优先级 ASC → 名单优先级 DESC
  → 建预占(RESERVED, expires_at = now + 60s)
  → 派单：record=ASSIGNED + 复用/新建会话 + 坐席=RESERVED
  → 坐席接单(RESERVED→ACCEPTED) 或 直接呼叫(隐式接单)
  → 多号码逐个拨
  → release_for_record：释放预占 + 坐席回 IDLE → 立刻 assign_for_agent 派下一单
```

- **两条并发路径 + 一条**：
  - **批量派发（10 万条）**：单条 `INSERT … SELECT` + `row_number() OVER (ORDER BY id)` 取模均分（`ROUND_ROBIN` 用 `(rn-1) % n`；`AVERAGE` 用 `chunk=ceil(total/n)` + `least(floor((rn-1)/chunk), n-1)`，**必须 floor**）+ `NOT EXISTS` 排除 + `ON CONFLICT (task_id, conversation_id) WHERE is_deleted=false DO NOTHING` + `RETURNING id` 计数 + 分批 `while inserted > 0`。
  - **领取 / 提交（乐观锁）**：带状态条件的原子 `UPDATE`（`WHERE status='PENDING'`；提交/释放 `WHERE status='REVIEWING' AND reviewer_id=me`）+ `rowcount == 1` 判定。
  - **超时回收 / 预占释放（悲观锁）**：`SELECT … FOR UPDATE` + 锁内复核。
- **一面数据库「铁门」**：活跃预占的部分唯一索引 `uq_agent_assignments_active_agent`（`WHERE is_deleted = false AND status IN ('RESERVED','ACCEPTED')`）——**同一坐席插不进第二条活预占**。

> **大白话**：坐席不是自己去抢单，而是「**一站到窗口，系统就往他手里塞一单**」——先查三样（人在不在、是不是空闲、手里有没有活），再从「最该打的活」里挑一条，给他 60 秒，不接就收回来给别人。打完立刻再塞下一单，所以他永远不空转。

#### 关键实现点

| 能力 | 实现 | 说明 |
| --- | --- | --- |
| 一坐席一预占 | 应用层查 + **部分唯一索引兜底** | 数据库是最终防线 |
| 挑单排序 | `list_assignable` + `pick_pending_for_task` | 技能队列 → 任务优先级 ASC → 名单优先级 DESC |
| 派单事务 | 一次提交写四张表 | 预占 + 记录 + 会话 + 坐席状态（含状态流水） |
| 打完回环 | `release_for_record` → `assign_for_agent` | docstring 明确「只预占不呼叫，无递归风险」 |
| 内部 vs 用户流转 | 内部 `can_transition`+告警 / 用户 `ensure_transition`+40902 | **刻意的不对称** |

> **大白话**：这条链上有三道保险——程序自己先查一遍、数据库唯一索引当「铁门」（同一坐席插不进第二条活单）、夜班值班员收拾超时漏网的。另外有个刻意设计：**用户自己点错了要立刻报错**，系统自己批量干活时遇到小问题只记警告、继续干完剩下的，不至于一条小异常把整批派单全废掉。

#### 面试可能追问的「诚实边界」

> ① **并发同抢抛的是数据库完整性错误**（`IntegrityError` → 落到 500 + `50000`），**没有单独包装成业务码 409xx**——「一坐席一活跃预占」实际是数据库拦住的，但报错语义不友好。
> ② **内部派单状态非法只记 warning 不报错**，会出现「状态没切成功但预占/记录/会话照写」。
> ③ **没有「拒单」语义**——只有 `accept` 和 `release`。
> ④ **重试电话不派给坐席**：`pick_pending_for_task` 只取 `PENDING`，`RETRY_WAITING` 到期由 `retry_dispatch` 定时任务直接执行，**不占预占**。
> ⑤ **`MANUAL` 模式任务不参与自动派单**（`list_assignable` 只取 `AUTO`/`PREDICTIVE`）。
> ⑥ **预占阶段不锁主叫号码**——号码到真正呼叫时才原子扣次，可能出现「人齐了、号码不够」。
> ⑦ **预占超时靠定时任务，最长延迟约 30 秒**（60 秒预占实际释放时刻可能到 60～90 秒）。

### 模块三 · 对话质检（QC）

#### 它是什么

一条把「客服对话」变成「评分与报表」的链路：

```
对话入库(手工/批量导入)
  → (语音) ASR 转写：说话人 + 文本 + 时间戳
  → 建质检任务 + 专家组(配额)
  → 批量派发明细(取模均分 + 冲突跳过)
  → 专家领取(乐观锁) → 打分 → 提交(四步一体)
  → 超时回收兜底 / 优秀对话沉淀案例库
  → 报表：完成率 / 每日完成量(先换时区再切天 + 补零)
```

- **对话与消息模型**（`models/qc/conversation.py`）：`qc_conversations` 存 `recording_path`（**仅路径不存二进制，§66**）、`transcript_status`、`transcript_engine`、`msg_count`；`qc_messages` 存 `seq` / `role` / `content` / `start_ms` / `end_ms` / `source`，索引 `ix_qc_messages_conversation_seq`，**append-only 不做软删除**。
- **ASR 转写**（`providers/asr/` + `services/qc/transcribe_service.py`）：契约 `AsrSegment(role, text, start_ms, end_ms)`；`AsrProvider(ABC)` 的 `transcribe_segments(*, audio_path)` 是抽象方法、`transcribe()` 是模板方法；工厂 `get_asr_provider()` 按 `.env` 的 `ASR_PROVIDER` 选实现；Service 先置 `RUNNING` 并 **commit** 再调 Provider；**`_rewrite_asr_messages` 四步保证重转幂等**（删旧 ASR → `coalesce(max(seq),0)` 取基准 → 批量插入 → `count(*)` 回填 `msg_count`）。
- **批量派发**（`services/qc/task_service.py`）：一条 `INSERT … SELECT` + `row_number()` 取模均分 + `ON CONFLICT DO NOTHING`；分批提交（`QC_DISPATCH_BATCH_SIZE=2000`）；`total_items` 用 `count(*)` 回填。
- **领取 / 提交**（`services/qc/review_service.py`）：`claim` 原子 UPDATE；提交顺序 = `insert_result`（`ON CONFLICT (item_id)` 防重复提交）→ `submit_item`（改状态）→ `increment_completed`（原子自增）→ `complete_if_done`（条件 UPDATE）。**`grade` 落在窄表 `qc_task_items`**，报表聚合只扫短列。
- **兜底**（`recycle_timeout_items`）：`list_timeout_items` → `repo.recycle`（行锁 + 锁内复核 → `PENDING`，清 `locked_at`/`timeout_at`，**保留 `reviewer_id`**）。
- **报表**（`services/qc/report_service.py`）：SQL 里**先** `func.timezone(QC_REPORT_TIMEZONE, reviewed_at)` **再** `func.date_trunc("day", …)`；半开区间 `[start, end)`；**补零在服务层 Python `while cursor <= date_to`**。

> **大白话**：质检这条链是——对话进来（**录音只存文件路径，不存音频本身**）→ 转成「谁说的、第几秒」→ 建任务和专家组 → 一条 SQL 把 10 万条均分给专家 → 专家领一条、打分、交一条 → 领了 30 分钟不交就自动收回 → 优秀对话进案例库 → 出完成率报表。

#### 关键实现点

| 关注点 | 做法 |
| --- | --- |
| 落盘策略 | 只存 `recording_path`，**不存音频二进制**（§66） |
| 重转幂等 | 先按 `source=ASR` 删旧消息，再按 `seq = max+1` 往后接（不与 TEXT 撞号） |
| 派发幂等 | `ON CONFLICT` 冲突条件的 WHERE **必须与索引字面一致**（差一字符即失效） |
| 提交原子性 | 四步一起提交（结果 + 明细状态 + 完成数 + 条件完成） |
| 窄表聚合 | `grade` 落 `qc_task_items`，避免扫 `qc_review_results` 的 Text/JSONB |
| 分桶顺序 | **先换时区再 `date_trunc`**（反了跨零点错位）；补零在服务层 |
| 评级阈值 | 优秀 ≥90、及格 ≥60（`QC_GRADE_EXCELLENT_MIN` / `QC_GRADE_PASS_MIN`） |

> **大白话**：四个关键点——录音只存地址；重转是「先删旧的再写新的」（所以转两次不会翻倍）；派发那句「冲突就跳过」**必须和数据库索引写的字面一模一样**，差一个字符保险就失效；报表统计只扫那张很窄的分数表。

#### 面试可能追问的「诚实边界」

> ① **`AliyunAsrProvider` 是模拟实现**：`name="aliyun"`、调用形态照阿里云「录音文件识别」写（提交任务 → 轮询结果），但内部是 `uuid` + `asyncio.sleep`，**不发真实 HTTP**；真实接入只需替换 `_submit_task` / `_poll_result`。
> ② **转写没有独立的 `TRANSITIONS` 状态机**（只有 `TranscriptStatus` 枚举 + Service 直接赋值），与应用其它 5 个状态机做法不一致。
> ③ **「重转清旧消息」代码已实现，但缺专门幂等用例**（现有测试只覆盖「转写成功」与「文本对话被拒」）。
> ④ **转写失败原因未落库**（无 `transcript_failure_reason` 字段）。
> ⑤ **无录音上传入口**（`recording_path` 由调用方传入字符串）。
> ⑥ **`ASR_PROVIDER_URL` 已定义但当前未使用**。
> ⑦ **转写是同步阻塞**的（同步端点 + `run_sync`），无任务队列。

### 模块四 · 服务、权限与报表

#### 它是什么

- **REST 服务（FastAPI）**：封装认证（`/auth/*`）、外呼（`/outbound/*` 103 个端点）、质检（`/qc/*` 37 个端点），共 **144 个端点**。
- **三层架构 + 事务归属**：Router 只做 HTTP 层（函数体通常 1～2 行）、Service 承载业务规则并**决定 commit 时机**、Repository 只写 SQLAlchemy 查询。`get_db()` 正常路径**不 commit**（提交权交给 Service）；`session_scope()` 给定时任务/中间件等非请求场景用。
- **依赖注入链（四段）**：`get_token_payload`（解 JWT + 验 `type` + 查 Redis 黑名单）→ `get_current_user`（查库 + 验 `is_active`）→ `require_permission(*codes)`（超管短路 / 权限码取或）→ `tenant_scope_optional|required`（租户收敛，普通用户传别的租户 → 403）。
- **统一响应与业务码**：`{code, message, data}`；`BizCode` 十个码（`SUCCESS=0` / `PARAM_ERROR=40001` / `UNAUTHORIZED=40101` / `FORBIDDEN=40301` / `NOT_FOUND=40401` / `CONFLICT=40901` / `STATE_NOT_ALLOWED=40902` / `NUMBER_EXHAUSTED=40903` / `RESOURCE_REFERENCED=40904` / **`SYSTEM_ERROR=50000`**）。四个全局异常处理器（`AppException` / `RequestValidationError` / `StarletteHTTPException` / `Exception`）把所有出口收敛成统一体。
- **OpenAPI**：`custom_openapi()` 覆盖 + `apply_examples()` 两层兜底（手写 `REQUEST_EXAMPLES` + `build_example()` 自动生成，递归限深 3）+ `test_openapi_docs.py` 覆盖率守门。
- **前端（Vue3 SPA）**：`constantRoutes`（login/404/CatchAll）+ `asyncRoutes`（首页 + 外呼 12 + 质检 6，**18 条 `meta.permission`**）；`filterRoutesByPermission` 递归过滤后 `addRoute`；Axios 拦截器统一注入 token 与判业务码；5 张 ECharts 图（按需注册，**未注册 GaugeChart**）。
- **定时任务**：5 个 job，参数统一 `max_instances=1, coalesce=True, replace_existing=True`，骨架统一「`with session_scope()` + `try/except logger.exception(...)`」。

> **大白话**：这一块是系统的「物业」——三层分工（前台接单、后厨做菜并决定啥时候结账、仓库取货）、进门四道关（查票 → 认人 → 看门禁 → 划范围）、所有出口统一话术、21 个页面、5 个夜班值班员。总规矩是：**谁能进哪扇门，由后端说了算**。

#### 安全要点

| 项 | 做法 |
| --- | --- |
| 密码 | bcrypt（成本因子 12，测试降到 4） |
| 令牌 | PyJWT(HS256)，access 30 分钟 / refresh 7 天；`expected_type` 防令牌混淆 |
| 登出 | Redis `jti` 黑名单；**Redis 不可用降级放行** |
| 租户 | `tenant_scope_*` 依赖收敛；普通用户跨租户 → 403 |
| 回调 | HMAC 签名 + 时间戳容差 300s；常数时间比对 |
| 审计 | `login_logs`（失败单独 commit）+ `operation_logs`（异步写、失败不阻断） |
| 错误呈现 | 规范业务码 + 中文 message，用户侧不出现 Traceback |

> **大白话**：密码加盐、两种票不能混用、登出记账（Redis 挂了先放行）、跨公司看图数据直接拦掉、外部回调验签名、操作留痕、出错给中文提示不给堆栈——用户永远看不到一堆吓人的红字。

#### 面试可能追问的「诚实边界」

> ① **脱敏未接入**：`mask_phone`（`138****1234`）与 `mask_id_card`（留前 6 后 4）**有实现也有单测，但全仓库没有任何生产调用点**——「能力已备、链路未接」。
> ② **操作日志四字段恒为 NULL**：`target_type` / `target_id` / `request_id` / `detail` 中间件未填充。
> ③ **行级租户隔离不是全局强制的**：靠每个路由声明 `Depends(tenant_scope_*)`，任一环漏掉即静默失效，无规范测试守门。
> ④ **`require_superuser` 已定义但无任何路由使用**（超管放行由 `require_permission` 短路实现）。
> ⑤ **业务码里没有 50001**，系统异常是 `50000`。

> 每项说明：**在项目中做什么** + **为什么选它（对比替代方案）**。原理性说明（RRF 类比、幂等机制等）在第 2 章对应模块展开，本章只作「技术意图」解释。

| 1 | **Python 3.10+** | 承载外呼/质检/API 全链路 | 后端生态完整；`target-version="py310"`，用 `X | None` 新式类型标注 |
| 2 | **FastAPI ≥0.115 + uvicorn[standard]** | 对外 REST 接口、依赖注入、自动生成 OpenAPI | 原生异步 + Pydantic 校验内建 + DI 体系（正适合「认证→权限→租户」收敛成一条链）；比 Flask 更适合异步与文档化 |

## 第 4 章 面试题库（57 题）

> 按 10 大分类组织，编号 Q1–Q57。每题同时给 **`原本答案`**（面试正式说，技术口径）与 **`大白话版`**（先理解、再复述）。答案严格依托本项目实现，**不编造项目里没有的能力**；对直觉与实现有差异处已在答案中标注。

### 一、项目整体与架构（6 题）

#### Q1. 这个项目是做什么的？整体架构说一遍。

- **原本答案**：呼叫中心一体化平台，两大业务域——智能外呼（导入 → 任务 → 选号 → 派单/呼叫 → 回写 → 重试/回收 → 会话 → IVR/回呼 → 报表）与对话质检（对话 → ASR → 派发 → 领取评分 → 案例 → 报表）。后端 FastAPI + Router/Service/Repository 三层 + PostgreSQL 16 + Redis；前端 Vue3 + Element Plus。规模：38 表 / 144 端点 / 63 权限码 / 21 页 / 5 定时任务 / 756 测试。
- **大白话版**：一个「自动打电话 + 检查客服服务质量」的平台。前半段是机器人替你拨号、打不通就排队重试、坐席忙就分配；后半段是把客服和客户的对话/录音拿来给质检专家打分。

#### Q2. 为什么选 PostgreSQL 而不是 MySQL？

- **原本答案**：真用上了只有 PG 才有的能力——**部分唯一索引**（`WHERE is_deleted=false`，软删后名字可复用）、`INSERT…SELECT…ON CONFLICT DO NOTHING`（10 万条派发幂等）、`SELECT…FOR UPDATE`（回收并发安全）、JSONB、timestamptz。换 MySQL 这些全要改写为应用层逻辑，并发正确性下降。
- **大白话版**：项目里最危险的几个并发操作都是靠数据库「一条 SQL 搞定」来保证不出错的，这些写法是 PG 特有的。换数据库等于把保险箱换成普通锁，还得自己盯着。
- **补充**：测试也坚持真实 PG（禁用 SQLite），因为要验的正是这些 PG 特性。

#### Q3. 为什么后端分两个包（outbound / qc）？

- **原本答案**：外呼关注「打出去」、质检关注「说得怎么样」，是**不同的限界上下文**。质检有独立的 `models/qc`、`services/qc`、`repositories/qc`、`schemas/qc`，只在基础设施层（`db`/`core`/`utils`/`providers`）复用，避免把外呼 22 张表的语义搅浑。
- **大白话版**：仓库分货架——外呼的货放外呼货架、质检的货放质检货架。因为「打电话成功」和「对话质量好不好」是两个完全不同的生意逻辑，混着放以后改一个碰一个。

#### Q4. 系统的并发风险点在哪？整体怎么防？

- **原本答案**：三处——① 10 万条批量派发（重复派发）；② 领取/提交（多人抢同一条）；③ 超时回收/预占释放（多实例重复触发）。防线分三层：应用层条件（状态机 + 条件判断）→ 数据库约束（`ON CONFLICT`、`rowcount`、部分唯一索引）→ 定时任务幂等（宽松扫描 + 加锁复核 + 动作提交）。
- **大白话版**：三个容易出事的地方：一次性派 10 万条、多人抢同一条、值班员重复巡场。三层保险：程序自己先判断 → 数据库这道铁门 → 值班员复核后才发现「这单别人做过了」。

#### Q5. 项目的已知边界有哪些？

- **原本答案**：① ASR/IVR/TTS/Phone 的阿里云/三方实现是模拟；② 录音只存路径、无上传与下载端点；③ `max_concurrency` 执行层未强制；④ 预测外呼只输出建议无闭环；⑤ 前端未接 refresh token；⑥ 首页模块进度表静态硬编码；⑦ 无应用 Dockerfile；⑧ 调度单机，多实例靠幂等兜底；⑨ 脱敏未接链路；⑩ 行级租户隔离无全局强制。
- **大白话版**：这题是送分题也是送命题——**主动说清「哪些没做完」，比被追问时支支吾吾强得多**。面试官要的不是完美项目，是你知道自己的边界在哪。

#### Q6. 如果让你改进，你会先做哪三件？

- **原本答案**：① 给 5 个定时任务加分布式锁（Redis 已具备条件）或独立 worker；② 把脱敏从「有函数无调用」接到实际链路（响应体 + 日志 Filter），并给行级租户隔离加规范测试扫描守门；③ 把 ASR 换成真实 HTTP 实现 + 引入异步任务队列，把转写从同步阻塞改为后台任务。
- **大白话版**：第一，值班员现在只有一个，上多台机器就得「登记谁巡场」（分布式锁）；第二，保险柜买了但没锁在门上（脱敏），得真装上去；第三，打电话给阿里云这件事现在还是「彩排」，得换成真的，而且转写太慢会卡住请求，应该改成「先收下、后台慢慢转」。

### 二、后端分层与接口契约（6 题）

#### Q7. 三层架构的边界是怎么在代码里落地的（不靠文档）？

- **原本答案**：靠四个文件的 docstring 钉成可核对事实——`repositories/__init__.py`「只负责 SQLAlchemy 查询，禁止写业务规则/权限/状态机」、`api/deps.py`「【基线冻结】鉴权契约在此定义，禁止修改」、`db/session.py`「事务由 Service 层控制，Router 不碰事务」、各 Service 类「事务在本层提交」。结构性证据：Router 函数体通常 1～2 行。
- **大白话版**：纪律不是写在《开发规范》里让人自觉，而是写在每个「岗位门口」的牌子上——打开文件第一眼就看到谁负责什么、谁不许越界。

#### Q8. 事务归属为什么在 Service 层？`get_db` 和 `session_scope` 区别？

- **原本答案**：`get_db()`（FastAPI 依赖）只 yield，正常路径**不 commit**、异常时 rollback，提交权交给 Service——只有 Service 知道「这次业务到哪算完整」。`session_scope()`（contextmanager）给非请求场景（定时任务/中间件/脚本）用，yield 后自动 commit、异常 rollback。
- **大白话版**：数据库「结账」这件事，前台只负责收银，真正决定「这一单几件事一起算钱」的是后厨。定时任务不在前台体系里，所以单独发一台「自助结账机」。

#### Q9. 统一响应与业务码为什么和 HTTP 状态码分开？

- **原本答案**：**解耦、各司其职**。HTTP 状态码给基础设施（网关/监控/探活）看，业务码给前端业务逻辑看。同一个 HTTP 409 下有四个业务码（40901 冲突 / 40902 状态不允许 / 40903 号码耗尽 / 40904 被引用），前端处理完全不同。成功一律 200，因为 `code=0` 已承载成功语义。
- **大白话版**：HTTP 状态码像「快递物流状态」，业务码像「包裹里到底是什么问题」。同样一个 409，可能是「重名、状态不对、号码用完、被引用了」——物流公司只关心前者，客户只关心后者。

#### Q10. `AppException` 体系怎么设计的？

- **原本答案**：基类 `AppException` 用类属性定义 `code` / `http_status` / `message`；八个子类：`ParamError`(40001/400)、`Unauthorized`(40101/401)、`Forbidden`(40301/403)、`NotFound`(40401/404)、`Conflict`(40901/409)、`StateNotAllowed`(40902/409)、`NumberExhausted`(40903/409)、`ResourceReferenced`(40904/409)。Service 里 `raise StateNotAllowed("对话已被质检引用，禁止删除")`——**完全不用知道 HTTP 码和数字码**。
- **大白话版**：业务代码只说「这件事现在不让做」（语义），不用记「对应 HTTP 409、编号 40902」（传输细节），那是出口安检员的事。
- **补充（诚实边界）**：`message` 可覆盖，所以日志必须同时记 code（`logger.warning("业务异常 %s %s -> %s(%s)", …, code)`），否则同种错误不同文案看着像两种错误。

#### Q11. 全局异常处理器怎么把所有出口收敛？

- **原本答案**：四个 handler：`AppException`（返回 `http_status` + `fail(code, message)`，记 warning）、`RequestValidationError`（改写成 **400 + 40001 + `[{field, msg}]`**，`loc` 用 `.` 拼成 `body.username`）、`StarletteHTTPException`（`_STATUS_TO_CODE` 映射 400/401/403/404/409，**映射不到落 50000**）、`Exception`（500 + 50000 + "系统异常，请稍后重试"，记 exception 栈）。**任何异常出口都被收敛成统一响应体**。
- **大白话版**：整个系统只有一个「总客服」——不管哪个角落出错，到出口前都会被同一个客服接住，用同一句话术回答。前端永远不用处理第二种格式。

#### Q12. 路由聚合为什么有顺序要求？

- **原本答案**：两个真实踩坑：① 带 `{id}` 的动态段会吞掉同层静态路径——质检模块**先挂静态路径**（专家组/任务/报表/案例库）**再挂 `{id}` 域**；② 同一文件内 `/qc/conversations/import`、`/import-batches` 必须声明在 `/{conversation_id}` **之前**，否则 `/import` 会被当成 `conversation_id="import"` 命中详情接口再报 422。
- **大白话版**：路由匹配是「排队按顺序问」——写着「你是谁」的问号路径会先抢答任何经过的人。所以「名字写死的路径」（`/import`）必须排在「问号路径」（`/{id}`）前面。

### 三、认证、权限与多租户（6 题）

#### Q13. 完整描述一次带鉴权的请求。

- **原本答案**：四段链——① `bearer_scheme`（`HTTPBearer(auto_error=False)`）取 `Bearer xxx`；② `get_token_payload` 用 `decode_token(token, expected_type="access")` 解 JWT（验签名/exp/type）并查 Redis 黑名单；③ `get_current_user` 把 `sub` 转 int 后查库，确认存在且 `is_active`；④ `require_permission(*)` 超管短路或权限码取或。FastAPI 保证同一请求内同名依赖只执行一次（缓存复用）。
- **大白话版**：进大楼四道关：门口查你有没有票 → 票是真是假、过没过期、是不是已注销 → 系统里你是不是本人、有没有被停用 → 你要进的这层楼有没有门禁权限。
- **补充**：`auto_error=False` 是刻意的——框架默认缺票返回 403，但项目契约要求所有「未登录」出口统一 401 + 40101。

#### Q14. `require_permission` 为什么做成返回函数的工厂？

- **原本答案**：因为需要**接收参数**（校验哪些权限码）。`Depends` 的机制是「调用传入的可调用对象」，所以先造出一个「知道要校验哪些码」的 checker 闭包再交给 `Depends`。两种消费方式：`dependencies=[Depends(require_permission("qc:task:list"))]`（只校验）或 `current_user: User = Depends(require_permission(...))`（校验 + 拿用户）。
- **大白话版**：普通依赖像「固定守门员」；带权限码的依赖像「按当班名单的守门员」——得先告诉他要查哪个名单（参数），他才能上岗。工厂就是「按名单造守门员」的流水线。

#### Q15. 超管为什么在 `require_permission` 里放行，而不是分配所有权限？

- **原本答案**：① **语义**：超管的「全权限」是身份属性，落成数据会在新增权限码时失同步（新码没分给超管，超管立刻缺权限）；② **性能**：在 `permission_codes()` 之前短路，省掉角色/权限查询。放行点不能在 `get_current_user`——超管一样要过认证（有效 token、账号启用）。
- **大白话版**：超管是「董事长」，不是「所有工牌都发一张的人」。如果靠发工牌，公司新设一个部门忘了给董事长发牌，董事长反而进不去了。
- **补充**：超管操作**同样被审计**记录（放行只在权限校验，不放过中间件）。

#### Q16. 401 和 403 怎么分？

- **原本答案**：401（`40101`）="我不知道你是谁"：缺 token、过期、类型错、已登出、用户不存在。403（`40301`）="我知道你是谁但你不能干"：权限码不足、账号停用、越权访问其它租户。对前端关键：401 触发登出跳登录，403 只提示无权限**不**清 token。
- **大白话版**：401 是「保安不认识你」，403 是「保安认识你、但你的门禁卡刷不了这扇门」。前者要重新登记，后者换个门试试就行。

#### Q17. 多租户隔离怎么落地？有什么边界？

- **原本答案**：领域表都带 `tenant_id`；依赖链第四段 `tenant_scope_optional/required` 收敛入参——超管或未绑定租户的账号不限租户；绑定租户的普通用户传别的租户 → 403；Repository 过滤是 `if tenant_id is not None` 才加条件。**边界（如实）**：隔离无全局强制，任一环漏掉静默失效，没有「所有列表接口必须带租户依赖」的自动化校验。
- **大白话版**：每个数据行都贴着「这家公司的标签」，普通员工只能看自己公司的，硬看别人的被拦（403）。但这是靠每个房间自觉挂标签（依赖），不是大楼统一装的门禁——新房间忘了挂就静默敞开。

#### Q18. 令牌混淆（refresh 当 access 用）怎么防？

- **原本答案**：`decode_token` 的 `expected_type` 参数。refresh 有效期 7 天远长于 access 的 30 分钟，若能拿去调业务接口等于把短命凭据换成长通行证。`get_token_payload` 传 `"access"`，`AuthService.refresh` 传 `"refresh"`。测试 `test_me_with_refresh_token_rejected` / `test_refresh_with_access_token_rejected` 双向钉死。
- **大白话版**：公司发两种卡：临时卡（30 分钟）和长期卡（7 天）。规定临时卡能进工位、长期卡只能去换新卡。不区分的话，拿长期卡就能随便进工位——等于偷偷延长了有效期。

### 四、数据建模与 Alembic（5 题）

#### Q19. 24 个部分唯一索引解决什么问题？有什么坑？

- **原本答案**：解决「软删后名字可复用」。唯一索引带 `WHERE is_deleted = false`，只有未删除行参与唯一约束。坑：① **`ON CONFLICT` 的冲突条件 WHERE 必须与索引字面一致**（差一个字符就失效）；② autogenerate 生成的迁移要检查 `postgresql_where`。
- **大白话版**：删掉的东西还躺在仓库里，但「重名检查」只看还在用的货架。实现上有个坑：告诉数据库「冲突时忽略」的那句话，必须和货架牌子上写的完全一字不差，否则保险就失效。

#### Q20. 枚举为什么用 `VARCHAR(32)` 不用 PG 原生 ENUM？

- **原本答案**：原生 ENUM 增删值要走迁移、跨库不通用；项目枚举迭代频繁。用 `enum_type()`（`native_enum=False`）+ Python 校验：DB 存字符串，Pydantic/SQLAlchemy 层校验合法性。
- **大白话版**：原生枚举像「出厂就焊死的档位」——想加一个档位得拆机器；字符串像「贴纸标签」，随时可贴可撕。项目枚举改得勤，用贴纸。

#### Q21. 38 张表怎么分组？质检为什么单独 9 张？

- **原本答案**：RBAC 5 / 审计 2 / 租户资源 3 / 外呼配置 5 / 任务名单 4 / 执行会话 5 / IVR 3 / 回呼 2 / 质检 9 ≈ 38。质检单独成包因为它是**不同限界上下文**，只在基础设施层复用。
- **大白话版**：数据库像仓库分货架，各管各的——因为「打电话成功」和「对话质量」是两门完全不同的生意。
- **补充**：`grade` 落在**窄表** `qc_task_items` 而非 `qc_review_results`——10 万行聚合只扫短列，不碰 Text/JSONB。

#### Q22. Alembic 8 个迁移版本怎么理解？

- **原本答案**：版本链 `4f3c67fccf12`（init rbac baseline）→ `bda9784036c5`（outbound p1 models）→ `3f83d065e96d`（task copy source & unique name）→ `3cc700e71d7c`（next retry & provider call id index）→ `96f1f96123f9`（task priority）→ `416f8ed0dca2`（p9 callback trigger & scheduled_at）→ `462b8fec26e1`（p10 user tenant scope）→ `c8f21a45d7be`（p11 qc domain models，**head**）。38 张表由其中 3 个版本建成（7 + 22 + 9），其余 5 个是增量（加列/索引/外键）。
- **大白话版**：数据库结构像一本连环账，8 个版本就是 8 次记账——前 3 笔是「开户」（建表），后 5 笔是「补登」（加列/加索引）。环境一致 = 所有人都按同一本账对到最后一笔（head）。

#### Q23. 软删除为什么不用全局过滤器？

- **原本答案**：`SoftDeleteMixin` 只有字段和 `mark_deleted()`，没有 `with_loader_criteria`/全局事件改写。取舍是**显式 SQL 的可调试性 vs 漏写风险**。全局过滤器一旦有「需要查已删除数据」的例外就要开逃生口，更绕。当前靠「每个查询手写 `is_deleted.is_(False)`」+ 测试兜。
- **大白话版**：自动给所有 SQL 加过滤条件像「房间自动装隐形隔断」——平时省事，但真要看「墙后面有什么」（回收站）就得拆墙。项目选每个房间自己写明，麻烦但一眼看懂。
- **补充（诚实边界）**：这是靠**纪律**而不是靠机制保的，纪律会疲劳，漏写会查到已删除数据。

### 五、状态机与并发控制（8 题）

#### Q24. 5 个状态机是什么？为什么集中管理？

- **原本答案**：外呼任务 6 态、坐席 5 态、回呼任务 6 态、质检任务 5 态、质检明细 4 态。统一 `TRANSITIONS: dict[状态, frozenset[状态]]` + `can_transition` / `ensure_transition`（非法抛 `StateNotAllowed` → 40902）/ `allowed_targets`。好处：状态流转只在一处定义就能被单测逐条钉死。
- **大白话版**：每个业务对象像关卡游戏的角色，「能跳到哪几关」都写在一张通关表里。如果每段业务代码各自写「能不能跳」，改一张表时漏改一处就会出现「明明到不了 5 关却直接跳过去」的 bug。

#### Q25. 单测怎么验证状态机？是笛卡尔积吗？

- **原本答案**：**不是**。四类用例：① 合法边逐条列举；② 非法边逐条列举（断言错误信息**同时含两个枚举值**）；③ 守卫按状态全遍历；④ 覆盖性断言 `test_every_status_has_transition_entry`（每个状态在表里有条目）。外呼 6 态理论 30 条非同态边，用例列了 21 条——**覆盖性的、不是数学完备的**。
- **大白话版**：不是把所有组合（6×6=36 种）全测一遍，而是把「写得出来的合法路 + 明显不能走的非法路」都点名验证，再检查「每个状态都有出场记录」。够用、可维护，不追求数学完备。

#### Q26. `DISPATCHED → COMPLETED` 这条边为什么必须存在？

- **原本答案**：`complete_if_done` 是条件 UPDATE——最后一个明细完成时把任务从 `REVIEWING` 推到 `COMPLETED`。但存在跳过 `REVIEWING` 的场景（明细提前全完成），条件 UPDATE 会在 `DISPATCHED` 状态上直接完成。表里没有这条边，这个合法操作就会抛状态不允许。
- **大白话版**：设计状态机时容易只画「理想路径」，但代码里有条「快车道」（明细提前全完成了，任务直接从派发跳到完成）。加边要按「代码里实际会走的路径」加。

#### Q27. 10 万条批量派发怎么保证均分和幂等？

- **原本答案**：一条 `INSERT … SELECT`：`row_number() OVER (ORDER BY id ASC)` + `CASE` 映射 + `NOT EXISTS` 排除已派 + `ON CONFLICT (task_id, conversation_id) WHERE is_deleted = false DO NOTHING` + `RETURNING id` 计数。均分：`ROUND_ROBIN` 用 `(rn-1) % n`；`AVERAGE` 用 `chunk = ceil(total/n)`、`least(floor((rn-1)/chunk), n-1)`（**必须 floor**，SQLAlchemy 除法结果是 NUMERIC）。分批 `while inserted > 0`。
- **大白话版**：把 10 万件货分给 10 个专家，不能一件一件搬（逐行插入 10 万次），而是一整单让数据库自动均分（按序号取模分桶），每次搬 2000 件。

#### Q28. 乐观锁怎么实现领取 / 提交？

- **原本答案**：带状态条件的原子 `UPDATE`：领取 `WHERE status='PENDING'`；提交/释放 `WHERE status='REVIEWING' AND reviewer_id=me`。靠 `rowcount == 1` 判定唯一成功。提交顺序刻意设计：先 `insert_result`（`ON CONFLICT (item_id)` 防重复提交）→ 再 `submit_item`（改状态）→ 再 `increment_completed`（原子自增）→ 再 `complete_if_done`（条件 UPDATE）。
- **大白话版**：抢座位先到先得——数据库只让第一个「以空闲状态申请」的人成功，后面的人发现条件不满足了就抢失败。不需要锁整张桌子，只需「改的时候核对着当前状态改」。

#### Q29. 超时回收为什么用悲观锁？

- **原本答案**：超时回收是「先读后判」的复合操作（读状态 → 复核 `timeout_at` → 决定是否置 `TIMEOUT`），且多实例定时任务会并发扫到同一条——用 `SELECT … FOR UPDATE` 行锁 + **锁内复核**保证只被处理一次。乐观锁适合「单步操作」，复合判断用悲观锁语义更直白。
- **大白话版**：乐观锁是「结账时核对单价」（单步、快）；超时回收是「先看这单能不能收 → 再决定怎么收」（多步、要思考），这种得先占住这单（行锁）再慢慢看。

#### Q30. psycopg3 的 `rowcount = -1` 踩坑是怎么回事？

- **原本答案**：psycopg3 对 `INSERT…SELECT` 返回 `rowcount = -1`（无法预知），被当成「0 行插入」会导致两个真实缺陷：① 派发多批次**只写入 3 行**（提前中断）；② **首次提交质检结果被误判为「已提交过」**。修复：改用 `RETURNING id` 统计真实行数；**UPDATE 的 rowcount 正常，故乐观锁仍用它**。
- **大白话版**：数据库报告「这次插了多少行」的口径变了——某些 INSERT 它不报数，返回「不知道（-1）」。代码要是把「不知道」当成「0」，就会提前下班（派发中断）或误报「干过了」（重复提交误判）。改成让数据库把插入的 ID 吐回来数就准了。

#### Q31. 真并发测试怎么写的？

- **原本答案**：`tests/integration/test_outbound_number_concurrency.py`：`ThreadPoolExecutor(max_workers=8)` 并发 24 次扣减同一号码，`USAGE_LIMIT=5`，断言 `successes == 5`（**精确值**）。不用事务回滚夹具（避免共享会话干扰），自建 `committed_number` 真实提交 + 测试后物理删除。**同步串行的 TestClient 无法验证真实并发，所以独立写这个集成用例**。
- **大白话版**：平时测试像「一个人按顺序按按钮」，验证不了「8 个人同时抢」。这题用 8 个线程同时去扣「5 次就封顶」的号码，断言「正好成功了 5 次」——多一次都会因为扣超而失败，数据不说谎。
- **补充（诚实边界）**：这是**全项目唯一的真并发用例**，在号码扣减路径上；质检明细用的是「串行 + 语义断言」。

### 六、智能外呼业务链路（6 题）

#### Q32. 名单导入流程？失败行怎么处理？

- **原本答案**：文件校验（≤10MB、仅 `xlsx`/`csv`）→ 表头别名归一化（去空白/下划线/横线/括号转小写）→ 逐行 `is_valid_phone` 校验 → 按 `(user_id, order_id)` 去重 → 建批次 → `bulk_insert` → 批次落 `SUCCESS / PARTIAL_FAILED / FAILED`。失败明细入库按 `MAX_IMPORT_FAILURE_DETAIL=500` 截断（**计数仍真实**），可导出 CSV（带 BOM）。
- **大白话版**：导名单像「安检过闸机」——每行是一个乘客，号码非法/重复就进不了闸（进失败名单）。结束时报「总共多少、成功多少、失败多少」。
- **补充**：这是真实修过的缺陷——**表头做了归一化但查找键没归一化**，导致「表头需含 started_at」恒报错。

#### Q33. 号码次数怎么扣才不出并发问题？

- **原本答案**：`UPDATE … SET used_count = used_count + step WHERE … AND status='ENABLED' AND (usage_limit IS NULL OR used_count + step <= usage_limit)`，返回 `rowcount`（§13 禁止读改写）。执行期 `_pick_calling_number` 对候选依次 `consume_atomically`，成功（`rowcount=1`）即选中。
- **大白话版**：号码次数像「余额」——扣钱和「余额够不够」必须在同一步完成，不能先查再扣（那两秒内可能被别人扣光了）。

#### Q34. 重试阶梯三档怎么走？

- **原本答案**：`apply_failure_ladder`：`permanent=True` 或 `max_retry_count <= 0` → `FAILED`；`retry_count < max_retry_count` → `RETRY_WAITING` + `next_retry_at = now + retry_interval`；否则 → `EXHAUSTED`。名单状态同步：SUCCESS→SUCCESS、终态失败→EXHAUSTED、ASSIGNED/CALLING→PROCESSING、其余→PENDING。执行 / 回调 / 回收**三处共用同一套阶梯**。
- **大白话版**：失败后给三次机会：说「过 60 秒再打」（等待重试）→ 每次都失败到次数用完说「放弃」（耗尽）→ 还有一种是「系统说别再试」（永久失败）。

#### Q35. 回调接口为什么不用 JWT？怎么防重放？

- **原本答案**：真实网关没有登录态，JWT 无从签发。改用共享密钥 HMAC-SHA256：头带 `X-Callback-Timestamp` + `X-Callback-Signature`（`hex(HMAC-SHA256(f"{timestamp}.{body}"))`）。校验链：密钥为空→不可用；时间戳非数字/签名缺失→401；**时间戳超出容差 300s→拒绝（防重放）**；`hmac.compare_digest` 常数时间比对。回调幂等：已有终态 → 忽略。
- **大白话版**：这个接口暴露在公网，等于「公开投信口」。信封上要盖「密钥私章」（签名）+「邮戳时间」（时间戳）——私章保证信是真的，邮戳保证 5 分钟内的信才收（防坏人录下旧信重放）。

#### Q36. 会话状态实际怎么流转？

- **原本答案**：实际只走 `CREATED/ASSIGNED → CALLING → ENDED|TIMEOUT`。`CONNECTED` 与 `RELEASED` **定义了但没有写入点**。**这是如实说明**。
- **大白话版**：设计时画了 5 个状态，实际代码只用到 4 个——有两个是「预留但没接上」。面试主动说清，比被追问出来好。

#### Q37. IVR 模块做到了什么程度？

- **原本答案**：可配流程/节点/流转；有**结构校验**（找不可达节点、终结节点还挂着流转这类问题）；还有**纯逻辑推演**（`ivr_strategy.py` 完全不碰数据库，给一组输入就能跑出轨迹）。Provider 侧 `MockIvrProvider` 返回 `final_node_key = "flow-{id}-end"`。
- **大白话版**：IVR 就是「按键菜单」（按 1 转人工、按 2 听介绍）。系统能配菜单、能检查菜单有没有「死胡同」（怎么按都到不了的地方），还能不接电话就「纸上推演」一遍按键流程。

### 七、坐席分配与预占（6 题）

#### Q38. 坐席是怎么「接到」任务的？触发点是什么？

- **原本答案**：触发点是**坐席状态变为 `IDLE`**——`PUT /outbound/agents/{id}/status` 带 `auto_assign=true` 时，`change_status` 提交状态后调 `OutboundAssignmentService.assign_for_agent(agent.id)`。另外批量入口 `POST /outbound/assignments/dispatch` 遍历空闲坐席逐个派单；呼叫结束 `release_for_record` 也会触发下一单。
- **大白话版**：坐席不抢单，是「一显示空闲，系统立刻塞一单给他」——你一站到窗口前，打饭阿姨就给你盛好了。

#### Q39. 派单按什么顺序挑任务和名单？

- **原本答案**：三级排序，全部集中在 `OutboundAssignmentService`：① 技能队列匹配（任务 `skill_queue_id` 等于坐席队列，或任务为 `NULL` 通用任务）；② 任务优先级 `priority ASC`；③ 名单优先级 `OutboundList.priority DESC`，同优先级按 `record.id ASC`。
- **大白话版**：先看「这活归不归你干」（技能队列），再看「哪个活更急」（任务优先级），最后看「这活里先打哪个客户」（名单优先级）。

#### Q40. 一个坐席同时只能有一个预占，怎么保证？

- **原本答案**：§35 要求。应用层先查 `get_active_assignment_by_agent`（查 `RESERVED`/`ACCEPTED`），数据库层用**部分唯一索引**兜底：`uq_agent_assignments_active_agent`（`WHERE is_deleted = false AND status IN ('RESERVED','ACCEPTED')`）。
- **大白话版**：一个坐席同一时间只能拿一单——先由程序自己检查「你手里是不是还有活」，再由数据库这个「铁面门卫」兜底：只要还有活着的预占记录，插第二条直接被拒。

#### Q41. 派单时一次事务写了几张表？两个 timeout 有什么区别？

- **原本答案**：四张表——`agent_assignments`（建 `RESERVED` 预占）+ `outbound_records`（置 `ASSIGNED`、写 `agent_id`/`assigned_at`/`timeout_at`）+ `outbound_sessions`（复用/新建）+ `agents`（置 `RESERVED`，写状态流水）。两个 timeout 是两回事：`expires_at = now + RESERVATION_TIMEOUT_SECONDS`（60s，坐席没接单就撤）由 `reservation_expire` 盯；`timeout_at = now + task.call_timeout_seconds`（派出去没打完就回收）由 `timeout_recycle` 盯。
- **大白话版**：派单是「预占 + 执行记录 + 会话 + 坐席状态」五处数据必须一起生效。两个超时一个是「服务员站位 60 秒不接就换人」，一个是「电话打出去超过规定时长没结果就作废」。

#### Q42. 打完一单怎么自动拿到下一单？

- **原本答案**：`release_for_record` 释放预占（`RELEASED` + 坐席回 `IDLE`）→ `commit` → 若 `trigger_assign=True` 就调 `assign_for_agent(agent_id)`。源码 docstring 说明：`trigger_assign` 只会**预占**下一单而**不会立即呼叫**，因此**不存在递归风险**。
- **大白话版**：打完 → 交还工位 → 立刻再领一单。但「领」只是把单子放你桌上（预占），不会自动替你拨号，所以不会「无限套娃」。

#### Q43. 内部派单时状态非法为什么只告警不报错？

- **原本答案**：`_switch_agent_status` 用 `can_transition` + `logger.warning` **跳过**；而用户手动改状态走 `ensure_transition` **抛 40902**。设计意图：派单是后台兜底链路，**不该因单个状态守卫把整批派单打断**。代价是「状态没切成功但预占/记录/会话照写」，只留 warning 日志。
- **大白话版**：用户点错按钮要立刻告诉他「不行」（报错）；系统自己批量干活时遇到一条小问题，记个警告跳过继续干，否则一批 50 个坐席的派单可能被一个异常全废掉。

### 八、对话质检与 ASR（7 题）

#### Q44. 为什么质检需要「分段消息」而不是纯文本？

- **原本答案**：质检项依赖说话人与时间戳——判断「坐席是否抢话」「客户是否长时间未回应」必须知道**每句话是谁说的、在录音的什么位置**。所以 ASR 契约是 `AsrSegment(role, text, start_ms, end_ms)` 列表。
- **大白话版**：光有「这台电话说了 10 句话」没用，得知道「哪几句是客服说的、哪几句是客户说的、分别在第几秒」，否则「谁在骂人」根本判不出来。

#### Q45. `AsrSegment` 为什么设计成 frozen dataclass？

- **原本答案**：`@dataclass(frozen=True)` 不可变——转写结果是「事实记录」，防止下游误改；`role` **复用项目已有 `MessageRole` 枚举**（AGENT/CUSTOMER/SYSTEM），不新造枚举；`start_ms`/`end_ms` 可空（部分引擎/降级场景无时间戳），语义上「可空」而非「必须 0」。
- **大白话版**：转写结果像「法庭笔录」——定了就不能改（frozen）；说话人用系统统一的三类身份，不另起炉灶；时间戳可能拿不到，所以允许空着而不是硬填 0。

#### Q46. Provider 抽象 + 工厂 + `.env` 切换怎么落地？

- **原本答案**：`AsrProvider(ABC)` 定义 `transcribe_segments(*, audio_path) -> list[AsrSegment]`（keyword-only + async）；`get_asr_provider()` 用 `_resolve(settings.ASR_PROVIDER, {"mock": MockAsrProvider, "aliyun": AliyunAsrProvider}, "ASR")()`，未知名抛 `AppException` 并**列出可选值**。Service 层只依赖抽象接口。测试里 `ASR_PROVIDER=mock` 保证可复现。
- **大白话版**：换引擎就像换手机卡——Service 只认「SIM 卡槽」（抽象接口），插哪家运营商的卡由 `.env` 决定，不拆机（不改业务代码）。

#### Q47. 转写状态怎么流转？为什么先 commit `RUNNING`？

- **原本答案**：`PENDING → RUNNING → SUCCESS | FAILED`。Service 先置 `RUNNING` 并 **先 commit**（让前端/报表立刻看到「转写中」），再调 Provider（经 `run_sync` 桥接）；成功 → `SUCCESS` + `transcript_engine = provider.name`；异常 → 先落 `FAILED` + commit + `logger.exception`，再 `raise ParamError(f"语音转写失败：{exc}") from exc`（异常链保留根因）。
- **大白话版**：转写是「先把状态改成『转写中』并对外可见，再去做耗时的事」。失败时不只抛错，还先落库「这次失败了」，不然下次重试时不知道上次为什么失败。

#### Q48. 重转怎么保证消息不翻倍？

- **原本答案**：`_rewrite_asr_messages` 四步：① `delete_messages_by_source(conversation.id, MessageSource.ASR)` 删旧 ASR 消息；② `max_message_seq` 用 `func.coalesce(func.max(QcMessage.seq), 0)` 取基准（**空表返回 NULL 是必踩点**）；③ `seq = base_seq + index` 批量插入（不与 TEXT 消息撞号）；④ `conversation.msg_count = count(*)` 回填。
- **大白话版**：重转 = 「把这一版胶片删掉、重新印一版」——先清旧的 ASR 消息（人工消息 TEXT 不动），新消息序号从当前最大序号往后接（不撞号），最后把总数重数一遍。所以转两次不会翻倍。

#### Q49. 阿里云 ASR 是真实接入吗？

- **原本答案**：**是模拟实现，如实说明**。`AliyunAsrProvider` `name="aliyun"`、调用形态照阿里云**录音文件识别**写（`_submit_task` 提交任务拿 task_id → `_poll_result` 轮询 `("RUNNING","RUNNING","SUCCESS")`），但内部是 `uuid.uuid4().hex[:16]` + `asyncio.sleep`，**不发真实 HTTP**。`_pick_script` 用 `hashlib.md5(audio_path)` 按路径哈希选台词本（保证重复转写结果一致）；两个演示开关：路径含 `_fail` → 抛 `RuntimeError("阿里云识别失败：音频格式不支持（StatusCode=41050001）")`、含 `_mono` → 合并为单段 `SYSTEM`。**真实接入只需替换 `_submit_task` / `_poll_result` 两个方法**（用 `httpx.AsyncClient`），`AsrSegment` 契约与异常语义完全复用。
- **大白话版**：现在的阿里云 Provider 是「彩排演员」——剧本、流程、站位（提交→轮询→分段）全对，但台词是背的（uuid + sleep），没真打电话给阿里云。上线时换成「真演员」，剧本一个字不用改。
- **补充**：阿里云对应产品是**录音文件识别**（非实时流式），其「说话人分离 + 句级时间戳 + ITN 数字归一 + 热词表」正是本契约需要的能力。

#### Q50. 转写为什么是「同步阻塞」的？怎么改？

- **原本答案**：端点是同步 `def`，Service 经 `run_sync` 桥接 async Provider——`run_sync` 在无事件循环时 `asyncio.run`，有事件循环时丢进**单线程池**（避免嵌套事件循环）。10 分钟录音会占住一个请求线程。改进：引入异步任务队列（Celery/RQ/自建），端点只负责「收下任务」，转写在后台 worker 执行。
- **大白话版**：现在用户点了「转写」就得**站在柜台等**，直到转完才拿到回执。改进是「先收下、给张小票，转好了再通知你」。

### 九、前端与报表（5 题）

#### Q51. 动态权限路由怎么实现？踩过哪些坑？

- **原本答案**：`constantRoutes`（login/404/CatchAll）+ `asyncRoutes`（首页 + 外呼 12 + 质检 6，18 条 `meta.permission`）；登录后 `filterRoutesByPermission` 递归过滤（`children.length===0` 整组剔除）→ `addDynamicRoutes` 去重 → 菜单由路由渲染。踩过两个坑：① 兜底路由**不能写 `redirect`**（`redirect` 在路由匹配阶段执行、早于 `beforeEach`，会把动态路由提前改写成 /404）；② 守卫注册完路由后**不能返回 `{...to}`**（首次导航命中 `to.name === 'CatchAll'`，vue-router 优先按 name 解析会又落回 404），必须返回 `{path, query, hash, replace: true}`。
- **大白话版**：路由表是「权限可见」的树——你有哪几片叶子的权限，就长出哪几条树枝（菜单+路由）。两个坑：写 `redirect` 等于「在安检前就派人把所有人引向 404 出口」；返回 `{...to}` 等于「按姓名找人，结果找到替身又送回 404」。

#### Q52. Axios 拦截器统一处理什么？

- **原本答案**：请求拦截器**每次实时读** localStorage 注入 `Bearer`；响应拦截器判 `body.code !== 0` → `ElMessage.error` + reject `ApiError(message, code, status)`，**返回整个 `ApiResponse`**（调用方写 `const { data } = await xxx()`）。`baseURL = import.meta.env.VITE_API_BASE_URL`、`timeout=15000`。401 三细节：`url.includes('/auth/login')` 豁免、模块级 `redirecting` 并发去重、带 `redirect` 参数整页刷新回跳。
- **大白话版**：所有请求出门自动带工牌，所有回复进门统一「体检」——`code !== 0` 就是有毛病，直接弹提示并拒收。登录过期时全站一堆请求同时 401，不能每人喊一声（会跳好几遍），要「第一声喊完其他人闭嘴」。

#### Q53. ECharts 怎么封装的？分桶补零怎么做的？

- **原本答案**：`utils/echarts.ts` **按需注册**（只注册 Bar/Line/Pie + Grid/Legend/Title/Tooltip + CanvasRenderer，省约 1MB；**未注册 GaugeChart**）；`useEcharts` 用 `shallowRef` + `setOption(option, true)` + 监听 resize + `onUnmounted` 里 `dispose()`。分桶：SQL 里**先** `func.timezone(QC_REPORT_TIMEZONE, reviewed_at)` **再** `func.date_trunc("day", …)`（顺序不可反）；半开区间 `[start, end)`；**补零在服务层 Python `while cursor <= date_to`**（不用 PG `generate_series`）；前端手写 `formatDate`（不用 `toISOString` 避免 UTC 偏移）。
- **大白话版**：图表库像「工具箱」，整箱扛着 1MB，实际常用就三样，所以只装三样。`dispose()` 是「用完整理干净再走」，不整理就会内存泄漏。切桶前先换算时区是「先改表再切段」，反了跨零点就错位；没有数据的那天补 0，折线图才不会骗人。
- **补充（诚实边界）**：所谓「完成率仪表盘」，代码里其实是**环形图 + 数字卡片**，`GaugeChart` 根本没注册；要有指针式得先补注册。

#### Q54. 前端类型踩过哪些真实的坑？

- **原本答案**：① 后端聚合列名 `pass` 是 Python 保留字（只能字符串列名），TS 侧改名 `pass_count`，页面用 `passOf()` 收敛读取，不散写 `as any`；② `params as unknown as Record<string, unknown>` 双断言（前端必填接口对象断言到 Record 不成立，需先过 `unknown`）；③ 未使用类型导入导致 `vue-tsc` 报错。
- **大白话版**：前后端字段名不能直接对齐时（`pass` 是 Python 关键字），加一层「翻译函数」而不是到处写 `as any`（绕过类型检查等于放弃保险）。

#### Q55. 报表为什么只聚合窄表？时区处理的关键点？

- **原本答案**：`grade` 落在窄表 `qc_task_items`（而非 `qc_review_results` 的 Text/JSONB），10 万行聚合只扫短列。时区关键点：**必须先 `func.timezone(...)` 再 `func.date_trunc(...)`**；用半开区间 `[start, end)`（`end = date_to + 1 天 00:00`）避免「00:00 这分钟被两个桶各算一次」；监控趋势用 `date_trunc("minute")` 不做时区换算。
- **大白话版**：报表要数「每天完成了多少」——数据本来就存着「哪条明细打了几分」，把这个分数放在一张**很窄的表**里，数起来不用翻大字段。切天之前必须先换成上海时间，不然跨零点那天会算错。

### 十、工程与质量（6 题）

#### Q56. 5 个定时任务各是什么？为什么要统一骨架？

- **原本答案**：① `timeout_recycle`（30s，超时回收，每条 commit）；② `retry_dispatch`（60s，扫运行中任务执行到期重试）；③ `reservation_expire`（30s，预占释放，复核三条件，每条 commit）；④ `callback_dispatch`（60s，回呼派单，单条 try/except，整批 commit）；⑤ `qc_item_recycle`（300s，质检明细超时回收，每条 commit）。参数统一 `max_instances=1, coalesce=True, replace_existing=True`；骨架统一「宽松扫描 + 加锁复核 + 动作提交」+ `with session_scope()` + `try/except logger.exception(...)`。
- **大白话版**：像呼叫中心夜班 5 个值班员——① 超时的电话收回来重排；② 到点的失败记录再推一遍；③ 坐席被占 60 秒没接就腾坑；④ 到点该回呼的客户派给空闲坐席；⑤ 专家领了明细 30 分钟不交就放回去让别人领。共同骨架是「先粗看一遍（扫描），真要动手时再拉出来仔细核对（加锁复核），确认没被别人处理过才动手」。
- **补充（诚实边界）**：调度是**单机**，多实例部署每个实例都会跑同一任务，**全靠幂等兜底**。

#### Q57. 测试怎么保证「测得真」？conftest 有哪些关键设计？

- **原本答案**：pytest + FastAPI `TestClient`（底层 httpx）+ **真实 PostgreSQL**（`TEST_DATABASE_URL`，库名 `app_test`，**禁用 SQLite**——要验的正是 `FOR UPDATE`、部分唯一索引、JSONB）。conftest 五个关键设计：① 环境变量在 `import app` **之前**注入（`BCRYPT_ROUNDS=4`、`SCHEDULER_ENABLED=false`、`ASR_PROVIDER=mock`，用 `os.environ.setdefault`）；② `_ensure_database_exists()`（`render_as_string(hide_password=False)` 是真实踩坑）；③ session 级 `engine` 跑 `upgrade head` + 设 `ALEMBIC_DATABASE_URL`；④ `db_session` 外层事务 + `join_transaction_mode="create_savepoint"` + `expire_on_commit=False`，结束 `transaction.rollback()`；⑤ `client` 用 `dependency_overrides[get_db]` 与用例共用会话。另有 `autouse` 的 `_silence_operation_log` monkeypatch `app.main._write_operation_log`。
- **大白话版**：考场必须和真实战场一样——你要练的是「单杠」（PG 特有的行锁/索引），在平地（SQLite）上练出来的成绩上了战场全不算数。测试开机自检顺序很讲究：必须在导入系统前先设环境变量（系统启动时读一次就定死了）；每个用例像拍电影：开场统一搭景（迁移）、演完统一撤（回滚），互不串戏。

### 附录 A：一句话速记模块职责

- **智能外呼执行链路**：导入名单（验号码+去重）→ 建任务 → 挑号码（**原子扣次**）→ 派单/呼叫 → 写通话历史 → 网关回调（**HMAC 签名**）→ 失败走重试阶梯 / 超时被回收。
- **坐席分配与并发控制**：坐席示闲 → 三级排序挑单 → 60 秒预占 → 派单（写四表）→ 接单/隐式接单 → 多号码逐个拨 → 打完释放 → **立刻派下一单**；一条 SQL 派发 + 原子 UPDATE 领取 + 行锁回收。
- **对话质检（QC）**：对话入库（只存路径）→ ASR 转写（说话人+文本+时间戳，清旧写新）→ 建任务+专家组 → 取模均分派发 → 原子领取 → 打分提交（四步一体）→ 超时回收 / 案例沉淀 → 报表（先换时区再切天 + 补零）。
- **服务、权限与报表**：三层架构（Router/Service/Repository）+ 依赖注入链（认证→权限→租户）+ 统一响应与业务码 + 21 页 Vue3 前端 + 5 个定时任务 + Compose 起数据层。

> **大白话**：这四条是把模块实现浓缩成「一条箭头链」。面试官不追问时，念一条就够；要点是**顺序别乱**（先验名单 → 再扣次数 → 再回写），顺序颠倒了就说明没真做过。

### 附录 C：可直接背诵的话术（面试防追问）

#### C1. 关于 ASR（简历写「阿里云 ASR」，代码是模拟实现）

- **简历建议措辞**：

- **被追问时的回答**：
  > 「契约是 `AsrSegment(role, text, start_ms, end_ms)`；`AsrProvider` 定义 `transcribe_segments(*, audio_path)` 抽象方法，`transcribe()` 是模板方法；工厂 `get_asr_provider()` 按 `settings.ASR_PROVIDER` 选实现，未知配置直接报错并列出可选值，Service 层只依赖抽象接口。**阿里云那个实现目前是模拟的**——`name="aliyun"`、调用形态严格照阿里云『录音文件识别』写（先 `_submit_task` 拿 task_id，再 `_poll_result` 轮询状态），但内部是 uuid + `asyncio.sleep`，不发真实 HTTP。之所以这么写，是因为我要先把**契约与状态流转**跑通、把重转幂等（先删旧 ASR 消息再按 `max(seq)+1` 写入）验证扎实，真实接入只需替换 `_submit_task` / `_poll_result` 两个方法为 `httpx.AsyncClient` 调用，上层一个字不用改。」

> **大白话**：简历上可以写「用 Provider 抽象接入了语音转写」；但被问「真打过阿里云吗」，要坦白「现在是彩排——接口、流程、异常语义都做扎实了，换真引擎时上层一个字不用改」。

#### C2. 关于转写状态机（简历写「状态机统一管理」，代码是枚举 + 赋值）

- **简历建议措辞**：
  > 「转写状态用 `PENDING → RUNNING → SUCCESS/FAILED` 管理，先落 `RUNNING` 再调引擎，失败落 `FAILED` 并抛出业务错误。」
- **被追问时的回答**：
  > 「转写状态目前是**枚举 + 服务层直接赋值**，不是像外呼任务/坐席/质检任务那样有一张集中的 `TRANSITIONS` 表——这一点我如实说，是**一致性缺口**。所以我特意把『先置 `RUNNING` 并 commit 再调 Provider』这条顺序约束写进了服务实现：这样前端和报表能立刻看到『转写中』，失败时也能先落 `FAILED` 再抛错，不会出现『抛了异常但库里还是 PENDING』的状态残留。后续我会把 `TRANSCRIPT_TRANSITIONS` 补上，和另外 5 个状态机对齐。」

> **大白话**：转写的状态切换现在是「代码里直接赋值」，没有像别的模块那样有一张集中的通关表——这是实话，也是我记下来要补的一致性缺口。

#### C3. 关于重转幂等（有实现，缺用例）

- **简历建议措辞**：
  > 「转写重跑时**先清理旧的 ASR 消息再写入新的**，保证同一对话重复转写不会产生重复消息。」
- **被追问时的回答**：
  > 「实现上分四步：① 按 `source = ASR` 删除该对话旧的转写消息（人工录入的 TEXT 消息不动）；② 用 `coalesce(max(seq), 0)` 取当前最大序号作基准——这里踩过一个点，空表时 `max()` 返回 NULL，必须 `coalesce`；③ 新消息 `seq = base_seq + index`，从基准往后接，**不会和 TEXT 消息撞号**；④ 最后 `count(*)` 回填 `msg_count`。**要说明的是：这段幂等逻辑有实现，但测试上还没补『同一对话转两次、断言消息数不翻倍』的专门用例**，现有测试只覆盖了『转写成功』和『文本对话被拒』两条。这是我列的待补项。」

> **大白话**：重转「不翻倍」的逻辑是写了的（先删旧再写新），只是还缺一条「转两次看条数」的测试——**做了没测，我如实说**。

#### C4. 关于脱敏（有函数，未接链路）

- **简历建议措辞**：
  > 「提供手机号 / 身份证号脱敏工具（`138****1234`、身份证留前 6 后 4），用于日志与响应输出。」
- **被追问时的回答**：
  > 「脱敏函数 `mask_phone` / `mask_id_card` **有实现也有单元测试**。但要如实说：**当前全仓库没有任何生产调用点**——响应体和日志里都还没接。所以现在没有泄露，只是因为日志里也没把手机号完整打进去，属于『没人踩进去』而不是『有防线拦住』。要补的话有两条路：一是需要输出号码的地方显式调用；二是在日志层加一个 `logging.Filter` 按字段名兜底擦除——后者更稳，因为不靠人记得。我倾向第二条。」

> **大白话**：脱敏函数写好了、也测过，但**代码里没有任何地方真的调用它**——所以现在是「买了防盗锁还没装到门上」，不是「装好了所以安全」。

#### C5. 关于租户隔离（显式声明，无全局强制）

- **简历建议措辞**：
  > 「通过 FastAPI 依赖注入把**认证 → 权限 → 租户范围**收敛为一条链，普通用户跨租户访问返回 403。」
- **被追问时的回答**：
  > 「链是四段：`get_token_payload`（解 JWT 并查 Redis 登出黑名单）→ `get_current_user`（查库 + 验 `is_active`）→ `require_permission(*codes)`（超管短路放行、其余按权限码取或）→ `tenant_scope_optional/required`（`_resolve_tenant_scope` 收敛入参：超管或未绑定租户的账号不限租户，绑定租户的普通用户传别的租户直接 403）。**但我要如实说明一个风险**：行级隔离是**显式声明式**的，靠每个路由自己挂 `Depends(tenant_scope_*)`，Repository 侧是 `if tenant_id is not None` 才加过滤条件——任一环漏掉就**静默失效**，没有兜底。我建议的补法是像 `test_openapi_docs.py` 那样写一个规范测试，扫描所有返回 `PageData` 的接口断言其带了租户依赖。」

> **大白话**：跨公司看数据这条防线，是「每个接口自己挂门禁」挂出来的，不是大楼统一装的——新接口忘了挂就悄悄敞开，所以我想补一个自动扫描的测试当守门员。

#### C6. 通用「不确定 / 不会」的兜底话术

- 若被问到确实没做过的点，**不要硬编**，用：
  > 「这块目前没有实现，是我在 MVP 阶段取舍掉的。我的判断依据是……（说清权衡：收益 / 成本 / 优先级），如果要补，我会从……入手。」
- 若被问到实现细节记不清，用：
  > 「具体参数我记不精确了，但设计上是……（讲清原理与取舍），代码里在 `<模块>` 这一段，可以现场看一下。」

> **大白话**：没做过的别硬编——直接说「这块当时取舍掉了，原因是……，要补我会从……入手」；参数记不准就说「参数记不清了，但设计思路是……，代码在某某模块可以现场翻」。**坦白 + 讲清权衡，比编一个听起来完美但一问就碎的答案强得多。**

### 大白话「三句话速记」

1. **打出去**：名单进来过安检（验号码、去重）→ 建任务 → 坐席一示闲就预占一单 → 原子扣号码次数 → 拨号 → 网关回调写回结果 → 打不通排队重试、超时被值班员收回。
2. **别抢乱**：一条 SQL 把 10 万条取模均分（重复派也不会派两遍）；领取靠「改的时候核对着状态改」（只有一人成功）；回收靠「先锁住再慢慢看」；一个坐席同时只能有一单（数据库铁门）。
3. **质检与报表**：录音转成「谁说的、第几秒」的分段文字（重转先清旧的）→ 派给专家打分 → 领了 30 分钟不交就放回去 → 报表先换时区再切天、空的天补 0。
