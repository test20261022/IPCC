# 提交流水线方案

> 本文档回答两个问题：**本项目能不能做一条提交流水线**，以及**怎么做**。方案覆盖本地提交钩子（pre-commit / pre-push）与远端 CI（PR 门禁、主干与标签流水线），并给出可直接落地的配置骨架。
>
> 文档状态：方案（尚未创建任何流水线文件）。核查日期：2026-10-22。

---

## 0. 结论

**能做，而且成本不高。**

但需要先明确一个边界：

- **本地 Git 钩子**（commit / push 时触发）只能约束本机操作，可以被 `--no-verify` 绕过，**不能作为最终门禁**；
- **远端 CI**（push / PR / tag 时触发）才是不可绕过、可审计的权威门禁。

因此推荐的完整形态是两层：

```text
本地：commit-msg + pre-commit + 可选 pre-push   → 快速失败，减少无效推送
远端：PR CI + 主干/标签流水线                  → 权威门禁，决定能否合并与发布
```

当前项目的实际情况：

| 维度 | 现状 | 结论 |
|---|---|---|
| Git 仓库 | 尚未初始化 | 流水线的前置条件，需先完成基线入库 |
| CI 配置 | 不存在 | 需要新增（GitHub Actions 或 GitLab CI） |
| 后端静态检查 | `ruff check app tests` 已通过 | 可直接作为门禁 |
| 后端格式检查 | `ruff format --check` 未通过，大量文件会被重排 | **暂不作为门禁**，需先做一次性格式化 |
| 后端单元测试 | `pytest tests/unit` 实测 277 passed，0.42s | 适合放进 pre-push |
| 后端全量测试 | 依赖真实 PostgreSQL；本地 5432 当前未监听 | 放进 CI，使用 PostgreSQL service |
| 数据库迁移 | Alembic 支持 `ALEMBIC_DATABASE_URL`，conftest 会自动建测试库并 `upgrade head` | 可在 CI 校验空库升级 |
| 前端类型检查 | `npm run type-check` 已通过 | 可直接作为门禁 |
| 前端构建 | 具备 `npm run build`，锁文件存在 | 可在 CI 构建并保留产物 |
| 部署 | 无应用 Dockerfile、无部署目标 | **CD 不在本期范围**，流水线止于构建产物 |

## 1. 目标与原则

### 1.1 目标

1. 在**提交时**拦住低级问题：格式脏数据、调试残留、大文件、明显语法/导入错误；
2. 在**推送/PR 时**验证可运行性：单元测试、接口测试、数据库迁移、前端类型与构建；
3. 在**合并时**保证 `main` 始终可发布；
4. 在**打标签时**产出可追溯的发布版本。

### 1.2 原则

- **快速失败**：越靠前的阶段越便宜，本地秒级，远端分钟级；
- **确定性**：外部依赖固定为 mock；测试进程关闭调度器；数据库使用真实 PostgreSQL；
- **可复现**：CI 中只使用一次性测试密钥，不依赖开发者本机环境；
- **不可绕过**：本地钩子可跳过，但 PR 必须通过远端检查才能合并；
- **渐进落地**：先本地钩子，再 CI，再分支保护，最后考虑发布与覆盖率。

## 2. 流水线分层设计

```text
git commit ──> [L0 commit-msg] ──> [L1 pre-commit] ──> 本地提交
                                                        │
git push ───> [L2 pre-push（可选）] ─────────────────────┤
                                                        ▼
PR ─────────> [L3 CI：lint / unit / api / migration / frontend] ──> 允许合并
                                                        │
tag vX.Y.Z ─> [L4 发布：重跑门禁 + 构建产物 +（可选）部署]
```

### 2.1 阶段定义

| 阶段 | 触发点 | 执行内容 | 目标耗时 | 失败后果 |
|---|---|---|---|---|
| L0 `commit-msg` | `git commit` | 校验提交信息符合 `type(scope): subject` | 毫秒级 | 拒绝提交 |
| L1 `pre-commit` | `git commit` | 尾随空格、文件末尾换行、合并冲突标记、大文件、YAML/JSON 语法、`ruff check`（仅暂存文件） | 秒级 | 拒绝提交 |
| L2 `pre-push` | `git push` | `pytest tests/unit`、`npm run type-check` | 十秒级 | 拒绝推送（可绕过） |
| L3 PR CI | PR 创建/更新 | 后端 lint、单元测试、全量测试（PostgreSQL）、迁移校验、前端类型检查与构建 | 分钟级 | **阻止合并** |
| L4 发布 | 合并到 `main` / 推送标签 | 重跑 L3、生成前端构建产物、发布记录 | 分钟级 | 阻止发布 |

### 2.2 为什么不把全量测试放在提交时

全量测试依赖真实 PostgreSQL，本地必须先启动数据库；如果把它放进 `pre-commit`：

- 每次提交都要求 Docker/数据库在线，开发体验差；
- 提交频率高，重复执行全量测试浪费明显；
- 钩子可以被绕过，安全性并没有提升。

因此：**提交时只做静态与轻量检查，全量验证交给 pre-push（可选）和 CI。**

## 3. 本地层：提交钩子

### 3.1 工具选择

使用 `pre-commit` 统一管理钩子：

- 跨平台（Windows / Linux 均可）；
- 钩子版本固定在配置文件中，团队成员一致；
- 支持只检查暂存文件，速度快；
- 与 CI 使用同一套 ruff 规则，避免“本地过、CI 挂”。

### 3.2 `.pre-commit-config.yaml`

```yaml
minimum_pre_commit_version: "3.7.0"
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-merge-conflict
      - id: check-added-large-files
        args: ["--maxkb=5120"]
      - id: check-yaml
      - id: check-json

  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.8.4
    hooks:
      - id: ruff
        args: ["--fix"]
        files: ^backend/.*\.py$
```

说明：

- `ruff` 的版本必须与 `backend/requirements.txt` 中的 `ruff>=0.8.0` 对齐，避免规则差异；
- **暂不加入 `ruff-format`**：当前代码库执行 `ruff format --check` 会被判定为大量未格式化文件，直接接入会造成一次性巨量改动和持续冲突。待完成一次独立的格式化提交后，再启用该钩子；
- `check-added-large-files` 上限 5 MB，用于拦住录音、数据库转储等误提交。

### 3.3 提交信息校验（可选）

两种做法，任选其一：

1. **commitlint**（Node 生态）：在 `frontend` 外单独建一个轻量工具配置，或在根目录引入 `@commitlint/cli`；
2. **本地 Python 脚本**：新增 `scripts/check_commit_msg.py`，在 `pre-commit` 的 `commit-msg` 阶段执行正则校验。

如果团队只有 1–2 人，可先靠约定，等提交量上来再强制。

### 3.4 `pre-push`（可选）

建议加入一个轻量钩子：

```yaml
  - repo: local
    hooks:
      - id: backend-unit-tests
        name: backend unit tests
        entry: python -m pytest tests/unit -q
        language: system
        pass_filenames: false
        stages: [pre-push]
        files: ^backend/
```

前端类型检查也可以放在 `pre-push`，但 `vue-tsc` 比单元测试慢，是否加入取决于团队对推送频率的容忍度。

### 3.5 本地层的能力边界

- 只检查**暂存文件**，不会发现“未暂存但已破坏”的代码；
- 可以通过 `git commit --no-verify` 绕过；
- 因此本地层定位是“减少噪音”，不是“保证质量”。

## 4. 远端层：CI 设计

### 4.1 平台选择

| 平台 | 适用情况 | 说明 |
|---|---|---|
| GitHub Actions | 代码托管在 GitHub | 配置简单，PostgreSQL 以 service 容器提供 |
| GitLab CI | 代码托管在 GitLab | 用 `services` 提供 PostgreSQL，结构等价 |
| 自建 Jenkins / Woodpecker | 有内网构建机 | 成本更高，不建议作为首期方案 |

当前仓库尚未初始化，也没有远端地址，**平台需在托管确定后二选一**。下文以 GitHub Actions 为主，GitLab CI 给出等价骨架。

### 4.2 任务划分

| Job | 依赖 | 内容 | 是否必需 |
|---|---|---|---|
| `backend-lint` | 无 | `ruff check app tests` | 必需 |
| `backend-unit` | 无 | `pytest tests/unit -q` | 必需（快速反馈） |
| `backend-api` | PostgreSQL | `pytest -q`（全量） | 必需 |
| `migration-check` | PostgreSQL | 空库 `alembic upgrade head` | 必需 |
| `frontend` | 无 | `npm ci` + `type-check` + `build` | 必需 |
| `coverage` | PostgreSQL | `pytest --cov`，先只记录不设阈值 | 可选，后续 |
| `deploy` | 构建产物 | 部署到目标环境 | 本期不做 |

### 4.3 GitHub Actions 骨架

```yaml
name: ci

on:
  pull_request:
  push:
    branches: [main]
    tags: ["v*"]

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  backend-lint:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: backend
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"
          cache: pip
          cache-dependency-path: backend/requirements.txt
      - run: pip install -r requirements.txt
      - run: ruff check app tests

  backend-unit:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: backend
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"
          cache: pip
          cache-dependency-path: backend/requirements.txt
      - run: pip install -r requirements.txt
      - run: python -m pytest tests/unit -q

  backend-api:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: app
          POSTGRES_PASSWORD: app
          POSTGRES_DB: app_test
        ports: ["5432:5432"]
        options: >-
          --health-cmd "pg_isready -U app"
          --health-interval 5s
          --health-timeout 3s
          --health-retries 30
    env:
      TEST_DATABASE_URL: postgresql+psycopg://app:app@localhost:5432/app_test
      DATABASE_URL: postgresql+psycopg://app:app@localhost:5432/app_test
      SECRET_KEY: ci-only-secret
      SCHEDULER_ENABLED: "false"
      ASR_PROVIDER: mock
    defaults:
      run:
        working-directory: backend
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"
          cache: pip
          cache-dependency-path: backend/requirements.txt
      - run: pip install -r requirements.txt
      - run: python -m pytest -q

  migration-check:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: app
          POSTGRES_PASSWORD: app
          POSTGRES_DB: app_migrate
        ports: ["5432:5432"]
        options: >-
          --health-cmd "pg_isready -U app"
          --health-interval 5s
          --health-timeout 3s
          --health-retries 30
    env:
      DATABASE_URL: postgresql+psycopg://app:app@localhost:5432/app_migrate
      ALEMBIC_DATABASE_URL: postgresql+psycopg://app:app@localhost:5432/app_migrate
      SECRET_KEY: ci-only-secret
    defaults:
      run:
        working-directory: backend
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"
          cache: pip
          cache-dependency-path: backend/requirements.txt
      - run: pip install -r requirements.txt
      - run: alembic upgrade head
      - run: alembic current

  frontend:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: frontend
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "24"
          cache: npm
          cache-dependency-path: frontend/package-lock.json
      - run: npm ci
      - run: npm run type-check
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: frontend-dist
          path: frontend/dist
          retention-days: 7
```

### 4.5 关键参数说明

| 参数 | 取值 | 理由 |
|---|---|---|
| Python | `3.13` | 与本地版本一致；`ruff` 的 `target-version=py310` 只是语法下限 |
| Node | `24` | 与本地一致，且为 LTS |
| PostgreSQL | `16` | 与 `docker-compose.yml` 一致 |
| `POSTGRES_DB` | `app_test` / `app_migrate` | 测试库与迁移校验库分离，互不污染 |
| `SCHEDULER_ENABLED` | `false` | 测试进程不启动后台调度，保证可复现 |
| `ASR_PROVIDER` | `mock` | 避免外部依赖与轮询延时 |
| `SECRET_KEY` | 一次性 CI 值 | 禁止使用真实密钥 |
| 并发策略 | 同 ref 取消旧任务 | 避免连续推送堆积构建 |

### 4.6 迁移校验说明

`backend/tests/conftest.py` 的 `engine` 夹具会在会话开始时：

1. 连接维护库 `postgres`，检查并创建测试库；
2. 设置 `ALEMBIC_DATABASE_URL` 指向测试库；
3. 执行 `alembic upgrade head`。

因此：

- 全量测试本身已经覆盖“空库升级”；
- `migration-check` 单独成 job 的价值是：**在测试失败时仍能明确区分“迁移链坏了”还是“业务用例失败”**；
- 后续发布前再加一个“上一发布版本库 → head”的升级任务，用于验证跨版本迁移。

注意：官方 `postgres` 镜像会把 `POSTGRES_USER` 创建为超级用户，具备 `CREATEDB` 权限；如果改用受管数据库，需要预先创建测试库，否则 conftest 的建库步骤会失败。

## 5. 分支保护与合并规则

CI 只有配合分支保护才真正生效。

### 5.1 `main` 保护规则

- 禁止直接 push；
- 必须通过 PR 合并；
- 必须通过以下检查：`backend-lint`、`backend-unit`、`backend-api`、`migration-check`、`frontend`；
- 至少 1 人批准；
- 合并前分支必须与 `main` 同步；
- 使用 Squash merge；
- 合并后自动删除分支。

### 5.2 绕过策略

- 本地 `--no-verify` 允许存在，但 PR 检查不可关闭；
- 管理员紧急绕过必须记录原因，并在下一次提交中补齐；
- 禁止通过修改 CI 配置来“让流水线变绿”。

## 6. 发布流水线（L4）

本期只做到“可构建、可追溯”，不包含部署。

### 6.1 触发

- 合并到 `main`：重跑全部检查，保留前端构建产物；
- 推送 `v*` 标签：重跑全部检查，生成发布记录与产物。

### 6.2 发布步骤

1. 确认 `main` 全部检查通过；
2. 同步 `APP_VERSION`、`frontend/package.json` 版本；
3. 更新 `CHANGELOG.md`；
4. 创建 annotated tag `vX.Y.Z`；
5. CI 重跑门禁并归档 `frontend/dist`；
6. 备份数据库后执行 `alembic upgrade head`；
7. 部署（后续接入）；
8. 冒烟验证并记录。

### 6.3 后续可扩展项

- 容器镜像构建与推送（需先补应用 Dockerfile）；
- 自动部署与回滚；
- 依赖漏洞扫描（`pip-audit`、`npm audit`）；
- 覆盖率趋势（`pytest-cov` + 报告归档）。

## 7. 风险与已知限制

| # | 风险/限制 | 现状 | 应对 |
|---|---|---|---|
| 1 | 代码尚未统一 `ruff format` | `ruff format --check` 当前失败 | 先做一次独立格式化提交，再把 formatter 加入门禁；之前只跑 `ruff check` |
| 2 | 全量测试依赖 PostgreSQL | 本地 5432 未监听；CI 用 service 容器 | 本地执行前先 `docker compose up -d db`；CI 固定 PG 16 |
| 3 | 本地钩子可被绕过 | Git 机制决定 | 以 CI + 分支保护为权威门禁 |
| 4 | 无应用 Dockerfile / 部署目标 | 只有数据库与 Redis 编排 | CD 不在本期范围，流水线止于构建产物 |
| 5 | Windows 换行符差异 | 仓库尚未初始化 | 先加入 `.gitattributes`，统一 LF |
| 6 | 测试建库需要 `CREATEDB` | 官方 PG 镜像默认满足 | 受管数据库需预先建库或调整 conftest |
| 7 | 无 Git 远端与 CI 配置 | 当前均不存在 | 先完成基线入库，再选择 GitHub / GitLab |
| 8 | 全量用例耗时高于单元测试 | 文档记录 756 个用例、约 33 秒 | 单元测试前置快速反馈，全量只在 CI / pre-push 可选阶段跑 |
| 9 | CI 成本 | 每次 PR 跑 5 个 job | 开启依赖缓存、取消旧任务、必要时按路径过滤 |

## 8. 落地步骤

| 阶段 | 动作 | 验收标准 |
|---|---|---|
| P0 基线 | 按《版本控制方案》初始化 Git、补 `.gitignore` / `.gitattributes`、完成基线提交 | 仓库中存在 `.gitattributes`，无 `.env` / `storage` / `dist` |
| P1 本地钩子 | 新增 `.pre-commit-config.yaml`，安装 `pre-commit`，执行 `pre-commit run --all-files` 并修正问题 | 任意一次提交都会跑通钩子；大文件与冲突标记被拦截 |
| P2 CI | 新增 `.github/workflows/ci.yml` 或 `.gitlab-ci.yml`，推送后验证 5 个 job | PR 页面能看到 lint / unit / api / migration / frontend 结果 |
| P3 分支保护 | 对 `main` 开启保护，把 5 个 job 设为必需检查 | 未通过检查的 PR 无法合并 |
| P4 发布 | 增加 tag 触发、产物归档、`CHANGELOG` | 推送 `v*` 标签后自动重跑门禁并归档 `frontend/dist` |
| P5 可选增强 | 覆盖率、依赖扫描、镜像、CD | 按需引入，不阻塞首期落地 |

## 9. 验证命令

### 9.1 本地验证

```bash
# 1. 安装并运行本地钩子
pre-commit install
pre-commit install --hook-type commit-msg
pre-commit run --all-files

# 2. 后端静态检查（当前已通过）
cd backend
ruff check app tests

# 3. 后端单元测试（无需数据库，当前 277 passed）
python -m pytest tests/unit -q

# 4. 后端全量测试（需先启动 PostgreSQL）
docker compose up -d db
python -m pytest -q

# 5. 迁移校验（使用独立库）
#    ALEMBIC_DATABASE_URL 指向空库后执行
alembic upgrade head
alembic current

# 6. 前端检查
cd ../frontend
npm ci
npm run type-check
npm run build
```

### 9.2 CI 验证

- 提交一个包含未使用导入的 Python 文件，确认 `backend-lint` 失败；
- 提交一个故意失败的单元测试，确认 `backend-unit` 失败；
- 修改迁移链但不更新 `down_revision`，确认 `migration-check` 失败；
- 提交一个 TypeScript 类型错误，确认 `frontend` 失败；
- 以上任一失败时，PR 的合并按钮应被阻塞。

## 10. 最终形态

```text
commit  →  提交信息 + 尾随空格 + 大文件 + ruff check（秒级，可绕过）
push    →  单元测试 + 前端类型检查（可选，十秒级）
PR      →  lint + unit + api + migration + frontend（权威门禁，不可绕过）
main    →  重跑全部门禁，保留构建产物
tag     →  重跑门禁 + 归档产物 + 发布记录
```

一句话总结：**本地钩子负责“别把明显错误推上去”，远端 CI 负责“没通过就不许合并”，两者配合才是一条完整的提交流水线。**
