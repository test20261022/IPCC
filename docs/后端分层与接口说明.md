## 0. 一分钟速览 + 四条必须说清的事实

| 主题 | 结论 |
|---|---|
| 分层 | `app/api/v1/**`（Router）→ `app/services/**`（Service）→ `app/repositories/**`（Repository）→ `app/models/**`（ORM） |
| Router 职责 | 只做 HTTP 层（§54）：声明路由/入参校验/`response_model`/`dependencies`/文档元信息，**不碰事务、不写业务规则** |
| Service 职责 | 业务规则 + **事务提交在本层**（§55），`XXXService(db)` 内部 `self.repo = XXXRepository(db)` |
| Repository 职责 | 只写 SQLAlchemy 查询（§54），统一过滤软删除；`tenant_id` 传入才过滤 |
| 依赖注入链 | `get_token_payload` → `get_current_user` → `require_permission(*)` → `tenant_scope_optional/required`，四段串成一条链 |
| 统一响应 | 所有接口返回 `{code, message, data}`：`ok()` / `fail()` / `page_data()`，类型上是 `ApiResponse[T]` / `PageData[T]` |
| 业务码 | `BizCode`（IntEnum）：`0` / `40001` / `40101` / `40301` / `40401` / `40901` / `40902` / `40903` / `40904` / `50000` |
| 异常处理 | `AppException` 体系 + 4 个全局 `exception_handler`，**任何异常出口都被收敛成统一响应体** |
| 入参校验 | Pydantic v2：`Field` 约束 + `field_validator` + `ConfigDict(from_attributes=True / extra="forbid")` |
| 文档 | FastAPI 自动生成 OpenAPI；`custom_openapi()` 注入 examples，另有覆盖率测试守门 |
| 表级权限 | 权限码（`require_permission("qc:conversation:list")`）+ RBAC 5 表 |
| 行级权限 | 租户范围依赖（`tenant_scope_optional / required`）+ Repository 的 `where(tenant_id == ...)` |
| 审计 | `login_logs`（登录成功/失败都记）+ `operation_logs`（写操作由中间件统一落库） |

### 四条如实说明（请先读这段）

1. **「敏感字段脱敏」目前是「工具已就绪、未接入链路」。** `app/utils/masking.py` 提供了 `mask_phone`（`13812341234 → 138****1234`）与 `mask_id_card`（保留前 6 后 4），并有单测 `tests/unit/test_masking.py`。但**全仓库（除定义与测试外）没有任何一处调用它**——响应体与日志都没有调用脱敏函数。现状之所以没暴露问题，是因为代码里也没有把手机号完整打进日志（`logger` 里出现的「号码」都是业务文案）。**结论：脱敏是「预留能力」，不是「已生效的防线」**，详见 §2.8。

2. **业务码里没有 `50001`，系统异常是 `50000`。** `BizCode.SYSTEM_ERROR = 50000`，`handle_unexpected_exception` 返回的就是它。若面试时你按记忆说 `50001`，打开 `core/response.py` 会对不上。

3. **依赖注入链里的「租户」这一环不是全局强制的，而是按路由显式声明。** 只有写了 `Depends(tenant_scope_optional)` / `Depends(tenant_scope_required)` 的接口才有行级隔离；Repository 的过滤条件是 `if tenant_id is not None`，**不传就不过滤**。也就是说：**新写一个列表接口时如果忘了加这一行依赖，行级隔离就静默失效**，没有全局兜底。详见 §2.7。

4. **审计日志表的字段只填了一部分。** `operation_logs` 模型里定义了 `target_type` / `target_id` / `request_id` / `detail` 四个字段，但中间件（`main.py::_build_operation_log`）**没有填充它们**（恒为 `NULL`）。目前记录的是：谁（`user_id` + 回查的 `username`）、何时（`created_at`）、什么路径方法（`path` / `method` / `module`）、结果（`status_code` / `success`）、耗时（`duration_ms`）、来源（`ip` / `user_agent`）。详见 §2.9。

另外两条：`require_superuser`（`api/deps.py`）**已定义但当前没有任何路由使用**（权限靠 `require_permission` 里的超管短路放行实现）；Redis 不可用时**登出黑名单降级为放行**（登出后旧 token 仍能用到过期），对应测试被 `skipif(not cache_available())` 标记。

## 第一部分 · 三层架构在项目里是什么

### 1.1 目录与职责边界

```
backend/app/
├── main.py                     # FastAPI 应用：lifespan / 中间件 / 全局异常处理 / OpenAPI 覆盖
├── api/
│   ├── deps.py                 # 【基线冻结】鉴权契约：get_db / get_current_user / require_permission / 租户范围
│   └── v1/
│       ├── router.py           # v1 路由聚合，挂载 auth / outbound / qc
│       ├── auth.py             # 认证接口
│       ├── outbound/*.py       # 外呼 12 个路由文件
│       └── qc/*.py             # 质检 6 个路由文件
├── services/
│   ├── auth_service.py
│   ├── outbound/*.py           # 任务/名单/执行/派单/回呼/报表/IVR...
│   └── qc/*.py                 # 对话/任务/派发/质检/案例/报表/转写/评分
├── repositories/
│   ├── __init__.py             # docstring 即纪律声明：只做查询，禁止业务规则/权限/状态机
│   ├── user_repository.py
│   ├── outbound/*.py
│   └── qc/*.py
├── schemas/                    # Pydantic v2 入参/出参（按域分目录）
├── models/                     # SQLAlchemy 2.0 声明式模型
├── core/                       # 配置 / 响应 / 异常 / 权限目录 / 安全 / 缓存 / 日志 / OpenAPI 示例
└── db/                         # Base / Mixin / engine / session / get_db / session_scope
```

三层的边界，在代码里是用**一句话纪律**钉住的：

| 层 | 纪律原文 | 位置 |
|---|---|---|
| Repository | 「只负责 SQLAlchemy 查询，禁止写业务规则 / 权限 / 状态机（§54）」 | `repositories/__init__.py` |
| Router | 「Router 只做 HTTP 层（§54）」 | `api/v1/auth.py` 文件 docstring |
| Service | 「事务在本层提交（§55）」 | 各 Service 类 docstring |
| 会话 | 「事务由 Service 层控制（§55），Router 不碰事务」 | `db/session.py` 文件 docstring |
| 鉴权 | 「【基线冻结】鉴权契约在此定义，后续模块只允许调用，禁止修改」 | `api/deps.py` 文件 docstring |

### 1.2 一次请求的完整链路

以「质检对话列表」`GET /api/v1/qc/conversations` 为例：

```
HTTP 请求
  │
  ├─ ① operation_log_middleware（main.py）
  │     · 记开始时间；放行；返回后若非 GET/HEAD/OPTIONS 且路径在 /api/v1 下，写 operation_logs
  │
  ├─ ② 依赖注入链（api/deps.py）
  │     · get_db            → 建一个请求级 Session
  │     · require_permission("qc:conversation:list")
  │         └─ get_current_user → get_token_payload → HTTPBearer → JWT 解析 → Redis 黑名单
  │                └─ UserRepository.get_by_id → is_active 检查
  │     · tenant_scope_optional → _resolve_tenant_scope（收敛到用户自己的租户）
  │     · PageParams（page / page_size 的 ge/le 校验）
  │
  ├─ ③ Router（api/v1/qc/conversations.py::list_conversations）
  │     · 只做：取 query 参数 → 调 service → return ok(page_data(...))
  │
  ├─ ④ Service（services/qc/conversation_service.py::list_conversations）
  │     · 调 repo.list_paged(...) + repo.count(...)，返回 (items, total)
  │
  ├─ ⑤ Repository（repositories/qc/conversation_repository.py::list_paged）
  │     · _apply_filters：is_deleted=false（必加）+ tenant_id（有才加）+ 各筛选条件
  │     · order_by(started_at desc, id desc) + offset/limit
  │
  └─ ⑥ 响应序列化
        · response_model=ApiResponse[PageData[ConversationOut]] 负责把 ORM 对象
          经 ConversationOut.model_validate（from_attributes=True）转成 JSON
```

**注意 ③ 里 Router 真的什么都没干**——没有事务、没有校验逻辑、没有业务判断，`ok()` 是唯一的"组装"动作。这是本项目分层的可核对证据：随便打开一个路由函数，函数体通常只有 1～2 行。

### 1.3 事务归属：为什么 Router 不碰事务

`db/session.py` 里有两个入口，分别服务两类场景：

| 函数 | 使用者 | 事务行为 |
|---|---|---|
| `get_db()` | FastAPI 依赖（Router → Service 请求链路） | 只 `yield`；**异常时 `rollback()`**，正常**不 commit**（交给 Service 决定何时提交）；`finally: close()` |
| `session_scope()` | 非请求场景：定时任务 / 中间件 / 脚本 | `yield` 后**自动 `commit()`**；异常 `rollback()` |

设计意图很明确：**"一次业务操作 = 一个事务边界"，只有 Service 知道这次操作到哪算完整**。比如质检提交链路里「写结果 → 改明细状态 → 任务完成数自增 → 条件完成」是四步，必须一起成功，所以 Service 里在四步之后才 `commit()`；而外呼超时回收是**逐条提交**（`with session_scope()` 每条一个事务），因为每条记录的回收互相独立，不该被彼此的失败连坐。这个"批量操作按条提交还是整批提交"的取舍，在项目里是按业务原子性分别决定的（回呼派单 `dispatch_due` 是**整批一个 commit**，超时回收是**每条一个 commit**）。

## 第二部分 · 技术栈逐项解释

### 2.1 FastAPI

| 概念 | 在本项目的用法 |
|---|---|
| ASGI 应用 | `app = FastAPI(title, version, description, lifespan=lifespan)`（`main.py`） |
| `lifespan` | `async with` 上下文：启动时 `get_redis()` 预热 + `start_scheduler()`；关停时 `shutdown_scheduler()` |
| `APIRouter` | 每个领域一个 router，带 `prefix` 与 `tags`，例如 `APIRouter(prefix="/qc/conversations", tags=["质检-对话"])` |
| 路由聚合 | `api/v1/router.py` 逐个 `include_router`；`main.py` 用 `app.include_router(api_router, prefix=settings.API_V1_PREFIX)` |
| 依赖注入 | `Depends()`：数据库会话、当前用户、权限、租户范围、分页参数 |
| 装饰器元信息 | `summary` / `description` / `response_model` / `dependencies` 全部写在装饰器上，直接进 OpenAPI |
| 中间件 | `@app.middleware("http")` 的 `operation_log_middleware`；另有 `CORSMiddleware`（仅当 `CORS_ORIGINS` 非空时挂载） |
| 异常处理 | `@app.exception_handler(X)` 四个：`AppException` / `RequestValidationError` / `StarletteHTTPException` / `Exception` |
| 自动文档 | `app.openapi` 被 `custom_openapi` 覆盖，注入 examples |
| 线程池桥接 | `starlette.concurrency.run_in_threadpool`——中间件写日志时避免阻塞事件循环 |

**一个值得说的细节**：`bearer_scheme = HTTPBearer(auto_error=False, ...)`。FastAPI 默认在缺 token 时会自己返回 403，而本项目要的是**统一 401/40101**，所以关掉自动报错，改由 `get_token_payload` 主动 `raise Unauthorized()`。这是"框架默认行为 vs 项目契约"冲突时，选择让契约赢的典型处理。

### 2.2 Router–Service–Repository 三层

**为什么是三层而不是两层或四层**（`repositories/__init__.py` 的 docstring 已经写出了底线）：

- **Router 不写业务**：同一个业务规则（例如"对话被质检引用后禁止删除"）可能被多个入口触发（接口 / 导入 / 定时任务），规则写在 Router 里就必然重复。
- **Repository 不写业务**：它是唯一直接接触 SQLAlchemy `select()` 的地方，职责是"把查询条件翻译成 SQL"，一旦它开始做权限判断或状态机校验，事务边界与失败语义就散掉了。
- **Service 是唯一"知道完整业务故事"的层**：它拿到 payload → 校验前置条件 → 调 repo 读写 → 决定提交时机 → 写业务日志。

在代码里最直观的对照是删除对话：

```python
# Router：只剩一行（api/v1/qc/conversations.py）
def delete_conversation(conversation_id: int, db: Session = Depends(get_db)) -> Any:
    QcConversationService(db).delete_conversation(conversation_id)
    return ok(None)

# Service：业务规则 + 事务（services/qc/conversation_service.py）
def delete_conversation(self, conversation_id: int) -> None:
    conversation = self.get_conversation(conversation_id)          # 不存在 → 404
    if self.repo.count_task_items(conversation_id) > 0 or (
        self.repo.count_case_references(conversation_id) > 0
    ):
        raise StateNotAllowed("对话已被质检引用，禁止删除")          # 业务规则 → 40902
    conversation.mark_deleted()                                     # 软删除
    self.db.commit()                                                # 事务边界
    logger.info("删除对话成功：id=%s", conversation_id)

# Repository：只给数据（repositories/qc/conversation_repository.py）
def count_task_items(self, conversation_id: int) -> int:
    stmt = select(func.count()).select_from(QcTaskItem).where(
        QcTaskItem.conversation_id == conversation_id,
        QcTaskItem.is_deleted.is_(False),
    )
    return int(self.db.execute(stmt).scalar_one())
```

**Repository 的组织方式**：没有做成 `BaseRepository[T]` 泛型基类，而是**按领域一个类**（`QcConversationRepository`、`UserRepository`、`OutboundTaskRepository`…），构造函数统一 `__init__(self, db: Session)`。理由是这个项目的查询高度领域化（软删除 + 租户 + 特定筛选组合 + 部分唯一索引语义），强行抽象基类反而会逼出 `**filters: object` 这种弱类型签名——项目中确实已经出现 `**filters: object` 与 `# type: ignore[arg-type]`（见 `list_paged` / `count`），这是**为换取灵活性而接受的类型损失**，属于已知取舍。

**软删除没有全局兜底**：`SoftDeleteMixin` 只提供 `is_deleted` / `deleted_at` / `mark_deleted()`，**没有** SQLAlchemy 的 `event` 或 `with_loader_criteria` 全局过滤器。每个 Repository 方法都要自己写 `is_deleted.is_(False)`。这是一个**可被面试追问的点**：好处是 SQL 完全显式（调试时不必猜"为什么查询被改写"），代价是**漏写就查到已删除数据**，靠代码规范 + 测试兜（`tests/api/test_soft_delete_index.py`）。

### 2.3 依赖注入链：认证 → 权限 → 租户范围

`api/deps.py` 的 docstring 写明这份契约是 **【基线冻结】** 的。链条是四段：

```
① get_token_payload(credentials = Depends(bearer_scheme))
     缺凭据 → Unauthorized（40101）
     decode_token(token, expected_type="access")
       · ExpiredSignatureError → Unauthorized("登录已过期，请重新登录")
       · PyJWTError          → Unauthorized("凭据无效")
       · type 不匹配          → Unauthorized("凭据类型不正确")   ← 用 refresh_token 访问也会被拦
     is_token_blacklisted(jti) → 已登出 → Unauthorized("登录已失效，请重新登录")
          ↓
② get_current_user(payload = Depends(get_token_payload), db = Depends(get_db))
     sub 转 int 失败 → Unauthorized("凭据无效")
     查库取 User → 不存在 → Unauthorized("用户不存在")
              → not is_active → Forbidden("账号已停用")（40301）
          ↓
③ require_permission(*codes)  ← 工厂函数，返回 _checker
     is_superuser → 直接放行（§59，操作仍被中间件记录）
     否则 permission_codes() 与 codes 取交集，任意命中即放行
     全不命中 → 日志 warning（含用户名 / 需要 / 拥有）+ Forbidden("缺少权限：a / b")
          ↓
④ tenant_scope_optional / tenant_scope_required（行级，见 §2.7）
```

**三个设计点值得单独讲**：

1. **`require_permission` 是工厂，不是普通依赖。** 它 `return _checker`，所以调用形式是 `Depends(require_permission("qc:task:list"))`。项目中它有**两种消费方式**：
   - `dependencies=[Depends(require_permission(...))]`——只做校验，不关心返回值（大多数接口）；
   - `current_user: User = Depends(require_permission(...))`——既要校验又要拿当前用户（如"我的质检工作台"、案例创建）。
   后者是前者的超集，两种混用是刻意的：不需要用户对象的地方就不引入变量。

2. **超管短路放在 `require_permission` 里而不是 `get_current_user` 里。** 因为超管的"全权限"语义只对权限校验成立，对认证不成立——超管一样要有效 token、一样要 `is_active=True`。放错位置会导致超管绕过认证。

3. **每次请求都查库，没有权限缓存。** `get_current_user` 每次都 `UserRepository.get_by_id`；`permission_codes()` 遍历 `user.roles → role.permissions`，两级关系都是 `lazy="selectin"`（预加载，避免 N+1），但仍是**每请求至少 3 条 SQL**（用户 / 角色 / 权限）。这是 MVP 的取舍：换来"改权限立刻生效、不需要失效缓存"。如果要做缓存，失效点会落在角色变更 / 用户停用两处。

### 2.4 统一响应与业务码

**响应体**（`core/response.py`）：

```python
class ApiResponse(BaseModel, Generic[T]):
    code: int = Field(default=0, description="业务码，0 表示成功")
    message: str = Field(default="success", description="提示信息")
    data: T | None = Field(default=None, description="业务数据")

class PageData(BaseModel, Generic[T]):
    items: list[T]; total: int; page: int; page_size: int
```

辅助函数 `ok(data, message="success")` / `fail(code, message, data=None)` / `page_data(items, total, page, page_size)` 直接返回 dict——**它们不是为了类型正确，而是为了让每个 Router 的返回写法完全一致**（全部 `return ok(...)`）。

**业务码与 HTTP 状态码解耦**（这是面试高频点）：

| 业务码 | 枚举 | HTTP | 语义 | 抛出点 |
|---|---|---|---|---|
| 0 | `SUCCESS` | 200 | 成功 | — |
| 40001 | `PARAM_ERROR` | 400 | 参数错误 / 校验失败 | `ParamError`、`RequestValidationError` |
| 40101 | `UNAUTHORIZED` | 401 | 未登录 / 过期 / 已登出 / 凭据类型错 | `Unauthorized` |
| 40301 | `FORBIDDEN` | 403 | 无权限 / 账号停用 / 越权租户 | `Forbidden` |
| 40401 | `NOT_FOUND` | 404 | 数据或路由不存在 | `NotFound`、`StarletteHTTPException(404)` |
| 40901 | `CONFLICT` | 409 | 唯一约束冲突 | `Conflict` |
| 40902 | `STATE_NOT_ALLOWED` | 409 | 当前状态不允许该操作 | `StateNotAllowed` |
| 40903 | `NUMBER_EXHAUSTED` | 409 | 外呼号码次数耗尽 | `NumberExhausted` |
| 40904 | `RESOURCE_REFERENCED` | 409 | 被引用，禁止编辑/删除 | `ResourceReferenced` |
| 50000 | `SYSTEM_ERROR` | 500 | 未处理异常（兜底） | `AppException` 基类 / `Exception` |

**为什么 409 有三个码**：HTTP 409 只能表达"冲突"，但前端需要的处理完全不同——40901 提示"名称重复"、40902 提示"当前状态不允许，请刷新后重试"、40903/40904 提示"号码用完了 / 被引用了不能删"。**业务码是给前端的语义槽位，HTTP 状态码是给网关/监控的**。前端 Axios 拦截器就是按 `body.code !== 0` 统一弹 `ElMessage.error(message)`。

**异常体系**（`core/exceptions.py`）：`AppException` 子类通过**覆盖类属性**（`code` / `http_status` / `message`）定义语义，构造时可选传 `message` 覆盖默认值：

```python
class StateNotAllowed(AppException):
    code = int(BizCode.STATE_NOT_ALLOWED)   # 40902
    http_status = 409
    message = "当前状态不允许该操作"
```

好处是：Service 层 `raise StateNotAllowed("对话已被质检引用，禁止删除")` 只关心业务语义，**不需要知道 HTTP 状态码和数字业务码**。

**四个全局异常处理器**（`main.py`）覆盖全部出口：

| handler | 触发 | 返回 |
|---|---|---|
| `AppException` | Service 主动抛的业务异常 | `exc.http_status` + `fail(exc.code, exc.message)`，同时 `logger.warning` 记路径与码 |
| `RequestValidationError` | Pydantic/FastAPI 入参校验失败 | 400 + 40001，`data` 里带 `[{field, msg}]` 列表（把 `loc` 用 `.` 拼成 `field`） |
| `StarletteHTTPException` | 404 路由未命中 / 405 等 | `_STATUS_TO_CODE` 映射（400/401/403/404/409），**未命中落 50000** |
| `Exception` | 未预期异常 | 500 + 50000 + "系统异常，请稍后重试"，`logger.exception` 记栈 |

**注意 `RequestValidationError` 的处理是本项目的额外价值**：FastAPI 默认返回 422 + 一坨 `detail` 数组，而这里被改写成 **400 + 40001 + 结构化 `data`**，与其它错误体格式一致。测试 `test_login_missing_field_returns_param_error` 就是钉这个行为的。

### 2.5 Pydantic v2 入参校验

**Schema 组织**：按域分目录（`schemas/auth.py`、`schemas/outbound/*`、`schemas/qc/*`），每个域有公共基类：

```python
class OutboundSchemaBase(BaseModel):
    model_config = ConfigDict(from_attributes=True)      # 允许 ORM 对象直接构造出参

class OutboundOutBase(OutboundSchemaBase):
    id: int; created_at: datetime; updated_at: datetime   # 出参统一带主键与时间戳

class OutboundUpdateBase(OutboundSchemaBase):
    model_config = ConfigDict(from_attributes=True, extra="forbid")  # 更新入参禁止多传字段
```

| v2 特性 | 项目用法 | 意图 |
|---|---|---|
| `ConfigDict(from_attributes=True)` | 所有出参基类 | 出参可由 ORM 对象 `model_validate` 直接构造（`get_detail` 里就是这么用的） |
| `ConfigDict(extra="forbid")` | 所有 Update 基类 | 前端多传字段直接 40001，**防止静默忽略拼错的字段名** |
| `Field(min_length / max_length / ge / gt / pattern)` | 入参全面使用 | 边界校验声明在类型上，同时进 OpenAPI 让前端可见 |
| `field_validator` | 仅 2 处：`display_name` 去空白、回呼 `phone` 去空白 | 只用于"类型系统表达不了"的规则（trim 后不能为空） |
| `model_dump(exclude_unset=True)` | 更新语义 | **只更新显式传入的字段**——PATCH 式语义 |
| `model_dump(exclude={...})` | 创建时剔除嵌套字段 | 如 `payload.model_dump(exclude={"messages"})` 再单独处理消息 |
| `BaseModel, Generic[T]` | `ApiResponse[T]` / `PageData[T]` | 泛型响应体，`ApiResponse[PageData[ConversationOut]]` 直接成为 `response_model` |
| 枚举字段 | `channel: ConversationChannel \| None` | 非法值在校验层就被拦，进 Service 的一定是合法枚举 |

**`field_validator` 只用了两处**，这是刻意的克制——大部分约束能靠 `Field` + 类型 + `Literal/Enum` 表达，加 validator 会让 OpenAPI 的 schema 变得不透明（前端看不到规则）。只有"trim 后不能为空"这类**需要变换再判断**的规则才写 validator。

**`PageParams` 不是 BaseModel，是普通类**（`schemas/common.py`）：

```python
class PageParams:
    def __init__(
        self,
        page: int = Query(default=1, ge=1, description="页码，从 1 开始"),
        page_size: int = Query(default=settings.DEFAULT_PAGE_SIZE, ge=1, le=settings.MAX_PAGE_SIZE),
    ) -> None: ...
    @property
    def offset(self) -> int: return (self.page - 1) * self.page_size
    @property
    def limit(self) -> int: return self.page_size
```

用 `Depends()` 注入（`page: PageParams = Depends()`）。它同时做了三件事：**校验边界**（`ge=1`、`le=MAX_PAGE_SIZE`）、**算 offset**（避免每个 Service 重复 `(page-1)*size`）、**把上限写进 OpenAPI**（前端能直接看到 `page_size ≤ 200`）。默认 20 / 上限 200 来自 `settings.DEFAULT_PAGE_SIZE` / `MAX_PAGE_SIZE`。

**一个真实踩过的类型坑**：更新语义用 `model_dump(exclude_unset=True)` 时，字段类型是 `X | None`，导致 `**changes` 传给 repo 后类型推断不精确——项目里出现了 `params as unknown as Record<string, unknown>`（前端 TS 侧）与 `**filters: object` + `# type: ignore[arg-type]`（后端）两处**为换取动态字段更新而接受的类型损失**。

### 2.6 OpenAPI 自动生成

FastAPI 本身会依据 `response_model` + Pydantic 模型 + `Path/Query/Header/Body` 声明自动生成 OpenAPI。本项目在此基础上做了两件额外的事：

**① 覆盖 `app.openapi` 注入 examples**（`main.py::custom_openapi` + `core/openapi_examples.py`）：

```python
def custom_openapi() -> dict[str, Any]:
    if app.openapi_schema:
        return app.openapi_schema          # 只生成一次并缓存
    schema = get_openapi(title=..., version=..., routes=app.routes)
    apply_examples(schema)                 # 统一注入 examples
    app.openapi_schema = schema
    return schema

app.openapi = custom_openapi
```

`apply_examples()` 的策略是**两层兜底**：
- `REQUEST_EXAMPLES`：**手写**的请求体示例，按组件名登记（如 `OutboundTaskCreate` 给出一个 9 月新客回访任务的完整 JSON，含 `numbers` 数组），贴近真实业务、可直接在 Swagger UI 试调用；
- `build_example()`：**自动生成**其余组件的占位示例——按 `$ref` 递归（限深 3 层防自引用死循环）、`enum` 取首值、`format=date-time/date/email` 给固定样例、按字段名查 `_STRING_HINTS`（`phone → 13800000001`）、模型自带 `example`/`default` 优先。**保证"每个接口都有 examples"**。

**② 用测试守门文档质量**（`tests/test_openapi_docs.py`）：这是一份"规范测试"，把 §58 的要求变成断言——

- `test_operations_exist`：外呼前缀下 operation 数 `> 100`；
- `test_every_operation_has_summary_and_description`：**每个** operation 都必须有 summary 与 description；
- `test_every_operation_declares_security`：每个 operation 都要有 `security`，**例外仅 `×/call-result/callback`**（网关回调按签名鉴权，不走路由认证）；
- `test_every_response_has_examples` / `test_every_request_body_has_examples`：200 响应与 JSON 请求体都要有 examples（`requestBody` 检查数 `>= 30`，文件上传 multipart 除外）；
- `test_all_referenced_components_have_examples`：从 operation 里正则捞出所有 `$ref`，被引用到的组件**必须**有 examples；
- `test_examples_are_json_serializable`：示例必须能 `json.dumps`，防止写进不可序列化对象。

**这份测试的意义**：以后新增接口忘了补 summary/examples，CI（提交前跑 pytest）会直接红，而不是等到前端问"这个接口怎么调"。

### 2.7 表级权限与行级权限

**表级权限（能不能进这个接口）**——RBAC 5 表（`users` / `roles` / `permissions` / `user_roles` / `role_permissions`）+ 权限码目录：

- 权限码的**唯一来源**是 `core/permissions.py`（`_p()` 外呼 40 条 + `_q()` 质检 23 条 = **63 条**），`scripts/init_db.py` 幂等同步入库；
- 路由上用 `Depends(require_permission("qc:task:dispatch"))` 声明；
- `require_permission` 支持**多码取或**（`require_permission("a", "b")` 命中任一即放行）。

**行级权限（能看哪几行）**——租户范围收敛：

```python
def _resolve_tenant_scope(current_user: User, tenant_id: int | None) -> int | None:
    """把入参 tenant_id 收敛为「该用户实际可访问的租户」（ASSUMPTION-058）"""
    if current_user.is_superuser or current_user.tenant_id is None:
        return tenant_id                       # 超管 / 平台账号：不限租户
    if tenant_id is not None and tenant_id != current_user.tenant_id:
        logger.warning("越权访问租户数据：...")
        raise Forbidden("无权访问其他租户的数据")
    return current_user.tenant_id               # 绑定用户：强制收敛到自己租户
```

三条规则的语义（有测试逐条钉死，见 `tests/api/test_tenant_scope.py`）：

| 用户类型 | 传 tenant_id | 不传 tenant_id |
|---|---|---|
| 超级管理员 | 可以查该租户 | 不限租户（查全部） |
| 绑定租户的普通用户 | **只能传自己的**，传别的 → 403/40301 | 自动收敛到自己租户 |
| 未绑定租户的普通用户（平台账号） | 可以查该租户 | 不限租户 |

两个依赖的差别只在"必填 / 可选"：`tenant_scope_required` 用于**必须确定租户**的接口（如实时监控快照、IVR 流程下拉），`tenant_scope_optional` 用于列表接口。

**必须说清的边界**（§0 事实 3）：行级隔离**没有全局强制**。链路是「路由声明依赖 → Service 透传 → Repository `if tenant_id is not None` 才过滤」。三处任何一处缺失，隔离就失效且**不会报错**。目前的事实是：

- 依赖链一侧：外呼 + 质检的路由**都声明了**租户依赖（`tenant_scope_optional` / `required` 在 api 层有 40+ 处使用）；
- Repository 一侧：过滤条件在 `_apply_filters` / `_apply_batch_filters` 里统一处理；
- 但**没有**"所有列表接口必须带租户依赖"的自动化校验，也没有 SQLAlchemy 层的租户强制。要补的话，最合适的守门位置是像 `test_openapi_docs.py` 那样写一个规范测试：**扫描所有返回 `PageData[...]` 的 operation，断言其参数里存在 `tenant_id`**。

`app/utils/masking.py` 全文只有两个纯函数：

```python

    """手机号脱敏：13812341234 -> 138****1234"""
    # 长度 ≤ 7 时整体打码；否则 前 3 + **** + 后 4

def mask_id_card(id_card: str | None) -> str:
    """身份证脱敏：保留前 6 位与后 4 位"""

```

**§67 的原始要求是"日志中禁止出现完整手机号 / 身份证号"**。现状核查结论：

| 检查项 | 事实 |
|---|---|
| 脱敏函数是否存在 | 存在，含空值/短串/正常串三类分支，函数语义清晰 |
| 是否有单测 | 有，`tests/unit/test_masking.py`（6 个用例：正常 / 短串 / 空串 / None） |
| 是否有生产调用点 | **没有**。全仓库 grep `mask_phone｜mask_id_card`，命中的只有"定义处"与"测试处" |
| 日志里有没有泄露完整手机号 | 当前**没有**。`logger` 调用里出现的"号码"都是业务文案（如"回呼失败：无可用主叫号码 task=%s"），没有把 `phone` 变量本身打进日志 |

**要接的话，最小改动是两处**：① 在需要记录号码的日志/响应处显式调用 `mask_phone()`；② 更稳的做法是在 `core/logging.py` 加一个 `logging.Filter`，对已知敏感字段名做兜底擦除，让脱敏从"靠人记得调"变成"框架层兜住"。这两条都**未实施**。

### 2.9 操作审计日志

两张互不重叠的表（`models/log.py`）：

| 表 | 记录什么 | 谁写 | 触发时机 |
|---|---|---|---|
| `login_logs` | 登录成功/失败、用户名、IP、UA、失败原因 | `AuthService._write_login_log` | 登录成功、密码错、用户不存在、账号停用 |
| `operation_logs` | 谁对什么路径方法做了什么、结果、耗时、IP、UA | `main.py::operation_log_middleware` | **非 GET/HEAD/OPTIONS** 且路径在 `/api/v1` 下，且不是 `/auth/login` |

**`login_logs` 有一个很关键的实现细节**：失败日志必须**独立提交**。

```python
if user is None or not verify_password(password, user.password_hash):
    self._write_login_log(None, username, ip, user_agent, False, "用户名或密码错误")
    self.db.commit()                       # ← 必须显式提交
    raise Unauthorized("用户名或密码错误")   # ← 抛出后 get_db 会 rollback
```

因为 `get_db()` 在异常路径上会 `rollback()`，如果失败日志只 `add` 不 `commit`，它就会**跟着异常一起被回滚掉**——"登录失败"这个最需要审计的事件反而没了记录。测试 `test_failed_login_writes_log` / `test_unknown_user_login_writes_log` / `test_inactive_user_login_writes_log` 就是钉这一点。

**`operation_logs` 的中间件设计**（`main.py`）：

```python
@app.middleware("http")
async def operation_log_middleware(request: Request, call_next):
    start = time.perf_counter()
    response = await call_next(request)                 # 先让请求跑完（拿到真实状态码与耗时）
    should_log = (
        request.method not in _SAFE_METHODS             # GET/HEAD/OPTIONS 不记
        and path.startswith(settings.API_V1_PREFIX)     # 只管业务接口，/health 等不记
        and not path.endswith(_LOGGED_SKIP_PATHS)       # /auth/login 不记（已由 login_logs 覆盖）
    )
    if should_log:
        duration_ms = int((time.perf_counter() - start) * 1000)
        try:
            await run_in_threadpool(_write_operation_log, request, response.status_code, duration_ms)
        except Exception:
            logger.exception("写入操作日志失败 %s %s", request.method, path)   # 审计失败不影响业务
    return response
```

四个设计取舍：

1. **只在写操作上记**（`_SAFE_METHODS` 白名单）：读操作量级大、审计价值低，记全量会把日志表撑爆。
2. **`run_in_threadpool` 而不是直接同步写**：中间件跑在事件循环上，同步 DB 写会阻塞整个事件循环。扔进线程池后，写日志不阻塞其它请求。
3. **写日志失败只记异常、不抛**：审计不能反过来把业务打挂（`except Exception` 兜住）。
4. **`user_id` 从 `authorization` 头自己解 JWT**：中间件里拿不到 `Depends` 注入的 `current_user`，所以用 `decode_token` 直接解；解不开就 `None`（例如公开接口）。`username` 则是**写完前再回查一次用户表**补齐——因为 JWT 里只有 `sub`（user_id），没有用户名。

**超管操作同样记录**（§59 / §70）：`require_permission` 对超管短路放行，但**不放行中间件**——所以超管的写操作一样进 `operation_logs`。

**未使用的字段**（§0 事实 4）：`operation_logs` 定义了 `target_type` / `target_id` / `request_id` / `detail`，中间件**没有填充**。要补 `target_id` 需要 Router/Service 主动告知（例如把路径参数写进 `request.state`），属于"知道怎么做但当前没做"的扩展点。

## 第三部分 · 面试问答

### A. FastAPI 与 ASGI（10 题）

**A1. 为什么选 FastAPI，而不是 Django / Flask？**
三层原因：① **自带 OpenAPI**——本项目的接口文档要求是硬性的（§58 要求每个 operation 都有 summary/description/response_model/examples），Django 要额外接 drf-spectacular、Flask 要接 flasgger，FastAPI 是框架内建；② **Pydantic 校验是类型驱动的**——入参约束写在类型上，同时用于校验和生成文档，一处定义两处生效；③ **依赖注入够用且轻**——本项目要的 DI 就是"会话 / 当前用户 / 权限 / 租户范围 / 分页参数"这五类，`Depends` 的工厂函数模式（`require_permission(*codes)` 返回 checker）正好够，不需要 Spring 那样的容器。

**A2. ASGI 与 WSGI 的区别，以及为什么它和"中间件写日志不能阻塞"有关？**
WSGI 是同步接口，一个 worker 同一时刻只能处理一个请求；ASGI 是异步接口，单 worker 可以在等待 I/O 时切去处理别的请求。本项目的数据库访问是**同步 SQLAlchemy**，FastAPI 对同步 `def` 端点会自动丢进线程池执行——所以业务本身不阻塞事件循环。但**中间件是 `async def`，跑在事件循环上**，如果我直接在里面做同步 DB 写，会把整个事件循环卡住。这就是为什么 `_write_operation_log` 必须经 `run_in_threadpool` 调用。

**A3. `lifespan` 是什么？为什么不用 `@app.on_event("startup")`？**
`lifespan` 是一个 `asynccontextmanager`，进入时执行启动逻辑、退出时执行关停逻辑。本项目用它做三件事：`get_redis()` 预热（Redis 挂了也只是降级，不阻断启动）、`start_scheduler()` 启动 APScheduler、`shutdown_scheduler()` 关停。相比 `on_event`，`lifespan` 的启动/关停逻辑写在**同一个函数里**，共享同一套资源清理路径，不会出现"启动写了、关停忘了"的问题（且 `on_event` 已在新版被标记为废弃）。

**A4. `response_model` 有什么用？它和直接 `return dict` 有什么区别？**
`response_model` 做了三件事：① **过滤多余字段**——ORM 对象里有 `password_hash` 之类，甚至有时会把不该出的字段序列化出去，`response_model` 是白名单；② **校正类型**——输出会被 Pydantic 再校验一遍，DateTime/Enum 序列化一致；③ **生成 OpenAPI schema**——`ApiResponse[PageData[ConversationOut]]` 直接进文档。本项目所有接口都写 `response_model=ApiResponse[X]`，而函数返回的是 `ok(...)` 这个 dict——**dict 是数据、response_model 是契约**，两者配合：写作自由，出口受控。

**A5. `HTTPBearer(auto_error=False)` 为什么要关掉自动报错？**
因为 FastAPI 默认在缺 Bearer 凭据时直接返回 **403**，但本项目的契约是**统一 401/40101**（前端 Axios 拦截器按 401 做统一登出跳转）。关掉 `auto_error` 后，缺凭据时 `credentials is None`，由 `get_token_payload` 主动 `raise Unauthorized()`，于是所有"没登录"的出口都收敛到 401 + 40101。这是"框架默认行为与项目契约冲突时，以契约为准"的例子。

**A6. 路由聚合为什么有顺序要求？**
两个真实踩坑：① **带 `{id}` 的动态段会吞掉同层静态路径**——所以 `router.py` 里质检模块**先挂静态路径**（专家组/任务/报表/案例库），**再挂带 `{id}` 的执行域**，并写了注释说明原因；② **同一文件内路径顺序**——`/qc/conversations/import`、`/import-batches` 必须声明在 `/{conversation_id}` **之前**，否则 `/import` 会被当成 `conversation_id="import"` 命中详情接口，然后在 int 转换处报 422。这不是 FastAPI 的 bug，是 path 匹配本身的特性。

**A7. 中间件和依赖注入，分别适合放什么逻辑？**
中间件适合**对所有请求一视同仁、且不依赖具体业务参数**的横切逻辑——本项目的操作日志就是这样（不分领域、只按方法与路径前缀决定记不记）。依赖注入适合**需要在函数签名里拿到结果**的逻辑——会话、当前用户、权限码、租户范围、分页参数都是要在函数体里用的值。判断标准：**"我需要把这个东西传给业务函数吗？"** 需要 → 依赖；不需要（只管记录/统计）→ 中间件。

**A8. 为什么用 `run_in_threadpool` 而不是 `asyncio.to_thread`？**
两者都能把同步函数扔到线程池，但 `run_in_threadpool` 用的是 **AnyIO 的线程池**，与 Starlette/FastAPI 自己的线程池是同一套——同步端点执行、`run_in_threadpool`、后台任务共享同一个池，不会出现"另起一套池导致线程数翻倍"。`asyncio.to_thread` 用的是默认 executor，与本框架的池分离。

**A9. 全局异常处理器里，`_STATUS_TO_CODE` 映射不到的 HTTP 状态码怎么处理？**
落 `SYSTEM_ERROR = 50000`。`_STATUS_TO_CODE` 显式映射了 400/401/403/404/409 五个，其余（如 405、415）走 `dict.get(status_code, 50000)`。这个设计的好处是**兜底不丢信息**：即使映射不到，响应体格式仍然是统一的 `{code, message, data}`，前端拦截器仍然能统一处理（不会遇到"格式不对解析失败"）。

**A10. `app.openapi` 被覆盖后为什么还要缓存 `openapi_schema`？**
因为生成 OpenAPI 涉及遍历所有路由、解析所有 Pydantic 模型，成本不低；而 `/openapi.json` 会被 Swagger UI、前端代码生成器、测试反复请求。`if app.openapi_schema: return app.openapi_schema` 让文档只生成一次。注意副作用：**开发时改了 schema 需要重启进程才能看到新文档**——这是这个缓存的代价。

### B. 三层架构与职责边界（9 题）

**B1. 三层架构的边界是怎么在代码里落地（而不是写在文档里的）？**
靠**四个文件的第一行 docstring**把它变成可核对的事实：`repositories/__init__.py` 写"只负责 SQLAlchemy 查询，禁止写业务规则/权限/状态机"、`api/deps.py` 写"鉴权契约在此定义，只允许调用禁止修改"、`db/session.py` 写"事务由 Service 层控制，Router 不碰事务"、各 Service 类写"事务在本层提交"。另外有**结构性证据**：随便打开一个 Router 函数，函数体通常只有 1～2 行（取参 → 调 Service → `return ok(...)`）。

**B2. 为什么 Repository 不做成泛型基类 `BaseRepository[T]`？**
本项目的查询高度领域化——软删除必过滤、租户可选过滤、部分唯一索引语义、大量特定筛选组合。做成泛型基类要么把所有参数塞进 `**kwargs`（类型全丢），要么给每个领域写一堆只在基类里"挂名"的方法。项目选择了**按领域一个 Repository 类 + 统一 `__init__(self, db)`**，对象方法语义清晰、可以直接 Ctrl+点进去读 SQL。代价是公共动作重复（`is_deleted.is_(False)` 反复写），这个代价被显式接受。

**B3. Service 层怎么保证"事务边界正确"？**
关键是 Service 是**唯一决定 commit 时机的地方**。三种典型决策：① **四步一起提交**——质检提交（写结果 → 改明细状态 → 任务完成数自增 → 条件完成）必须原子；② **逐条提交**——超时回收每条记录独立，一条失败不该连坐其它条，所以 `with session_scope()` 每条一个事务；③ **整批提交**——回呼派单 `dispatch_due` 扫一批后整批 commit（单条失败 `try/except` 跳过，不影响整批）。`get_db()` 的正常路径**不 commit**（只在异常时 rollback），正是为了把提交权交给 Service。

**B4. 请求级会话 `get_db()` 和非请求级 `session_scope()` 为什么要分开？**
因为在 FastAPI 依赖体系之外（定时任务、中间件、脚本）拿不到 `Depends` 注入的会话。如果硬用 `get_db()`，那些场景就得自己写 try/commit/rollback/close 样板。`session_scope()` 用 `@contextmanager` 把「yield → 自动 commit → 异常 rollback → finally close」封成 with 语句，让定时任务里每条记录回收都写成 `with session_scope() as db:`，错误处理不可能漏写。**接口一致、语义不同**：请求级交给 Service 决定提交，非请求级默认提交。

**B5. 软删除为什么不用 SQLAlchemy 全局过滤器？**
`SoftDeleteMixin` 只提供字段与 `mark_deleted()`，没有用 `with_loader_criteria` 或 `event.listen` 做全局改写。取舍是：**显式 SQL 的可调试性 vs 漏写的风险**。全局过滤器一旦有例外（比如"回收站需要查已删除数据"），就得开 `execution_options` 逃生口，反而更绕。本项目选显式，风险由"每个查询都写 `is_deleted.is_(False)`"的规范 + `test_soft_delete_index.py` 兜。**面试时应该主动承认代价**：这是靠纪律而不是靠机制保的，纪律会疲劳。

**B6. 同一份业务规则被多处触发时怎么不重复？**
规则写在 Service，Router / 定时任务 / 导入流程都调同一个 Service 方法。举例：`QcReviewService.recycle_timeout_items()` 既被定时任务调用，也可以在测试里直接调；`_rewrite_asr_messages` 只存在于 `QcTranscribeService`。**判断规则该不该进 Service 的标准是"它会不会被第二个入口用到"**——会，就必须进 Service；不会（纯 HTTP 层的东西，如解析 `X-Forwarded-For`），就留在 Router/deps。

**B7. 前端 `Model` 和后端 Schema 是什么关系？**
后端的 `schemas/**` 是**唯一契约来源**：它同时产出三样东西——入参校验规则、OpenAPI 文档、前端可读的字段与类型。前端 TypeScript 类型应当与后端 Schema 一一对应（项目里通过 `utils/echarts.ts`、页面类型定义手工对齐）。这里有一个真实的对齐坑：后端聚合列名是 `pass`（Python 里 `pass` 是保留字，只能用字符串列名），TS 侧就改名为 `pass_count`，页面里再用 `passOf()` 收敛读取——**字段名不能跨语言直接对齐时，用一层映射函数而不是到处写 `as any`**。

**B8. 如果要在所有列表接口强制租户隔离，你会怎么做？**
三步：① **守门测试**——像 `test_openapi_docs.py` 那样写规范测试，扫描所有返回 `PageData[...]` 的 operation，断言其参数里含 `tenant_id`（缺了就红）；② **Repository 收敛**——把所有 `_apply_filters` 的租户判断挪进一个公共函数，避免各写一遍；③ 如果要更强，用 SQLAlchemy `with_loader_criteria` 按上下文变量注入租户条件。**现状是①③都没做**（见 §2.7），所以正确的回答是"我知道这个洞，也说了补法，但当前没补"。

**B9. 三层架构在这个项目里最明显的一次收益是什么？**
**排队取号的并发正确性只需要在一处保证**。号码扣减的原子性（`INSERT…SELECT` + `ON CONFLICT` + `UPDATE` 条件扣减）全部落在 Repository + Service，接口层完全不需要知道"有没有并发问题"；反过来说，测试里那个真并发用例（`ThreadPoolExecutor` 8 线程 × 24 次扣减，断言恰好成功 5 次）调的就是 Service/Repository 的方法，**不需要构造 HTTP 请求**。分层让"并发正确性"可被独立验证。

### C. 依赖注入与认证授权（11 题）

**C1. 完整描述一次带鉴权的请求，用户信息是怎么一步步被拿到的？**
四段链：① `bearer_scheme`（`HTTPBearer`）从头里取出 `Bearer xxx`；② `get_token_payload` 用 `decode_token(token, expected_type="access")` 解 JWT（校验签名、`exp`、`type`），并查 Redis 黑名单确认未被登出；③ `get_current_user` 把 `sub` 转成 int 后查库，确认用户存在且 `is_active`；④ `require_permission(*)` 用超管短路或权限码交集做授权。这四段是 `Depends` 层层嵌套，**FastAPI 保证同一请求内每个依赖只执行一次**（同名依赖会被缓存复用）。

**C2. 为什么 `require_permission` 要做成返回函数的工厂？**
因为它需要**接收参数**（要校验哪些权限码）。`Depends` 的机制是"调用传入的可调用对象"，所以需要校验 `qc:task:list` 时，得先造出一个"知道要校验哪些码"的 checker 函数再交给 `Depends`。这是 FastAPI 里实现"带参数的依赖"的标准手法：`def require_permission(*codes) -> Callable[..., User]` 返回闭包 `_checker`。

**C3. 超管为什么在 `require_permission` 里直接放行，而不是给超管分配所有权限？**
两个理由：① **语义更准**——超管的"全权限"是**身份属性**，不是数据里的角色分配，落成数据会在权限码新增时失同步（新码没分给超管，超管立刻缺权限）；② **性能**——超管放行在 `permission_codes()` 之前短路，省掉一次角色/权限查询。放行点必须在 `require_permission` 而**不能**在 `get_current_user`：超管一样要过认证（有效 token、账号启用）。

**C4. 为什么认证失败分 401 和 403 两种？**
401（未认证，`40101`）= "我不知道你是谁"：缺 token、token 过期、token 类型不对（拿 refresh 当 access 用）、已登出、用户不存在。403（已认证但无权，`40301`）= "我知道你是谁，但你不能干这个"：权限码不足、账号停用、越权访问其它租户。**这个区分对前端很关键**：401 要触发登出并跳登录页；403 只提示"无权限"，**不应**清 token。项目测试里 `test_me_without_token → 401`、`test_conversation_list_requires_permission → 403`、`test_login_inactive_user → 403`（账号停用是"已知道你是谁但你不能用"）就是按这个语义分的。

**C5. `decode_token` 的 `expected_type` 参数解决了什么问题？**
防止**令牌混淆**：refresh_token 的有效期长得多（7 天 vs 30 分钟），如果能拿去调业务接口，等于把短命凭据换成了长命凭据。`get_token_payload` 传 `expected_type="access"`，`AuthService.refresh` 传 `expected_type="refresh"`，互不通用。测试 `test_me_with_refresh_token_rejected` 与 `test_refresh_with_access_token_rejected` 双向都钉了。

**C6. 登出为什么用 Redis 黑名单而不是删 token？**
JWT 是**无状态**的——服务端不存 token，签发后无法"撤回"。要做到登出即刻失效只有两条路：① 服务端存 session（有状态，放弃 JWT 的优点）；② **黑名单**（只存"已失效的 jti"，是白名单的补集，量小）。本项目选②：`blacklist_token(jti, ttl)` 用 `SETEX` 写入，TTL 取 refresh 的最长有效期（`_REFRESH_TTL_SECONDS = 7 天`），因为 token 自己会过期，黑名单只需覆盖到它自然过期即可，**黑名单天然自清理，不会无限增长**。

**C7. Redis 挂了会怎样？这是设计缺陷吗？**
会**降级为放行**：`is_token_blacklisted` 在 Redis 不可用时 `return False`，意味着登出过的 token 在过期前仍可用（`blacklist_token` 也返回 False 并只记 warning）。这是**明确的可用性优先**取舍——如果反过来（Redis 挂了就全拒），一次 Redis 抖动会让整个平台所有人都登录不了。代价是"登出后短时间窗口内 token 仍可用"。测试对此如实处理：`@pytest.mark.skipif(not cache_available(), ...)` 明确承认"Redis 不可用时这个用例无意义"。

**C8. `get_current_user` 每请求查库，如果要做缓存你会怎么做？**
缓存 key 用 user_id，value 放（用户基础信息 + 权限码集合），TTL 设短一点（如 60s）或改为**主动失效**：在"角色权限变更 / 用户停用 / 用户改角色"三处 `DEL` 掉对应 key。本项目**没做缓存**，理由写在取舍上：MVP 阶段请求量不大，而权限变更必须立刻生效（安全属性），缓存失效点越多越容易漏。要做的话我会先确认"权限变更入口是否唯一"，不唯一就宁可短 TTL 也不做主动失效。

**C9. 依赖里 `db: Session = Depends(get_db)` 和 `current_user: User = Depends(get_current_user)` 用同一个会话吗？**
是的。`get_current_user` 自己声明了 `db: Session = Depends(get_db)`，FastAPI 在同一请求内对**同一个依赖函数**会缓存结果，所以 `get_current_user` 里的 db 和路由函数里注入的 db **是同一个 Session 对象**。这很重要——否则 `current_user` 会属于另一个会话，改动它（`user.last_login_at = ...`）不会随路由的提交一起生效（甚至可能触发 detached 错误）。

**C10. 权限码为什么集中在 `core/permissions.py`，而不是散在各个接口上？**
因为权限码要被**三方共用**：`init_db` 落库、API 依赖校验、前端菜单/按钮控制。散在接口上会出现三类漂移：拼写不一致（`qc:task:dispatch` vs `qc:task:dispath`）、新增权限码忘了入库（导致 403 永远过不了）、前端菜单用了库里没有的码。集中定义后，`tests/api/test_qc_permissions.py::test_permission_catalog_matches_expected` 还能断言"目录无重复、module 正确、全量目录 == 外呼 + 质检"。

**C11. `get_client_ip` 为什么要读 `X-Forwarded-For`？**
因为生产环境前面有 Nginx / 负载均衡，`request.client.host` 拿到的是**代理 IP**，不是真实客户端 IP。`X-Forwarded-For` 是代理链写入的，取**第一段**（最左边的原始客户端）才是真实来源。这在审计日志里很关键——`operation_logs.ip` 和 `login_logs.ip` 都靠它。注意它的安全边界：`X-Forwarded-For` 是**可伪造的头**，只有在"确定入口代理会重写该头"的前提下才可信；项目当前没有校验可信代理，属于已知边界。

### D. 统一响应 / Pydantic v2 / OpenAPI（10 题）

**D1. 统一响应体的 `{code, message, data}` 和 HTTP 状态码是什么关系？**
**解耦、各司其职**：HTTP 状态码给基础设施（网关、监控、负载均衡、K8s 探活）看，业务码给前端业务逻辑看。同一个 HTTP 409 下有三个业务码（40901 冲突 / 40902 状态不允许 / 40903 号码耗尽），因为前端处理完全不同——40901 提示"名称已存在"、40902 提示"当前状态不允许请刷新"、40903 引导"号码用完了"。反过来，成功一律 200（不用 201/204），因为 `code=0` 已经承载了成功语义，前端只判断一处。

**D2. 为什么不用 HTTP 状态码表达全部语义？**
因为状态码是**有限且语义固定**的（RFC 定义），而业务错误是**无限**的。用 4xx 表达所有业务错误必须编码（比如 40901 只能塞进 409），前端就得解析 message 字符串来判断，脆弱且难国际化。业务码是"给机器的稳定标识"，message 是"给人的提示"，两者分离。

**D3. `AppException` 用类属性定义 code/status，有什么好处和风险？**
好处：Service 层 `raise StateNotAllowed("对话已被质检引用，禁止删除")` 完全不用知道 HTTP 码和数字码，**业务语义与传输语义分离**；新增错误类型只需加一个类。风险有两个：① **继承层次不能太深**——谁覆盖了 `code` 要能一眼看到，本项目是一层继承（`AppException` → 具体异常），够平；② **`message` 可被覆盖**，所以日志里必须同时记 `code`（`logger.warning("业务异常 %s %s -> %s(%s)", ...)` 里带 code），否则同类错误的不同文案会看起来像不同错误。

**D4. FastAPI 默认的 `RequestValidationError` 是 422，为什么改成 400 + 40001？**
为了**格式统一**。默认 422 返回 `{"detail": [{"loc": [...], "msg": ..., "type": ...}]}`，是一个跟 `{code, message, data}` 完全不同的结构——前端拦截器要么写两套解析，要么统一响应体这个设计就白做了。改成 400 + 40001 后，`data` 里放结构化的 `[{field, msg}]`（把 `loc` 用 `.` 拼成 `body.username` 这种路径），前端既能统一提示，又能做字段级定位。

**D5. Pydantic v2 相比 v1 有哪些在本项目里用到的变化？**
最直接的三处：① **`ConfigDict` 替代内部 `class Config`**——`model_config = ConfigDict(from_attributes=True, extra="forbid")`，配置项成了可合并的字典，所以能做"基类定通用配置、子类追加"；② **`model_validate` 替代 `from_orm`**、`model_dump` 替代 `dict()`——Orum→Schema 转换统一入口（`ConversationOut.model_validate(conversation)`）；③ **校验核心换 Rust**，`Field` 的约束从"运行时手写"变成 schema 声明。**性能提升在本项目不是主要动机**（接口 QPS 不高），**主要动机是 v2 的类型建模更清晰**（`X | None`、泛型、`Literal`/Enum 都是一等公民）。

**D6. `ConfigDict(extra="forbid")` 为什么只加在 Update 基类上？**
因为**创建和更新的容错需求不同**。创建时多传字段通常是前端把不相关字段一起发了，允许忽略更宽松；但**更新时字段名拼错是非常危险的**——用户以为改了 `retry_interval`，实际传成 `retry_interval_`，如果静默忽略，接口返回 200 但数据没变，前端和用户都以为成功了。`extra="forbid"` 让这类错误直接 40001 报出来。这是"**关键路径上宁可报错也不要静默**"的体现。

**D7. `model_dump(exclude_unset=True)` 和 `exclude_none=True` 有什么区别？为什么用前者？**
`exclude_unset=True` 排除"**请求里根本没传**"的字段；`exclude_none=True` 排除"**值为 null**"的字段。更新语义要的是前者——因为"把某字段显式置为 null"是一个**有效操作**（比如清空 `remark`），如果用 `exclude_none`，用户想清空就永远清不掉。所以 `exclude_unset` 才能实现"只更新显式传入的字段"。**这是本项目更新语义的核心一行**（`update_conversation` 里 `changes = payload.model_dump(exclude_unset=True)`）。

**D8. `PageParams` 为什么不继承 BaseModel？**
因为它不是一个"数据模型"，而是**从 Query 参数构造出来的运行期对象**。用普通类 + `Depends()`，在 `__init__` 里直接声明 `Query(...)`，FastAPI 会把每个参数当作独立的查询参数处理（而不是整体当成一个 body/单一参数）。同时它用 `@property` 提供 `offset`/`limit` 派生值——`BaseModel` 里写 property 也可以，但没必要引入模型语义（不需要 `model_dump`、不需要校验整个对象）。

**D9. OpenAPI 的 examples 是怎么"保证每个接口都有"的？**
两道机制：① **生成时注入**——`apply_examples()` 先查手写的 `REQUEST_EXAMPLES`，没有就用 `build_example()` 按 JSON Schema 自动造（含 `$ref` 递归、enum 首值、format 映射、字段名提示词），并且**请求体与响应体都要给**，还额外处理了 `Body(embed=True)` 那种**内联（非组件）**的请求体；② **测试守门**——`test_every_response_has_examples` / `test_every_request_body_has_examples` / `test_all_referenced_components_have_examples` 会在 CI 里失败。**生成负责"都有"，测试负责"以后也都有"**——只做前者，新增接口一样会漏。

**D10. `build_example` 为什么要限制递归深度为 3？**
因为 `$ref` 可以自引用（A 组件含 B，B 又含 A，或 A 含自身）。递归解析会在自引用处无限展开→爆栈。限制 `depth > 3` 直接返回 `None`，保证"宁可示例不全，也要文档能生成"。**这是生成器类代码的通用防御**——文档生成是"锦上添花"的功能，绝不能因为它把主服务拖垮。

### E. 权限与审计（8 题）

**E1. 表级权限和行级权限在这个项目里分别是什么？**
表级 = **能不能访问这个接口/资源类型**，由权限码 + `require_permission` 实现（例如没有 `qc:task:dispatch` 就不能调派发接口）。行级 = **在同一接口内能看见哪些数据行**，由租户范围实现（`tenant_scope_optional/required` 收敛 `tenant_id`，Repository 用 `where(tenant_id == ...)` 过滤）。两者**缺一不可**：只有表级权限，A 租户的用户还是能查到 B 租户的数据；只有行级，用户可能越权调用不该用的功能。

**E2. 行级隔离目前最大的风险是什么？**
**机制不完整、没有全局强制**。隔离链路是「路由声明依赖 → Service 透传 → Repository `if tenant_id is not None` 过滤」，任何一环漏掉就静默失效且不报错。特别是 Repository 那侧的 `is not None` 判断——**不传就不过滤**，语义是"不限租户"，这在超管场景是特性，在新接口忘传时就是漏洞。补法我在 §2.7 写了（规范测试 + 公共过滤函数），**但当前没补**，这是需要主动告知的边界。

**E3. 为什么 `require_permission` 支持多码取或？**
因为存在"**同一接口多入口**"的场景：比如某个接口既可以由具备 `outbound:assignment:may_dispatch` 的人触发，也可以是系统任务触发；或者"列表接口既服务外呼角色也服务质检角色"。取或（`any(code in owned for code in codes)`）比"必须全有"更贴合业务——这里没有出现需要 AND 的场景。**如果出现"必须同时具备多个权限"的需求，应该新加一个 `require_all_permissions`，而不是改这个函数**（它的语义已经被 60+ 处调用锚定了）。

**E4. 审计日志为什么分 `login_logs` 和 `operation_logs` 两张表？**
因为**记录维度与生命周期不同**：登录日志关注"凭据层面的成功/失败与原因"（用户名可能不存在，此时没有 `user_id`），且**每次登录都要记**（包括成功的）；操作日志关注"已认证用户对业务资源的写操作"，只在写方法上记，且**跳过 `/auth/login`**（已有 login_logs 覆盖，避免同一事件记两遍）。合成一张表会出现大量互相为空的字段（登录日志不需要 `path`/`duration_ms`，操作日志不需要 `success` 之外的"失败原因"文案）。

**E5. 失败登录日志为什么要显式 commit？**
因为 `get_db()` 在异常路径上会 `rollback()`——`AuthService.login` 抛 `Unauthorized` 后，请求依赖 `get_db` 捕获异常执行回滚。如果失败日志只 `db.add` 不 `commit`，它会跟着回滚，"登录失败"这个最需要审计的事件就丢了。所以在抛出前必须 `self.db.commit()`。**这条是本项目里"依赖生命周期"最容易踩的坑之一**，而且恰恰踩在最需要留痕的路径上。

**E6. 中间件里的操作日志为什么要先 `await call_next(request)` 再写？**
因为要记录**结果**（`status_code`、`success = status_code < 400`）和**耗时**。必须先让请求跑完才能拿到这两样。顺带说明：这也是为什么它是"环绕式"中间件（`start = time.perf_counter()` 在 `call_next` 之前）——耗时 = 请求全程耗时。

**E7. 审计日志写失败了怎么办？**
**只记异常，不抛**（`except Exception: logger.exception(...)`）。审计是"旁路"能力，不能反过来把业务打挂——否则日志表写满/DB 抖动会导致所有写接口失败，这是把可用性交给了审计。代价是"审计可能丢记录"，需要用**监控告警**（日志表写入失败次数）来兜，而不是用阻断来兜。**同理适用于 `login_logs`**：`_write_login_log` 失败不应影响登录本身（当前实现里它们共用业务事务，所以是"跟随业务一起成功/失败"，与操作日志的旁路语义不同——这是一个可以在面试里主动指出的差异）。

**E8. 脱敏在这个项目里生效了吗？**
**没有**，必须如实回答。`mask_phone` / `mask_id_card` 存在且有单测，但**全仓库没有任何生产调用点**（响应体没调、日志没调）。当前没有实际泄露，是因为代码里也没把手机号完整打进日志——但这是"没人踩进去"，不是"有防线拦住"。要真正生效，最小改动是在需要记录号码处显式调用，更稳的做法是加 `logging.Filter` 做字段级兜底擦除，让脱敏从"靠人记得"变成"框架兜住"。**把"有工具"说成"有防护"是面试里很容易被戳穿的夸大**，正确说法是"能力已备、链路未接"。
