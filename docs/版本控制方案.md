# 版本控制方案

> 本文档定义本项目的 Git 版本控制策略，覆盖仓库形态、分支模型、提交规范、PR 门禁、CI 流水线、数据库迁移管控、版本号与发布流程、文件与密钥管理。适用于后端（FastAPI + SQLAlchemy + Alembic）、前端（Vue 3 + Vite）、文档与本地编排（docker-compose）组成的单仓项目。
>
> 文档状态：方案（尚未执行初始化）。核对日期：2026-10-21。

---

## 0. 一页速览

| 主题 | 结论 |
|---|---|
| 仓库形态 | **单仓 monorepo**，不拆多仓、不使用 submodule |
| 分支模型 | **主干开发（trunk-based）**：`main` + 短生命周期 `feature/*`、`fix/*`、`chore/*`、`docs/*`，必要时 `release/*`、`hotfix/*` |
| 合并方式 | PR + Squash merge，保持 `main` 线性历史 |
| 提交规范 | Conventional Commits，格式 `type(scope): subject` |
| 版本号 | SemVer（当前 `0.x`），annotated tag `vX.Y.Z` |
| 质量门禁 | ruff + pytest（真实 PostgreSQL）+ Alembic 空库升级 + 前端 type-check/build |
| 数据库 | 迁移文件全部入库；已合并迁移只增不改；破坏性变更走 expand-contract |
| 密钥 | `backend/.env` 永不入库；只提交 `.env.example` 与非敏感前端环境文件 |
| 大文件 | 录音、数据库转储、构建产物不入库；暂不需要 Git LFS |

## 1. 现状与判断依据

| 项目 | 现状 | 对方案的影响 |
|---|---|---|
| Git 仓库 | 尚不存在（无 `.git`） | 可从零建立干净基线，无历史包袱 |
| 目录结构 | `backend/`、`frontend/`、`docs/`、`docker-compose.yml` | 适合单仓 monorepo |
| 代码规模 | 约 311 个源文件、2.8 MB | 普通 Git 足够，不需要 LFS |
| 忽略规则 | `.gitignore` 已覆盖 `__pycache__`、`node_modules`、`dist`、`storage`、`.env`、`*.log` | 基础正确，需少量补充 |
| 数据库迁移 | `backend/alembic/versions/` 下 8 个迁移版本 | 必须建立迁移纪律 |
| 质量工具 | `backend/pyproject.toml` 已配置 ruff 与 pytest | 规则已有，但无 CI，靠人工执行 |
| 敏感文件 | `backend/.env` 存在；`backend/.env.example` 可提交 | 首次提交前必须做密钥核查 |
| 前端环境 | `frontend/.env.development`、`.env.production` 仅含标题与 API 路径 | 可提交，作为环境模板 |
| 杂项文件 | `.task3-original.json` 为运行数据快照；`.trae/documents/质检模块落地方案.md` 为内部设计文档；`docs/asr-report/shots/` 约 350 KB | 分别决定不入库 / 移入 `docs/` / 正常入库 |
| 运行时数据 | `backend/storage/` 约 1.34 MB、360 个录音类文件 | 已被忽略，继续保持 |

**总体结论：** Git + 单仓 + 主干开发 + Conventional Commits + SemVer 标签 + PR 门禁 + Alembic 迁移纪律。

不建议完整 Git Flow（多长期分支、`develop`）与多仓拆分：项目规模下，完整 Git Flow 的管理成本高于收益。

## 2. 仓库形态与目录边界

保持单仓，按目录划分职责：

| 目录 | 内容 | 提交策略 |
|---|---|---|
| `backend/app/` | FastAPI 业务代码 | 提交 |
| `backend/tests/` | 单元、接口、集成测试 | 提交 |
| `backend/alembic/` | 迁移脚本与配置 | 必须提交，禁止回改已合并迁移 |
| `backend/scripts/` | 初始化与运维脚本 | 提交 |
| `backend/requirements.txt`、`pyproject.toml`、`alembic.ini` | 依赖与工具配置 | 提交 |
| `backend/.env` | 本地密钥与配置 | 忽略 |
| `backend/.env.example` | 配置模板 | 提交，值使用占位符 |
| `backend/storage/` | 录音、导入文件等运行时数据 | 忽略 |
| `backend/.pytest_cache/`、`.ruff_cache/`、`__pycache__/` | 缓存 | 忽略 |
| `frontend/src/`、`package.json`、`package-lock.json`、构建配置 | 前端源码与锁文件 | 提交（锁文件必须提交） |
| `frontend/dist/`、`node_modules/` | 构建产物与依赖 | 忽略 |
| `docs/` | 设计文档与截图 | 提交 |
| `docker-compose.yml` | 本地 PostgreSQL / Redis 编排 | 提交 |

如后续进入多人协作，可增加 `.github/CODEOWNERS` 做目录级评审归属，但不作为首期必做项。

## 3. 首次入库基线

### 3.1 补充忽略规则

在现有 `.gitignore` 基础上追加：

```gitignore
# 运行数据与临时快照
.task3-original.json
*.sqlite3
*.dump
*.bak

# 测试与构建缓存
.coverage
htmlcov/
coverage.xml
*.tsbuildinfo

# IDE / 操作系统
.idea/
.DS_Store
Thumbs.db
*.orig
*.rej
```

`.trae/` 二选一处理：

- 推荐：把 `.trae/documents/质检模块落地方案.md` 移入 `docs/design/` 后正常提交，避免项目知识散落在工具目录；
- 备选：整目录忽略，但需确认文档有其它留存位置。

### 3.2 新增 `.gitattributes`

Windows 开发、Linux/容器部署，必须统一换行符：

```gitattributes
* text=auto eol=lf
*.png binary
*.jpg binary
*.jpeg binary
*.gif binary
*.ico binary
*.bat text eol=crlf
*.ps1 text eol=crlf
```

### 3.3 首次提交前检查清单

- [ ] 确认 `backend/.env` 未进入暂存区；
- [ ] 扫描 `SECRET_KEY`、`FIRST_SUPERUSER_PASSWORD`、各类 `*_API_KEY` 是否出现在待提交文件中；
- [ ] 确认 `frontend/dist/`、`backend/storage/`、`__pycache__/`、`.pytest_cache/` 未被暂存；
- [ ] 确认 `frontend/.env.development`、`.env.production` 无敏感值；
- [ ] 把 `backend/.env.example` 中的密钥与管理员密码改为明确占位值（如 `change-me`）；
- [ ] 用 `git status --ignored` 核对忽略结果。

### 3.4 建立基线

```bash
git init -b main
git add backend frontend docs docker-compose.yml .gitignore .gitattributes
git status
git commit -m "chore: 初始化项目基线（后端 / 前端 / 文档 / 迁移）"
git tag -a v0.1.0 -m "v0.1.0 项目基线"
```

要求：

- 基线使用**一次提交**，不要人为拆成大量补丁；
- 标签与当前 `APP_VERSION=0.1.0`、`frontend/package.json` 的 `version=0.1.0` 对齐；
- 首次提交后立即核对 `git ls-files`，确认没有混入运行数据。

## 4. 分支模型

采用主干开发 + 短生命周期分支：

| 分支 | 用途 | 来源 | 合并方式 |
|---|---|---|---|
| `main` | 唯一长期分支，始终可发布 | — | 受保护，禁止直接 push |
| `feature/<slug>` | 新功能 | `main` | Squash merge，合并后删除 |
| `fix/<slug>` | 普通缺陷修复 | `main` | Squash merge |
| `chore/<slug>` | 工程、依赖、配置 | `main` | Squash merge |
| `docs/<slug>` | 文档 | `main` | Squash merge |
| `release/<x.y.z>` | 可选，仅需多人共同稳定版本时使用 | `main` | 合并回 `main` 后打标签 |
| `hotfix/<x.y.z>` | 线上紧急修复 | 最近发布标签 | 合并回 `main` 与仍在维护的 release 分支 |

示意：

```text
main      ──●────●─────────●──────────●────●──
             \            /            \  /
feature/qc  ●──●──●──●──●            hotfix ●──● → v0.1.1
```

硬性规则：

- 分支存活时间尽量短，一个 PR 只做一件事；
- 合并前把 `main` 同步到分支，在分支内解决冲突；
- `main` 使用 Squash merge，保持线性、可读历史；
- 禁止对 `main` 执行 `push --force`，禁止改写已共享历史；
- 合并后删除分支。

命名示例：

```text
feature/qc-batch-dispatch
fix/callback-timeout-release
chore/ci-pipeline
docs/version-control
release/0.2.0
hotfix/0.1.1
```

## 5. 提交规范

采用 Conventional Commits：

```text
<type>(<scope>): <subject>
```

### 5.1 type 取值

| type | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `refactor` | 不改变行为的重构 |
| `perf` | 性能优化 |
| `test` | 测试补充或调整 |
| `docs` | 文档 |
| `chore` | 杂项、脚本 |
| `build` | 依赖、构建配置 |
| `ci` | 流水线 |
| `revert` | 回滚提交 |

### 5.2 scope 建议

固定使用：`outbound`、`qc`、`auth`、`asr`、`backend`、`frontend`、`db`、`ci`、`docs`、`deps`。

### 5.3 示例

```text
feat(qc): 支持十万条对话按批派发
fix(outbound): 超时回收时同步释放坐席预占
refactor(backend): 抽取失败重试阶梯为独立模块
test(qc): 补充重复领取的幂等用例
chore(ci): 增加 PostgreSQL 服务与迁移校验
build(deps): 升级 fastapi 到 0.115
```

### 5.4 写作要求

- subject 使用中文，长度控制在约 72 字符内；
- body 说明“为什么改”和影响范围，而不是重复“改了什么”；
- 禁止 `update`、`修改一下`、`fix bug` 这类无信息提交；
- 一个提交只表达一个逻辑变更。

## 6. PR 流程与质量门禁

### 6.1 PR 模板必填项

- 变更目的与影响范围；
- 是否包含数据库迁移、是否向后兼容；
- 测试方式（新增或修改了哪些用例）；
- 配置项变化是否同步 `backend/.env.example`；
- 是否涉及密钥、大文件、运行数据；
- 文档是否需要同步。

### 6.2 必过检查

| 检查 | 命令或内容 |
|---|---|
| 后端静态检查 | `ruff check app tests`（工作目录 `backend/`） |
| 后端测试 | `python -m pytest -q`，需真实 PostgreSQL |
| 迁移可执行 | 空库执行 `alembic upgrade head` |
| 前端类型检查 | `npm run type-check`（工作目录 `frontend/`） |
| 前端构建 | `npm run build` |
| 文档类改动 | 可通过路径过滤跳过重型任务 |

### 6.3 评审规则

- 至少 1 人批准；
- 涉及认证、权限、迁移、外呼策略、回呼调度的变更建议 2 人评审；
- 单人项目也必须走 PR 自审，禁止直接提交 `main`；
- 单个 PR 尽量控制在可理解的范围内，经验值不超过约 400 行有效改动；
- 合并前确认 CI 全绿、无冲突、无未跟踪的临时文件。

## 7. CI 流水线方案

当前项目明确存在“无 CI 流水线、ruff 与 pytest 靠人工执行”的缺口，这是本方案优先补齐的部分。

### 7.1 流水线阶段

1. `backend-lint`：ruff 静态检查；
2. `backend-test`：PostgreSQL service + pytest；
3. `migration-check`：空库执行 `alembic upgrade head`，验证迁移链完整；
4. `frontend-check`：`npm ci` + `type-check` + `build`。

测试环境沿用 `backend/tests/conftest.py` 已注入的配置：

- `SCHEDULER_ENABLED=false`：测试进程不启动调度器，回收与派发由用例手动触发；
- `ASR_PROVIDER=mock`：外部服务固定为 mock，保证确定性；
- `BCRYPT_ROUNDS=4`：降低与校验逻辑无关的哈希成本。

### 7.2 GitHub Actions 参考

GitLab CI 结构等价，仅语法不同。

```yaml
name: ci
on:
  pull_request:
  push:
    branches: [main]

jobs:
  backend:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: app
          POSTGRES_PASSWORD: app
          POSTGRES_DB: app_test
        ports: ["5432:5432"]
        options: >-
          --health-cmd "pg_isready -U app"
          --health-interval 5s
          --health-timeout 3s
          --health-retries 30
    env:
      TEST_DATABASE_URL: postgresql+psycopg://app:app@localhost:5432/app_test
      SECRET_KEY: ci-only-secret
      SCHEDULER_ENABLED: "false"
      ASR_PROVIDER: mock
    defaults:
      run:
        working-directory: backend
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip
          cache-dependency-path: backend/requirements.txt
      - run: pip install -r requirements.txt
      - run: ruff check app tests
      - run: python -m pytest -q

  frontend:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: frontend
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: npm
          cache-dependency-path: frontend/package-lock.json
      - run: npm ci
      - run: npm run type-check
      - run: npm run build
```

### 7.3 补充要求

- Python 版本必须固定，建议 3.12 或与本地一致的 3.13，并在 README 与 CI 中保持一致；
- 迁移校验除空库外，发布前再执行一次“上一发布版本库 → head”的升级路径；
- 后续可引入 `pytest-cov`，先记录趋势，不急于设置硬门禁；
- CI 中禁止使用真实生产密钥，全部使用一次性测试值。

## 8. 数据库迁移版本控制

`backend/alembic/versions/` 下已有 8 个迁移，必须与代码同等级管理。

### 8.1 规则

1. 迁移文件必须入库，并与模型修改在同一个 PR 中提交；
2. 已合并的迁移禁止修改，包括修 typo、调顺序、改 `down_revision`；需要变更时新增迁移；
3. `revision` 链保持线性，`down_revision` 必须指向当前 head；出现分叉时显式创建 merge revision；
4. 禁止直接提交 `alembic revision --autogenerate` 的产物而不审查 diff；
5. 破坏性变更采用 expand-contract：先加新列或新表，再双写或回填，然后切换读取，最后在后续版本删除旧结构；
6. 发布顺序固定为：备份 → `alembic upgrade head` → 部署新版本；
7. `backend/scripts/init_db.py` 只负责首次建库与种子数据，不承担版本演进；
8. 测试库通过 `ALEMBIC_DATABASE_URL` 指向测试库，保证迁移不落到开发库；
9. 回滚优先“前向修复”；`downgrade()` 至少保证最近一个版本可用并纳入验证；数据库备份恢复是最后手段。

### 8.2 迁移 PR 检查项

- [ ] 模型与迁移是否一致；
- [ ] 新列是否允许 NULL 或带默认值；
- [ ] 是否新增索引、唯一约束、外键，是否评估锁表时间；
- [ ] 是否存在数据回填，回填是否可重入；
- [ ] 是否验证了空库升级；
- [ ] 是否评估了旧版本应用与新表结构的兼容性。

## 9. 版本号、标签与发布

### 9.1 SemVer 规则

当前处于 `0.x` 阶段：

| 位 | 触发条件 |
|---|---|
| MAJOR | 对外 API、数据模型或部署方式出现不兼容变更 |
| MINOR | 新增向后兼容的功能 |
| PATCH | 向后兼容的缺陷修复 |

版本信息需同步三处：

- `backend/.env` 与 `backend/.env.example` 的 `APP_VERSION`；
- `frontend/package.json` 的 `version`；
- 发布说明或 `CHANGELOG.md`。

### 9.2 标签规则

- 使用 annotated tag，如 `v0.2.0`；
- 一个发布对应一个标签，标签推送后不移动、不删除；
- 单人开发可直接在 `main` 打标签；需要多人稳定版本时使用 `release/x.y.z`；
- 紧急修复从最近标签切 `hotfix/x.y.z`，修复后打 PATCH 标签，并合并回 `main`。

### 9.3 发布流程

1. 冻结本次发布范围；
2. 同步三处版本号；
3. 更新 `CHANGELOG.md`；
4. 确认 CI 全绿；
5. 创建 annotated tag；
6. 备份数据库；
7. 执行 `alembic upgrade head`；
8. 部署新版本；
9. 冒烟验证：登录、外呼任务执行、回呼派单、质检派发与领取提交、ASR 转写；
10. 观察日志与关键指标，记录发布结果。

### 9.4 回滚策略

| 场景 | 做法 |
|---|---|
| 代码缺陷 | 重新部署上一个标签；单点问题可用 `git revert` 生成反向提交 |
| 数据库结构 | 优先前向修复；`downgrade()` 需事先验证；最后手段为备份恢复 |
| 配置错误 | 回退配置并重启，禁止通过改历史提交掩盖问题 |
| 共享分支 | 禁止 `reset --hard`、禁止强推 |

### 9.5 API 版本

- 现有 `/api/v1` 内做向后兼容的增量变更；
- 出现破坏性变更时新增 `/api/v2`，不在同一路径下悄悄改变语义；
- 如需容器化部署，镜像同时打 `app:vX.Y.Z` 与 `app:sha-<短哈希>`，生产禁止只用 `latest`。

## 10. 文件与二进制内容策略

| 类型 | 例子 | 策略 |
|---|---|---|
| 源码、迁移、测试、文档、锁文件 | `backend/app`、`alembic/versions`、`package-lock.json` | 必须提交 |
| 本地配置 | `backend/.env` | 永不提交 |
| 配置模板 | `backend/.env.example`、`frontend/.env.*` | 提交，只放非敏感值 |
| 运行时数据 | `backend/storage/`、导入文件、录音 | 忽略；长期留存放对象存储 |
| 构建产物 | `frontend/dist/`、`node_modules/` | 忽略 |
| 缓存 | `__pycache__/`、`.pytest_cache/`、`.ruff_cache/` | 忽略 |
| 文档截图 | `docs/asr-report/shots/*.png`（约 350 KB） | 正常提交 |
| 临时快照 | `.task3-original.json` | 不入库；测试需要时移到 `backend/tests/fixtures/` 并脱敏 |
| 数据库转储 | `*.dump`、`*.sql` 备份 | 不入库 |
| 大二进制 | 超过约 5 MB 的文件 | 先评估必要性，确需版本化再使用 Git LFS |

当前仓库体积很小，不需要引入 LFS。不要把所有二进制都放进 LFS，否则会增加克隆与 CI 成本。

## 11. 工具落地

### 11.1 `.editorconfig`

统一缩进、编码与换行，减少 Windows 与 Linux 之间的无意义 diff。

### 11.2 `pre-commit`

```yaml
minimum_pre_commit_version: "3.7.0"
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-merge-conflict
      - id: check-added-large-files
        args: ["--maxkb=5120"]
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.8.4
    hooks:
      - id: ruff
        args: ["--fix"]
        files: ^backend/
      - id: ruff-format
        files: ^backend/
```

ruff 版本应与 `backend/requirements.txt` 中的 `ruff>=0.8.0` 对齐，避免本地与 CI 规则不一致。

### 11.3 提交信息校验

可选引入 commitlint，或在 CI 中用 PR 标题正则校验 `type(scope): subject`。团队规模较小时可先靠约定，提交量上来后再自动化。

## 12. 分阶段落地

| 阶段 | 动作 | 验收标准 |
|---|---|---|
| P0 基线 | 补 `.gitignore`、加 `.gitattributes`、清理特殊文件、密钥核查、`git init -b main`、一次基线提交、打 `v0.1.0` | `git status --ignored` 干净；仓库中无 `.env`、无 `dist`、无 `storage`、无缓存 |
| P1 协作规则 | 开启 `main` 保护、确定分支命名、提交规范、PR 模板与评审规则 | 所有变更只能经 PR 进入 `main` |
| P2 自动化 | CI（lint / test / migration / frontend）、pre-commit、可选 commitlint | PR 未过检查无法合并 |
| P3 发布治理 | `CHANGELOG`、发布与回滚清单、迁移升级演练、备份策略、可选覆盖率趋势 | 每次发布可复现、可回滚、有记录 |

---

## 13. 不建议的做法

- 采用完整 Git Flow，保留长期 `develop` 分支；
- 提交 `frontend/dist/`、`backend/storage/`、`backend/.env`；
- 修改已合并的 Alembic 迁移；
- 对 `main` 强推或改写已共享历史；
- 使用 `git add -A` 盲提交；
- 把录音、数据库转储、密钥放进仓库；
- 在 `.env.example` 中保留可直接使用的生产级默认口令；
- 用调整历史提交的方式掩盖配置或发布错误。

## 14. 附录：首次入库命令清单

```bash
# 1. 确认工作区状态
git status --ignored

# 2. 初始化仓库（默认分支 main）
git init -b main

# 3. 只添加需要入库的内容
git add backend frontend docs docker-compose.yml .gitignore .gitattributes

# 4. 检查暂存区，确认无 .env / storage / dist / 缓存
git status

# 5. 基线提交
git commit -m "chore: 初始化项目基线（后端 / 前端 / 文档 / 迁移）"

# 6. 打基线标签
git tag -a v0.1.0 -m "v0.1.0 项目基线"

# 7. 复核已跟踪文件
git ls-files
```

最终形态：**一个 `main` 主干、短分支 + Squash PR、Conventional Commits、`vX.Y.Z` 标签、CI 四道门禁、Alembic 迁移只增不改。**
