# 第一部分 · 项目全景

## 一、项目总览：这是什么、为什么这么搭

**一句话**：一套面向企业的呼叫中心一体化平台，两大业务域——**智能外呼**（名单导入 → 建任务 → 选号码 → 派单/呼叫 → 结果回写 → 重试/超时回收 → 会话小结 → IVR/回呼 → 报表监控）与**对话质检**（客服对话 → 专家领取评分 → 10 万条级批量派发 → 完成率/每日完成量报表 → 优秀案例库）。

**规模盘点（可核对）**：38 张业务表、8 个 Alembic 版本、144 个 HTTP 端点（认证 4 / 外呼 103 / 质检 37）、63 个 RBAC 权限码（外呼 40 / 质检 23）、21 个前端页面、5 个定时任务、756 条自动化测试（需 PostgreSQL 在运行）。

**后端技术栈**：FastAPI + uvicorn[standard] + SQLAlchemy 2.0（同步）+ psycopg3 + PostgreSQL 16 + Alembic + Pydantic v2 + PyJWT + bcrypt + Redis（可选降级）+ APScheduler（单机）+ openpyxl + pytest + ruff。

**三个贯穿全局的设计基调**：
1. **统一契约**：所有接口返回 `{code, message, data}`；错误码集中在 `BizCode`；异常经全局处理器收敛，任何出口都不会漏出非统一结构。
2. **并发与幂等靠数据库而不是应用锁**：10 万条派发用 `INSERT…SELECT` + `ON CONFLICT`；领取/提交用带状态条件的原子 `UPDATE` + `rowcount`；超时回收用 `SELECT…FOR UPDATE` + 锁内复核。
3. **外部系统一律抽象**：call / phone / ivr / asr / tts 全部走「Provider 接口 + 工厂 + `.env` 切换」，Service 层只依赖抽象。

**为什么质检单独成包**：外呼关注"打出去"、质检关注"说得怎么样"，是**不同的限界上下文**。所以质检有独立的 `models/qc`、`services/qc`、`repositories/qc`、`schemas/qc`，只在基础设施层（db/session、core、utils）复用，避免把外呼 22 张表的语义搅浑。

## 二、外呼域十二大流程（每条一句话）

| # | 流程 | 一句话 |
|---|---|---|
| 1 | 认证与权限 | 登录只发 token（access 30 分钟 / refresh 7 天），用户信息另调 `/auth/me`；登出靠把 `jti` 塞进 Redis 黑名单 |
| 2 | 任务生命周期 | 6 态（DRAFT/READY/RUNNING/PAUSED/COMPLETED/CANCELLED）；只有 DRAFT/CANCELLED 可删，只有 DRAFT/READY/PAUSED 可改；复制任务幂等 |
| 3 | 名单导入 | Excel/CSV → 表头别名归一化 → 逐行验号码 → 按 `(user_id, order_id)` 去重 → 失败行单独记录；批次只落 SUCCESS/PARTIAL_FAILED/FAILED |
| 4 | 号码选取 | 扣次数是带条件的原子 UPDATE（`WHERE status='ENABLED' AND (usage_limit IS NULL OR used_count+step<=usage_limit)`），四种选取策略 |
| 5 | 执行引擎 | 每条记录一个事务；遍历被叫号码、每个号码选主叫并原子扣次、写 CallHistory、调网关；全失败走重试阶梯 |
| 6 | 结果回写 | 不用 JWT，用 HMAC-SHA256 签名 + 时间戳容差（300s 防重放）；回调幂等（已有终态直接忽略） |
| 7 | 重试与超时 | 三档：不可重试→FAILED；还能重试→RETRY_WAITING 按 `next_retry_at` 排队；次数用完→EXHAUSTED。超时回收用行锁 + 锁内复核 |
| 8 | 坐席与派单 | 坐席 5 态；一坐席一预占（部分唯一索引兜底）；预占 60s 超时自动释放 |
| 9 | 会话与小结 | 实际生命周期 `CREATED/ASSIGNED → CALLING → ENDED|TIMEOUT`（CONNECTED/RELEASED 定义了但无写入点，如实） |
| 10 | IVR | 节点/流转可配置；结构校验找不可达节点、终结节点挂流转等；模拟推演是纯逻辑引擎（不碰 DB） |
| 11 | 回呼 | IVR 触发按 `origin_session_id` 幂等建任务；触发条件按固定优先级取首个命中 |
| 12 | 报表监控 | 话务流水多条件筛选 + 汇总 + 明细；监控 1 分钟分桶且补零；前端 30s 自动刷新 |

## 三、数据模型与 RBAC

**38 张表按 9 组**：RBAC 基线 5、审计 2、租户资源 3、外呼配置 5、任务与名单 4、执行与会话 5、IVR 3、回呼 2、对话质检 9。

**三个数据层设计点**：
1. **软删除 + 部分唯一索引**：`is_deleted` 字段 + 唯一索引带 `WHERE is_deleted = false`——只有未删除行参与唯一约束，所以"删掉重名任务再建同名"能成功。全库共 **24 个**部分唯一索引。
2. **枚举一律 `VARCHAR(32)` + Python 校验**，不用 PG 原生 ENUM——原生枚举增删值要跑迁移、跨库不通用。
3. **时间统一 `timestamptz`（UTC）**，只在报表层按 `QC_REPORT_TIMEZONE`（默认 Asia/Shanghai）换算分桶。

**RBAC 五张表**：`users → user_roles → roles → role_permissions → permissions`。63 个权限码唯一来源是 `core/permissions.py`，由 `scripts/init_db.py` **幂等**写入并授予内置 admin 角色。前端路由 `meta.permission` 与 `v-permission` 指令用同一批码，做到"一处定义、三处生效"——但真正鉴权始终在后端。

## 四、状态机与并发控制

**5 个状态机**：外呼任务 6 态、坐席 5 态、回呼任务 6 态、质检任务 5 态、质检明细 4 态。统一模式：`TRANSITIONS: dict[状态, frozenset[状态]]` + `can_transition` / `ensure_transition`（非法抛 `StateNotAllowed` → 40902）/ `allowed_targets` + 集合守卫（`EDITABLE_STATUSES` / `DELETABLE_STATUSES` / `FINISHED_STATUSES` 等）。**状态流转只在一处定义，就能被单测逐条钉死**。

**单测手段（如实）**：是"合法边逐条列举 + 非法边逐条列举（断言错误信息含两个枚举值）+ 守卫按状态全遍历 + 覆盖性断言"，**不是 6×6 笛卡尔积穷举**——外呼 6 态理论 30 条非同态边，用例列了 21 条。

**三条并发路径**：
- **派发（10 万条）**：单条 `INSERT…SELECT` + `row_number() OVER (ORDER BY id)` 取模均分（ROUND_ROBIN 用 `(rn-1) % n`；AVERAGE 用 `chunk=ceil(total/n)` + `least(floor((rn-1)/chunk), n-1)`，**必须 floor**）+ `NOT EXISTS` 排除 + `ON CONFLICT (task_id, conversation_id) WHERE is_deleted=false DO NOTHING`（**冲突条件的 WHERE 必须与索引字面一致**）+ 分批 `while inserted > 0`。
- **领取/提交（乐观锁）**：带状态条件的原子 `UPDATE … WHERE status='PENDING' RETURNING…`，`rowcount == 1` 判定成功——多人抢同一条只有一人能改。
- **超时回收（悲观锁）**：`SELECT…FOR UPDATE` + 锁内复核，因为是"先读后判"的复合操作。

**真实踩坑**：psycopg3 下 `INSERT…SELECT` 的 `rowcount` 返回 **-1**（UPDATE 正常）——计数必须改用 `RETURNING`，否则"派发中断 / 误判已提交"。

## 五、前端与报表

- **权限路由**：登录后按 `meta.permission`（共 18 条）递归过滤 `asyncRoutes` 再 `addRoute`，菜单由路由渲染。两个真实踩坑：① 兜底路由**不能写 `redirect`**（`redirect` 在路由匹配阶段执行，早于 `beforeEach`，会把动态路由提前改写成 /404）；② 守卫注册完路由**不能返回 `{...to}`**（会按 name 又落回 CatchAll），必须返回 `{path, query, hash, replace: true}`。
- **Axios**：拦截器注入 token（每次实时读 localStorage）；响应拦截器判 `body.code !== 0` 统一弹错并 reject；401 三个细节——`/auth/login` 豁免、`redirecting` 并发去重、`redirect` 参数整页刷新回跳。
- **ECharts**：`utils/echarts.ts` 按需注册（只注册 Bar/Line/Pie + Grid/Legend/Title/Tooltip + CanvasRenderer，省约 1MB；**未注册 GaugeChart**）；`useEcharts` 用 `shallowRef` + `setOption(option, true)` + 监听 resize + `dispose()`。
- **分桶与补零**：SQL 里先 `func.timezone(settings.QC_REPORT_TIMEZONE, …)` **再** `func.date_trunc("day", …)`（顺序不可反，否则跨零点错位）；半开区间 `[start, end)`；**补零在服务层 Python `while cursor <= date_to`**（不用 PG 的 `generate_series`，跨库更稳）；监控用 `date_trunc("minute")` 不做时区换算。
- **真实字段坑**：后端聚合列名 `pass`（Python 保留字）→ TS 侧改名 `pass_count`，页面用 `passOf()` 收敛；`params as unknown as Record<string, unknown>` 双断言是真实修过的类型坑。

## 六、工程与质量（5 个定时任务 + 测试）

**五个定时任务（都是后台兜底，不是主流程）**：

| 任务 | 间隔 | 大白话 |
|---|---|---|
| 超时回收 | 30s | "电话打出去超时没结果，收回来标超时，能重试就排队重试" |
| 重试派发 | 60s | "到点的失败记录，再推一遍" |
| 预占释放 | 30s | "坐席被预占 60s 没接，腾坑给别人" |
| 回呼派单 | 60s | "到点该回呼的客户，有空闲坐席就派" |
| 质检回收 | 300s | "专家领了明细 30 分钟不交，放回去让别人领" |

**统一骨架**：全部是「宽松扫描 → 加锁复核 → 动作提交」的幂等范式——重复触发不会产生脏数据（关键！因为调度是单机 APScheduler，多实例部署每个实例都会跑，全靠幂等兜底）。**提交粒度按业务原子性分**：超时回收/预占释放/质检回收**每条一个 commit**；回呼派单**整批一个 commit**。

**测试体系**：pytest + FastAPI TestClient（底层 httpx）+ **真实 PostgreSQL**（禁用 SQLite——要验的正是 `FOR UPDATE`、部分唯一索引、JSONB 这些 PG 能力，用 SQLite 得到的是"假通过"）+ Alembic `upgrade head`。conftest 五个关键设计：环境变量在 `import app` **之前**注入（`BCRYPT_ROUNDS=4`、`SCHEDULER_ENABLED=false`、`ASR_PROVIDER=mock`）、`_ensure_database_exists()`、session 级 engine 跑迁移、`db_session` 外层事务 + savepoint、`client` 用 `dependency_overrides`。**唯一的真并发用例**：8 线程 × 24 次扣减、断言恰好成功 5 次。ruff 作为提交前门槛（`line-length=100`、`select=E,F,I,B,UP`、`ignore=B008`、`exclude=alembic/versions`）。

## 七、语音转写（ASR）

**为什么不能只返回纯文本**：质检要判断"坐席有没有抢话 / 客户情绪如何"，必须知道**每句话是谁说的、什么时候说的**——所以 ASR 产出「说话人 + 文本 + 时间戳」的分段消息。

- **契约**：`AsrSegment(role: MessageRole, text: str, start_ms: int|None, end_ms: int|None)`（frozen dataclass）。
- **抽象**：`AsrProvider(ABC)`，`transcribe_segments(*, audio_path) -> list[AsrSegment]` 是抽象方法，`transcribe()` 是模板方法（默认拼接全文）。
- **工厂**：`get_asr_provider()` 按 `.env` 的 `ASR_PROVIDER`（默认 `mock`）选 `MockAsrProvider` / `AliyunAsrProvider`，未知名直接报错并列出可选值。
- **状态流转**：`PENDING → RUNNING → SUCCESS | FAILED`。先置 `RUNNING` 并**先 commit**（让前端能看到进行中），再调用 provider。
- **重转幂等**：`_rewrite_asr_messages` 四步——① 删旧 ASR 消息（`delete_messages_by_source`）② `coalesce(max(seq), 0)` 取基准（空表必踩点）③ `seq = base_seq + index` 批量插入（不会和 TEXT 消息撞号）④ `count(*)` 回填 `msg_count`。
- **如实说明**：`AliyunAsrProvider` 是**模拟实现**（`name="aliyun"`，调用形态照阿里云"录音文件识别"写——提交任务 → 轮询结果，但内部是 uuid + `asyncio.sleep`，不发真实 HTTP）；转写**没有独立的 `TRANSITIONS` 状态机**（只有枚举 + 直接赋值）；"重转清旧消息"代码已实现但**缺专门幂等用例**；转写是同步阻塞（同步端点 + `run_sync`）。

## 八、后端分层与接口

**三层**：Router（只做 HTTP 层，1～2 行就结束）→ Service（业务规则 + **事务提交在本层**）→ Repository（只写 SQLAlchemy 查询）。纪律写在四个文件的 docstring 里（`repositories/__init__.py`"禁止写业务规则/权限/状态机"、`api/deps.py`"【基线冻结】"、`db/session.py`"事务由 Service 层控制"）。

**依赖注入链四段**：`get_token_payload`（解 JWT + 验 type + 查黑名单）→ `get_current_user`（查库 + 验 is_active）→ `require_permission(*codes)`（超管短路放行 / 权限码取或）→ `tenant_scope_optional/required`（租户收敛：普通用户传别的租户 → 403）。

**统一响应与业务码**：`{code, message, data}`；`BizCode` 里 **`SYSTEM_ERROR = 50000`（没有 50001）**；HTTP 409 下有三个码（40901 重名 / 40902 状态不允许 / 40903 号码耗尽 / 40904 被引用）——业务码给前端语义槽位、HTTP 状态码给网关监控，两者解耦。四个全局异常处理器把所有出口收敛成统一体，`RequestValidationError` 从默认 422 改成 400 + 40001 + `[{field, msg}]`。

**OpenAPI**：`custom_openapi()` 覆盖 `app.openapi`，`apply_examples()` 两层兜底（手写 `REQUEST_EXAMPLES` + `build_example()` 自动生成，递归限深 3 防自引用），并用 `test_openapi_docs.py` 守门——每个 operation 必须有 summary/description/security/examples。

**权限与审计（如实部分）**：脱敏函数 `mask_phone`/`mask_id_card` **写了、测了，但全仓库没有任何生产调用点**（"能力已备、链路未接"）；`login_logs` 记登录成功/失败（**失败日志必须单独 commit**，否则跟着异常回滚就丢了）；`operation_logs` 由中间件异步写（线程池，只记非 GET/HEAD/OPTIONS，写失败只记异常不阻断业务），但 `target_type/target_id/request_id/detail` 四个字段恒为 NULL（中间件未填充）。

## A. 项目整体与技术选型（9 题）

### A1. 这个项目是做什么的？介绍一下整体架构。
**标准回答**：一套呼叫中心一体化平台，两大业务域——智能外呼（名单导入 → 建任务 → 选号码 → 派单/呼叫 → 结果回写 → 重试/超时回收 → 会话小结 → IVR/回呼 → 报表监控）和对话质检（客服对话 → 专家领取评分 → 批量派发 → 完成率报表 → 案例库）。后端 FastAPI + 三层架构（Router/Service/Repository），PostgreSQL 16 + SQLAlchemy 2.0，前端 Vue3 + Element Plus，5 个 APScheduler 定时任务兜底。
**大白话**：一个"自动打电话 + 检查客服服务质量"的平台。前半段是机器人替你拨号、打不通就排队重试、坐席忙就分配；后半段是把客服和客户的对话/录音拿来给质检专家打分，看客服说得合不合格。

### A2. 为什么选 PostgreSQL？换成 MySQL 行不行？
**标准回答**：真用上了只有 PG 才有的能力——**部分唯一索引**（`WHERE is_deleted=false`，软删后名字可复用）、`INSERT…SELECT…ON CONFLICT DO NOTHING`（10 万条派发幂等）、JSONB（导入失败明细/评分明细）、timestamptz。换 MySQL 这些全要改写为应用层逻辑，并发正确性下降。
**大白话**：项目里最危险的几个并发操作都是靠数据库"一次SQL搞定"来保证不出错的，这些写法是 PG 特有的。换数据库等于把保险箱换成普通锁，还得自己盯着。
**加分点**：测试也坚持真实 PG（禁用 SQLite），因为要验的正是这些 PG 特性。

### A3. 为什么选同步 SQLAlchemy？异步不行吗？
**标准回答**：事务边界清晰（`db/session.py` 明确"事务由 Service 层控制"）。Service 层是同步实现，配合 `utils/async_bridge.py`（`run_sync`）调用 async Provider 接口——既满足 Provider 契约、又不阻塞 HTTP（`run_sync` 在无事件循环时 `asyncio.run`，有事件循环时丢进单线程池）。全面 async 会让所有 Service 函数变 async、事务与异常处理复杂度显著上升。
**大白话**：数据库读写用"排队的同步方式"（每步等结果），但调外部 AI/网关这类慢操作用异步。同步的好处是出错时机好猜、事务边界清楚；异步的好处是不空等。项目在中间加了一层"桥"，两头的好处都要。

### A4. 为什么选 Redis？Redis 挂了会怎样？
**标准回答**：Redis 只承担**登出黑名单**一件事（`blacklist_token` 按 `jti` 写入，TTL 取 refresh 的 7 天，天然自清理）。`core/cache.py` 在 Redis 不可用时**自动降级放行**并打日志——`is_token_blacklisted` 返回 False。测试里对应用例带 `skipif(not cache_available())`。
**大白话**：Redis 就像门卫的"黑名单本子"——谁被登出就记上。本子丢了（Redis 挂了），门卫选择"先放行"而不是"全不放"，因为宁可让被登出的人多赖一会儿，也不能让全公司都进不了门。
**加分点**：这是刻意的可用性优先取舍，不是缺陷；代价是"Redis 挂了登出不是即时生效"。

### A5. 软删除 + 部分唯一索引解决什么问题？
**标准回答**：`SoftDeleteMixin` 提供 `is_deleted`/`deleted_at`/`mark_deleted()`。唯一索引带 `WHERE is_deleted = false`，只有未删除行参与唯一约束——所以"删除同名任务后再建同名的"能成功，普通唯一索引做不到。全库 24 个此类索引。
**大白话**：删除不是真删，是贴一张"已删除"标签。但唯一性检查只看没贴标签的行——所以旧任务虽然还在数据库里躺着，但新任务可以重新用它的名字。
**加分点**：软删除没有全局过滤器，每个查询都要手写 `is_deleted.is_(False)`——这是为显式可调试付出的代价，漏写会查到已删除数据。

### A6. 63 个权限码怎么管理？为什么集中在一处？
**标准回答**：权限码唯一来源是 `core/permissions.py`（外呼 40 + 质检 23 = 63），`scripts/init_db.py` 幂等同步入库并授予 admin。命名规范 `模块:对象:动作`。前端路由 `meta.permission` 与 `v-permission` 用同一批码。集中定义避免三类漂移：拼写不一致、新增码忘了入库（403 永远过不了）、前端菜单用了库里没有的码。
**大白话**：权限码就像项目里的"身份证号"，只有民政局（`permissions.py`）能发号。如果到处各自写，就会出现"甲写了 `dispath`、乙写了 `dispatch`"这种谁都对不上的乱象。
**加分点**：有测试断言"权限码目录无重复、全量 == 外呼 + 质检"。

### A7. Provider 抽象 + 工厂 + .env 切换是什么？为什么？
**标准回答**：call / phone / ivr / asr / tts 五个域都有「抽象接口 + 具体实现」。`providers/factory.py` 的 `_resolve(name, mapping, kind)` 按 `settings.XXX_PROVIDER` 选实现，未知名抛 `AppException("未知的 X Provider：…可选 …")`。Service 层只依赖抽象接口，绝不直接实例化具体 Provider。开发/测试用 `mock`，上线改 `.env` 不改代码。
**大白话**：把"和外部公司打交道"的事全隔离到一层。开发时用假人（mock）陪你排练，上线时换个真员工（真实实现）——但舞台上所有剧本台词都一样，不用改业务代码。
**加分点**：真实实现缺地址时直接报错而非静默降级；统一 `PROVIDER_TIMEOUT_SECONDS` / `PROVIDER_MAX_RETRIES` 防止无限等待。

### A8. 事务归属为什么在 Service 层？`get_db` 和 `session_scope` 区别？
**标准回答**：`get_db()`（FastAPI 依赖）只 yield，正常路径**不 commit**，异常时 rollback，提交权完全交给 Service——因为只有 Service 知道"这次业务到哪算完整"（如质检提交四步：写结果 → 改明细状态 → 完成数自增 → 条件完成）。`session_scope()`（contextmanager）给非请求场景用（定时任务/中间件/脚本），yield 后自动 commit、异常 rollback。
**大白话**：数据库的"存钱"操作像"结账"——前台（Router）只负责收银，真正决定"这一单几件事一起算钱"的是后厨（Service）。定时任务不在前台体系里，所以单独发一个"自助结账机"（session_scope）。
**加分点**：提交粒度按业务原子性分——超时回收逐条 commit，回呼派单整批 commit。

### A9. 项目有哪些已知边界？（诚实清单）
**标准回答**：① ASR/IVR/TTS Provider 仅 mock；② 录音只存路径，无下载/试听端点；③ `max_concurrency` 执行层未强制（用 `EXECUTE_BATCH_SIZE`）；④ 预测外呼只输出建议无自动拨号闭环；⑤ 前端未接 refresh token；⑥ 首页模块进度表是静态硬编码且已过期；⑦ 无应用 Dockerfile；⑧ 调度单机，多实例会重复执行；⑨ `.env` 密钥都是开发默认值。
**大白话**：这题是送分题也是送命题——主动说清楚"哪些没做完"，比被追问时支支吾吾强得多。面试官要的不是完美的项目，是你"知道自己系统边界在哪"。
**加分点**：每个边界都能说出补法（分布式锁用 Redis 已具备条件、refresh token 静默续期等）。

## B. FastAPI 与 ASGI（6 题）

### B1. ASGI 和 WSGI 区别？为什么中间件写日志不能阻塞？
**标准回答**：WSGI 同步接口，一个 worker 同一时刻处理一个请求；ASGI 异步接口，单 worker 可在等待 I/O 时切换处理其它请求。本项目 DB 是同步 SQLAlchemy，FastAPI 自动把同步 `def` 端点丢线程池——业务不阻塞事件循环。但中间件是 `async def` 跑在事件循环上，若直接同步写 DB 会卡死整个事件循环，所以 `_write_operation_log` 必须经 `run_in_threadpool`。
**大白话**：服务生（事件循环）在门口同时招呼很多人，不能让"写日志"这种小事把他一个人占住——所以日志写库这活扔给跑腿的（线程池）干，服务生继续招呼客人。
**加分点**：`run_in_threadpool` 用的是 AnyIO 线程池，与同步端点共用一套池，不会线程数翻倍。

### B2. `lifespan` vs `@app.on_event("startup")`？
**标准回答**：`lifespan` 是 `asynccontextmanager`，进入跑启动、退出跑关停，**启动/关停写在同一处**。本项目用它做 `get_redis()` 预热（挂了只降级不阻断）、`start_scheduler()`、`shutdown_scheduler()`。`on_event` 的启动/关停分离，容易出现"启动写了、关停忘了"，且已在新版标记废弃。
**大白话**：`on_event` 像"开灯写一个函数、关灯写一个函数"，两个函数可能分开维护、一个改了另一个忘了。`lifespan` 像"灯的总开关"，开和关绑定在同一个房间里，不会漏。
**加分点**：资源清理与启动逻辑共享同一路径。

### B3. `response_model` 有什么用？和直接 return dict 区别？
**标准回答**：`response_model=ApiResponse[X]` 做三件事：① **字段白名单**——ORM 对象里的 `password_hash` 之类不会泄出去；② **类型校正**——DateTime/Enum 序列化一致；③ **生成 OpenAPI schema**。函数返回 `ok(...)` 这个 dict 是"数据"，`response_model` 是"出口契约"——写作自由，出口受控。
**大白话**：函数内部可以随便返回，但出门前要过安检（response_model）——安检机决定"哪些东西（字段）允许带出门"。
**加分点**：泛型 `ApiResponse[PageData[ConversationOut]]` 直接成为文档里的 schema。

### B4. `HTTPBearer(auto_error=False)` 为什么要关自动报错？
**标准回答**：FastAPI 默认缺 Bearer 时直接返回 403，但项目契约是所有"未登录"出口统一 401 + 40101（前端按 401 做登出跳转）。关掉后 `credentials is None` 由 `get_token_payload` 主动 `raise Unauthorized()`，所有出口收敛到一处。
**大白话**：框架默认说"没带票就骂你一顿（403）"，但公司规定"没带票先带去登记（401）"——所以要关掉框架自己的嗓门，改由自己的保安按公司规矩来。
**加分点**：体现"框架默认行为 vs 项目契约冲突时，以契约为准"。

### B5. 路由聚合为什么有顺序要求？
**标准回答**：两个真实踩坑：① 带 `{id}` 的动态段会吞掉同层静态路径——所以质检模块**先挂静态路径**（专家组/任务/报表/案例库）**再挂 `{id}` 域**；② 同一文件内 `/qc/conversations/import`、`/import-batches` 必须声明在 `/{conversation_id}` **之前**，否则 `/import` 会被当成 `conversation_id="import"` 命中详情接口再报 422。
**大白话**：路由匹配是"排队按顺序问"——写着"你是谁"的问号路径会先抢答任何经过的人。所以要把"名字写死的路径"（/import）排在"问号路径"（/{id}）前面，不然 /import 会被问号路径拦住。
**加分点**：不是框架 bug，是 path 匹配特性；代码里写了注释防止后人改乱顺序。

### B6. 全局异常处理器兜底怎么设计？
**标准回答**：四个 handler：`AppException`（Service 主动抛的，返回 `http_status` + `fail(code, message)`，记 warning）、`RequestValidationError`（改写成 400 + 40001 + `[{field, msg}]`，`loc` 用 `.` 拼成 `body.username`）、`StarletteHTTPException`（`_STATUS_TO_CODE` 映射 400/401/403/404/409，**映射不到落 50000**）、`Exception`（500 + 50000 + "系统异常，请稍后重试"，记 exception 栈）。**任何异常出口都被收敛成统一响应体**。
**大白话**：整个系统只有一个"总客服"——不管什么角落出错，到出口前都会被同一个客服接住，用同一句话术（`{code,message,data}`）回答。前端永远不用处理第二种格式。
**加分点**：`RequestValidationError` 从默认 422 改成 400+40001，格式全系统统一。

## C. 三层架构与职责边界（6 题）

### C1. 三层边界是怎么在代码里落地的（不靠文档）？
**标准回答**：靠四个文件的第一行 docstring 钉成可核对事实——`repositories/__init__.py`"只负责 SQLAlchemy 查询，禁止写业务规则/权限/状态机"、`api/deps.py`"【基线冻结】鉴权契约在此定义，禁止修改"、`db/session.py`"事务由 Service 层控制，Router 不碰事务"、各 Service 类"事务在本层提交"。结构性证据：随便打开 Router 函数，函数体通常只有 1～2 行（取参 → 调 Service → `return ok(...)`）。
**大白话**：纪律不是写在《开发规范》里让人自觉，而是写在每个"岗位门口"的牌子上——谁负责什么、谁不许越界，打开文件第一眼就看到。
**加分点**：删对话的对比——Router 一行、Service 管规则与提交、Repository 只管查询，三层各一眼可辨。

### C2. 为什么 Repository 不做成泛型基类 `BaseRepository[T]`？
**标准回答**：项目查询高度领域化——软删除必过滤、租户可选过滤、部分唯一索引语义、大量特定筛选组合。泛型基类要么把参数塞进 `**kwargs`（类型全丢），要么给每个领域写只在基类挂名的方法。选了"按领域一个 Repository 类 + 统一 `__init__(self, db)`"，语义清晰可直接点进 SQL。代价是公共动作重复，显式接受。
**大白话**：每个业务的查法都不一样（有的要过滤软删、有的要按租户、有的要部分唯一索引），硬套一个"万能模板"反而要写一堆 `**kwargs` 魔法。宁可每个类自己写清楚，也别搞一个看着省事、用起来靠猜的基类。
**加分点**：承认 `**filters: object` + `# type: ignore[arg-type]` 的类型损失是为灵活性付的代价。

### C3. Service 怎么保证"事务边界正确"？
**标准回答**：Service 是唯一决定 commit 时机的地方，三种典型决策：① **多步一起提交**（质检提交四步必须原子）；② **逐条提交**（超时回收每条独立，一条失败不连坐，`with session_scope()` 每条一个事务）；③ **整批提交**（回呼派单扫一批后整批 commit，单条失败 try/except 跳过）。`get_db()` 正常路径不 commit，正是为了把提交权交给 Service。
**大白话**："一次业务 = 一个完整动作"，只有执行动作的人知道动作什么时候做完。有的动作一步都不能拆（质检提交），有的动作是一筐萝卜可以一根一根拔（超时回收），有的是一筐一起倒进袋子（回呼派单）——都听后厨（Service）的安排。
**加分点**：`session_scope()` 用 contextmanager 把 commit/rollback/close 封装掉，定时任务里错误处理不可能漏写。

### C4. 软删除为什么不用 SQLAlchemy 全局过滤器？
**标准回答**：`SoftDeleteMixin` 只有字段和 `mark_deleted()`，没有 `with_loader_criteria`/`event.listen` 全局改写。取舍：**显式 SQL 的可调试性 vs 漏写风险**。全局过滤器一旦有"需要查已删除数据"的例外就要开逃生口，更绕。当前靠"每个查询手写 `is_deleted.is_(False)`"规范 + `test_soft_delete_index.py` 兜。
**大白话**：自动给所有 SQL 加过滤条件像"房间自动装隐形隔断"——平时省事，但真要看"墙后面有什么"（回收站）就得拆墙。项目选择每个房间自己写明，麻烦但一眼看懂。
**加分点**：面试主动承认代价——"这是靠纪律而不是靠机制保的，纪律会疲劳"。

### C5. 同一份业务规则被多处触发时怎么不重复？
**标准回答**：规则写在 Service，Router / 定时任务 / 导入流程都调同一个 Service 方法。判断标准："它会不会被第二个入口用到"——会，就必须进 Service；纯 HTTP 层的东西（如解析 `X-Forwarded-For`）留在 Router/deps。例：`QcReviewService.recycle_timeout_items()` 既被定时任务调也能被测试直接调。
**大白话**：业务规矩只有一份，写在最中间的一层。谁想执行这个规矩，都得到这来借（调用），不许自己在别处另写一份——另写一份改的时候就会漏。
**加分点**：这也让并发正确性可被独立验证（测试直接调 Service/Repository，不需要构造 HTTP 请求）。

### C6. 三层架构在本项目最明显的一次收益？
**标准回答**：**排队取号的并发正确性只需要在一处保证**。号码扣减的原子性（`INSERT…SELECT` + `ON CONFLICT` + 条件 UPDATE）全部落在 Repository + Service，接口层完全不知道"有没有并发问题"。真并发测试用例（8 线程 × 24 次扣减、断言恰好成功 5 次）调的就是 Service/Repository 方法，不需要 HTTP。
**大白话**：最危险的事（并发抢号）被关在最里面的一间屋子，并且这间屋子单独做过压力演习。外面的人（接口）根本不知道里面有这场戏——他们只需要正常调用。

## D. 依赖注入与认证授权（9 题）

### D1. 完整描述一次带鉴权的请求。
**标准回答**：四段链——① `bearer_scheme`（HTTPBearer）取 `Bearer xxx`；② `get_token_payload` 用 `decode_token(token, expected_type="access")` 解 JWT（验签名/exp/type）并查 Redis 黑名单；③ `get_current_user` 把 `sub` 转 int 后查库，确认存在且 `is_active`；④ `require_permission(*)` 超管短路或权限码取或。FastAPI 保证同一请求内同名依赖只执行一次（缓存复用）。
**大白话**：进大楼四道关：门口查你有没有票（token）→ 票是真是假、过没过期、是不是已经注销（黑名单）→ 系统里你是不是本人、有没有被停用 → 你要进的这层楼你有没有门禁权限。四道关是排好队的，第一关不过后面都不用走。
**加分点**：拿 refresh_token 当 access 用也会被拦（`expected_type` 校验）。

### D2. 为什么 `require_permission` 要做成返回函数的工厂？
**标准回答**：因为需要**接收参数**（要校验哪些权限码）。`Depends` 的机制是"调用传入的可调用对象"，所以先造出一个"知道要校验哪些码"的 checker 闭包再交给 `Depends`。调用形式两种：`dependencies=[Depends(require_permission("qc:task:list"))]`（只校验）或 `current_user: User = Depends(require_permission(...))`（校验 + 拿用户）。
**大白话**：普通依赖像"固定守门员"；带权限码的依赖像"按当班名单的守门员"——得先告诉他要查哪个名单（参数），他才能上岗。所以工厂就是"按名单造守门员"的流水线。
**加分点**：两种消费方式是超集关系，不需要用户对象的地方就不引入变量。

### D3. 超管为什么在 `require_permission` 里放行，而不是分配所有权限？
**标准回答**：① **语义**：超管的"全权限"是身份属性，落成数据会在新增权限码时失同步（新码没分给超管，超管立刻缺权限）；② **性能**：在 `permission_codes()` 之前短路，省掉角色/权限查询。放行点不能在 `get_current_user`——超管一样要过认证（有效 token、账号启用）。
**大白话**：超管是"董事长"，不是"所有工牌都发一张的人"。如果靠发工牌，公司新设一个部门（新权限码）忘了给董事长发，董事长反而进不去了。所以门口直接认"董事长本人"，不发牌。
**加分点**：超管操作**同样被审计**记录（放行只在权限校验，不放过中间件）。

### D4. 401 和 403 怎么分？
**标准回答**：401（`40101`）="我不知道你是谁"：缺 token、过期、类型错、已登出、用户不存在。403（`40301`）="我知道你是谁但你不能干"：权限码不足、账号停用、越权访问其它租户。对前端关键：401 触发登出跳登录，403 只提示无权限**不**清 token。
**大白话**：401 是"保安不认识你"，403 是"保安认识你、但你的门禁卡刷不了这扇门"。前者要重新登记，后者换个门试试就行，不用重新登记。
**加分点**：测试按此语义分开（`test_me_without_token → 401`、`test_conversation_list_requires_permission → 403`、`test_login_inactive_user → 403`）。

### D5. `decode_token` 的 `expected_type` 解决什么问题？
**标准回答**：防止**令牌混淆**。refresh_token 有效期 7 天远长于 access 的 30 分钟，若能拿去调业务接口等于把短命凭据换成长期通行证。`get_token_payload` 传 `"access"`，`AuthService.refresh` 传 `"refresh"`，互不通用。测试 `test_me_with_refresh_token_rejected` / `test_refresh_with_access_token_rejected` 双向钉死。
**大白话**：公司发两种卡：临时卡（30 分钟）和长期卡（7 天）。规定临时卡能进工位，长期卡只能去换新卡。如果不区分，拿长期卡就能随便进工位——等于把有效期偷偷延长了。所以每张卡都标了用途，走错门直接拦。
**加分点**：`type` 是 JWT 载荷里的固定字段，`sub`/`type`/`jti`/`iat`/`exp` 五件套。

### D6. 登出为什么用 Redis 黑名单而不是删 token？
**标准回答**：JWT 无状态，签发后服务端无法"撤回"。两条路：① 服务端存 session（放弃无状态优点）；② 黑名单——只存"已失效的 jti"，是白名单的补集。TTL 取 refresh 最长有效期 7 天：token 自己会过期，黑名单只需覆盖到其自然过期，**天然自清理不增长**。
**大白话**：token 是"已发出的邀请函"，邀请函发出去就收不回了。所以只能在大门口贴一张"这 10 个号码的邀请函作废"的名单。名单上的记录到邀请函自然过期那天就自动撕掉，不会越堆越多。
**加分点**：登出时可选同时拉黑 refresh token。

### D7. `get_current_user` 每请求查库，要做缓存怎么做？
**标准回答**：缓存 key 用 user_id，value 放"基础信息 + 权限码集合"，TTL 短（如 60s）或**主动失效**（角色权限变更/用户停用/改角色三处 DEL）。项目**没做缓存**——MVP 请求量不大，而权限是安全属性必须立刻生效，缓存失效点越多越容易漏。要做前先确认"权限变更入口是否唯一"，不唯一宁可短 TTL。
**大白话**：现在每来一个人都去档案室翻一遍档案（查库），慢但绝对准确。想快就得复印一份放前台（缓存）——但角色改了得记得销毁复印件，忘了就会放人进错门。安全敏感的东西，宁可慢一点也别冒这个险。
**加分点**：两级关系（user→roles→permissions）用 `lazy="selectin"` 预加载，避免 N+1。

### D8. 依赖里两个 `Depends(get_db)` 是同一个 Session 吗？
**标准回答**：是的。`get_current_user` 自己声明 `db: Session = Depends(get_db)`，FastAPI 在同一请求内对**同一个依赖函数缓存结果**——所以 `get_current_user` 里的 db 与路由注入的 db 是**同一个 Session 对象**。否则改 `current_user`（如 `last_login_at`）不会随路由的提交生效，甚至触发 detached 错误。
**大白话**：一次请求从头到尾就用"同一本账本"（同一个数据库会话），大家拿到的是同一个对象，不是一人一本复印件。如果各拿各的复印件，改了别人看不见，账就乱了。
**加分点**：这是依赖注入里最容易忽略、也最容易出线上 bug 的细节。

### D9. 权限码为什么集中定义而不是散在接口上？
**标准回答**：权限码被三方共用：`init_db` 落库、API 依赖校验、前端菜单/按钮控制。散在接口上会出现三类漂移：拼写不一致、新增码忘了入库（403 永远过不了）、前端用了库里没有的码。集中定义后还能用测试断言"目录无重复、module 正确、全量 == 外呼 + 质检"。
**大白话**：同一个权限码在数据库、后端校验、前端菜单三处都要出现。集中定义保证"三处说的是同一个词"——否则数据库里叫 `dispatch`、后端校验写 `dispath`、前端菜单写 `dispathch`，三个地方各自为政，全对不上。
**加分点**：新增权限码的标准动作 = 改 `permissions.py` → 跑 `init_db` → 改前端两处。

## E. 统一响应 / Pydantic v2 / OpenAPI（8 题）

### E1. `{code, message, data}` 和 HTTP 状态码是什么关系？
**标准回答**：**解耦、各司其职**。HTTP 状态码给基础设施（网关/监控/探活）看，业务码给前端业务逻辑看。同一个 HTTP 409 下有三个业务码（40901 重名 / 40902 状态不允许 / 40903 号码耗尽 / 40904 被引用），前端处理完全不同。成功一律 200，因为 `code=0` 已承载成功语义。
**大白话**：HTTP 状态码像"快递物流状态"（运单号层面），业务码像"包裹里到底是什么问题"（商品层面）。同样一个"包裹异常"（409），可能是"地址重复、客户不在、箱子碎了"——物流公司只关心前者，客户只关心后者，两个系统各看各的。
**加分点**：前端 Axios 拦截器只判 `body.code !== 0`，一处统一弹错。

### E2. 为什么不用 HTTP 状态码表达全部业务语义？
**标准回答**：状态码**有限且语义固定**（RFC 定义），业务错误**无限**。用 4xx 表达所有业务错误必须编码（如把 40901 塞进 409），前端就得解析 message 字符串判断——脆弱且难国际化。业务码是"给机器的稳定标识"，message 是"给人的提示"，分离。
**大白话**：HTTP 状态码是"标准话术"，总共就那么多句；业务错误是"每家公司的黑话"，成千上万种。用标准话术讲黑话，只能靠猜内容（解析字符串）。干脆各说各话：机器认编号（业务码），人看提示（message）。
**加分点**：`BizCode` 用 IntEnum，常量集中在 `core/response.py`。

### E3. `AppException` 用类属性定义 code/status，好处与风险？
**标准回答**：好处：Service `raise StateNotAllowed("对话已被质检引用，禁止删除")` 完全不用知道 HTTP 码和数字码，业务语义与传输语义分离；新增错误类型加一个类。风险：① 继承层次不能太深（本项目一层继承，够平）；② `message` 可覆盖，所以日志必须同时记 code（`logger.warning("业务异常 %s %s -> %s(%s)", …, code)`），否则同错误不同文案看着像不同错误。
**大白话**：业务代码里只说"这件事现在不让做"（语义），不用记"对应 HTTP 409、数字 40902"（传输细节）——那是出口安检员的事。但既然文案可以自定义，日志里就得连编号一起记，不然两个不同文案的同种错误会被当成两种错误。
**加分点**：错误类型 = `AppException` + 覆盖类属性 `code`/`http_status`/`message`，一处定义。

### E4. 为什么把 `RequestValidationError` 从 422 改成 400 + 40001？
**标准回答**：为了**格式统一**。默认 422 返回 `{"detail": [{loc, msg, type}]}`，是另一种结构——前端要么写两套解析，要么统一响应体设计白做。改成 400 + 40001 后，`data` 放 `[{field, msg}]`（`loc` 用 `.` 拼成 `body.username`），前端既能统一提示又能字段级定位。
**大白话**：所有出口都该说同一种语言。框架默认的 422 说的是"外语"，前端没法统一翻译。改成和别处一样的 `{code,message,data}`，前端一个解析器通吃。
**加分点**：`RequestValidationError` 和 `AppException` 两个 handler 输出的格式完全一致。

### E5. Pydantic v2 相对 v1，本项目用到了哪些点？
**标准回答**：① `ConfigDict` 替代内部 `class Config`——配置可合并，能做"基类定通用、子类追加"（`ConfigDict(from_attributes=True)` 出参基类、加 `extra="forbid"` 的 Update 基类）；② `model_validate` 替代 `from_orm`、`model_dump` 替代 `dict()`；③ 校验核心换 Rust。性能不是主要动机（QPS 不高），主要动机是 v2 类型建模更清晰（`X | None`、泛型、Literal/Enum 一等公民）。
**大白话**：v2 把"校验规则"从类里的隐藏配置变成显式可合并的字典——所以能像搭积木一样"基类放通用规则，子类加自己的规则"，而 v1 做不到这种组合。
**加分点**：泛型 `ApiResponse[T]` / `PageData[T]` 是 v2 的通用能力，v1 泛型校验支持很差。

### E6. `extra="forbid"` 为什么只加在 Update 基类？
**标准回答**：创建与更新的容错需求不同。创建多传字段通常无害；但**更新时字段名拼错非常危险**——用户以为改了 `retry_interval`，实际传成 `retry_interval_`，若静默忽略则接口 200 但数据没变。`extra="forbid"` 让这类错误直接 40001 报出来——"关键路径上宁可报错也不要静默"。
**大白话**：建新东西时多带点东西没事；但"修改"操作就像按密码锁——按错一个键（字段名拼错）必须"咔"地报警（报错），不能假装锁开了（返回成功但没改）。
**加分点**：这是"防静默失败"原则的体现，也防前端字段名重构后悄悄失联。

### E7. `model_dump(exclude_unset=True)` 和 `exclude_none=True` 区别？为什么用前者？
**标准回答**：`exclude_unset=True` 排除"请求里**根本没传**"的字段；`exclude_none=True` 排除"值**为 null**"的字段。更新语义要前者——因为"把字段显式置 null"是**有效操作**（如清空 remark），用 `exclude_none` 就永远清不掉。所以 `update_conversation` 里 `changes = payload.model_dump(exclude_unset=True)` 实现"只更新显式传入的字段"。
**大白话**：排除"没传的"和排除"传了 null 的"完全不同——"没传"= 别动它；"传了 null" = 用户明确要清空它。用错了后者，用户想清空字段就永远清不掉。
**加分点**：这是 PATCH 式更新语义的核心一行，配合 `**changes` 动态字段更新。

### E8. OpenAPI 的 examples 怎么保证"每个接口都有"？
**标准回答**：两道机制：① **生成时注入**——`apply_examples()` 先查手写 `REQUEST_EXAMPLES`，没有就用 `build_example()` 按 JSON Schema 自动造（`$ref` 递归限深 3、enum 取首值、format 映射、字段名提示词），**请求体与响应体都给**；② **测试守门**——`test_every_response_has_examples` / `test_every_request_body_has_examples` / `test_all_referenced_components_have_examples` 在 CI 里失败。**生成负责"都有"，测试负责"以后也都有"**。
**大白话**：接口文档的示例像菜单的"推荐菜"——先由大厨手写一批招牌菜示例，没写到的菜由后厨自动配一套"标准示例"。但光有自动配还不行，还得有人天天检查"是不是每个菜都有示例"，检查不通过就上不了菜（CI 红）。
**加分点**：`test_openapi_docs.py` 还断言每个 operation 必须有 summary/description/security（仅回调接口例外）。

## F. 数据模型与 RBAC（6 题）

### F1. 24 个部分唯一索引解决什么问题？实现上有什么坑？
**标准回答**：解决"软删后名字可复用"。唯一索引带 `WHERE is_deleted = false`。坑：① **`ON CONFLICT` 的冲突条件 WHERE 必须与索引字面一致**（差一个字符就失效，可能报 `ON CONFLICT DO UPDATE command cannot affect row a second time` 或根本没走到幂等）；② autogenerate 生成的迁移要检查 `postgresql_where`。
**大白话**：删掉的东西还躺在仓库里，但"重名检查"只看还在用的货架（未删除行）。这事的实现细节有个坑：告诉数据库"冲突时忽略"的那句话，必须和货架牌子上写的完全一字不差，否则保险就失效了。
**加分点**：同时配合"副本任务直接返回（copy_task 幂等）"等应用层去重，唯一索引是最终防线。

### F2. 多租户 `tenant_id` 怎么落地？有什么边界？
**标准回答**：领域表都带 `tenant_id`。依赖注入链的第四段 `tenant_scope_optional/required` 收敛入参：超管或未绑定租户的账号不限租户；绑定租户的普通用户传别的租户 → 403。Repository 过滤是 `if tenant_id is not None` 才加条件。**边界（如实）**：隔离无全局强制，任一环漏掉静默失效——没有"所有列表接口必须带租户依赖"的自动化校验。
**大白话**：每个数据行都贴着"这家公司的标签"。普通员工只能看自己公司的数据，硬看别人的会被拦（403）。但要小心：这个"只看自己公司"是靠每个房间自觉挂标签（依赖），不是大楼统一装的门禁——新房间忘了挂就静默敞开。
**加分点**：补法已想好——像 `test_openapi_docs.py` 那样写规范测试扫描所有返回 `PageData` 的接口断言带 `tenant_id`。

### F3. 表级权限和行级权限分别是什么？
**标准回答**：表级 = 能不能访问接口/资源类型（权限码 + `require_permission`）；行级 = 同一接口内能看哪些数据行（租户范围 + Repository `where(tenant_id == ...)`）。缺一不可：只有表级，A 租户用户能查到 B 租户数据；只有行级，用户可能越权调用不该用的功能。
**大白话**：表级权限 = 你有没有这扇门的钥匙（能不能进这个功能）；行级权限 = 进门后你能翻哪些柜子（同个功能里只能看自己公司的数据）。两把锁都得有。
**加分点**：前端 `v-permission` 只是隐藏入口，真正鉴权在后端。

### F4. Alembic 8 个迁移版本怎么理解？
**标准回答**：版本链 `4f3c67fccf12`（RBAC 基线）→ `bda9784036c5`（外呼 P1 模型）→ `3f83d065e96d`（任务复制源+唯一名）→ `3cc700e71d7c`（重试字段+provider 索引）→ `96f1f96123f9`（任务优先级）→ `416f8ed0dca2`（回呼触发+scheduled_at）→ `462b8fec26e1`（用户租户范围）→ `c8f21a45d7be`（质检领域，head）。38 张表由 3 个建表版本建成（7+22+9），其余 5 个是增量（加列/索引/外键）。
**大白话**：数据库结构像一本连环账，8 个版本就是 8 次记账——前 3 笔是"开户"（建表），后 5 笔是"补登"（加列/加索引）。环境一致 = 所有人都按同一本账对到最后一笔（head）。
**加分点**：`alembic upgrade head` 统一执行；多方言兼容靠 `postgresql_where` 等方言参数。

### F5. 枚举为什么用 `VARCHAR(32)` 不用 PG 原生 ENUM？
**标准回答**：原生 ENUM 增删值要走迁移、跨库不通用；项目枚举频繁迭代。用 `enum_type()`（native_enum=False）+ Python 校验：DB 存字符串，Pydantic/SQLAlchemy 层校验合法性。
**大白话**：原生枚举像"出厂就焊死的档位"——想加一个档位得拆机器（迁移）；字符串像"贴纸标签"，想加标签随时贴、随时撕。项目枚举改得勤，用贴纸。
**加分点**：SQLAlchemy 2.0 方言里 `VARCHAR` + Python 枚举是跨数据库安全的标准做法。

### F6. 38 张表怎么分组？为什么质检单独 9 张？
**标准回答**：RBAC 5 / 审计 2 / 租户资源 3 / 外呼配置 5 / 任务名单 4 / 执行会话 5 / IVR 3 / 回呼 2 / 质检 9。质检单独成包是因为它与外呼是**不同限界上下文**（外呼关注"打出去"，质检关注"说得怎么样"），只在基础设施层复用，避免 22 张外呼表的语义被搅浑。
**大白话**：数据库像仓库分货架——外呼的货放外呼货架、质检的货放质检货架，各管各的。因为"打电话成功"和"对话质量好不好"是两个完全不同的生意逻辑，混着放以后改一个碰一个。
**加分点**：`grade` 落在窄表 `qc_task_items` 上而非 `qc_review_results`——10 万行聚合只扫短列，不碰 Text/JSONB。

## G. 状态机（5 题）

### G1. 5 个状态机是什么？为什么集中管理？
**标准回答**：外呼任务 6 态、坐席 5 态、回呼任务 6 态、质检任务 5 态、质检明细 4 态。统一 `TRANSITIONS: dict[状态, frozenset[状态]]` + `can_transition` / `ensure_transition`（非法抛 `StateNotAllowed` → 40902）/ `allowed_targets`。好处：状态流转只在一处定义，就能被单测穷举；禁止在 service 里散落 `if status == ...`。
**大白话**：每个业务对象像"关卡游戏的角色"，状态就是它当前在第几关、能跳到哪几关都写在一张"通关表"里。如果每段业务代码各自写"能不能跳"，改一张表时漏改一处就会出现"明明到不了 5 关却直接跳过去"的 bug。
**加分点**：集合守卫（`EDITABLE_STATUSES`/`DELETABLE_STATUSES`/`FINISHED_STATUSES`）把"可编辑/可删/终态"也集中定义。

### G2. `ensure_transition` 报错为什么能到 40902？
**标准回答**：非法流转抛 `StateNotAllowed`，它是 `AppException` 子类，类属性 `code = 40902`、`http_status = 409`。异常经全局 handler 转成统一响应体 `fail(40902, message)`。前端拿到 40902 提示"当前状态不允许，请刷新后重试"。
**大白话**：业务代码只说"这步不能走"（语义），编号 40902 和 HTTP 409 由异常类自己带在身上，出口处自动翻译。前端看到 40902 就知道"刷新一下再看"。
**加分点**：测试断言非法边报错信息**同时含两个枚举值**（当前态和目标态），方便定位。

### G3. 单测怎么"穷举"状态机？是笛卡尔积吗？
**标准回答**：不是。四类用例：① 合法边逐条列举断言能转；② 非法边逐条列举断言抛错（错误信息含两个枚举值）；③ 守卫按状态全遍历（如 EDITABLE 只含 DRAFT/READY/PAUSED）；④ 覆盖性断言 `test_every_status_has_transition_entry`（每个状态在表里有条目）。外呼 6 态理论 30 条非同态边，用例列了 21 条——**覆盖性的、不是数学完备的**。
**大白话**：不是把所有组合（6×6=36 种）全测一遍，而是把"写得出来的合法路 + 明显不能走的非法路"都点名验证，再检查"每个状态都有出场记录"。够用、可维护，不追求数学完备。
**加分点**：如实承认这一点——面试时主动说"不是笛卡尔积"比被问住强。

### G4. 为什么质检 `DISPATCHED → COMPLETED` 这条边必须存在？
**标准回答**：`complete_if_done` 是条件 UPDATE——当最后一个明细完成时把任务从 `REVIEWING` 直接推到 `COMPLETED`。但存在跳过 `REVIEWING` 的场景：若某任务派发后明细已全部完成（或明细直接完成），条件 UPDATE 会在 `DISPATCHED` 状态上直接完成。若这张表没有 `DISPATCHED → COMPLETED`，这个合法操作就会抛状态不允许。
**大白话**：设计状态机时容易只画"理想路径"（派发→复核中→完成），但代码里存在一条"快车道"（明细提前全完成了，任务直接从派发跳到完成）。给状态机加边要按"代码里实际会走的路径"加，不能只按理想画。
**加分点**：这是"状态机必须回绕代码里所有 UPDATE 条件"的典型反例。

### G5. 状态机设计怎么防止"非法流转"在代码里散落？
**标准回答**：约定 + 工具两条腿：约定是"状态流转只在 `*_state.py` 的 `TRANSITIONS` 里改"（`docs/项目说明.md` 5.3 开发流程明示）；工具是 `ensure_transition()` 在 Service 每个状态操作里调用。两者共同保证：改流转只动一张表，加了非法边会被单测抓住。
**大白话**：规矩是"所有关卡跳转都写在同一张通关表"，工具是"每次跳关前强制查表"。只要这两条在，想绕过表直接跳关（在 Service 里手写 `if status==...`）就会被 review/测试拦下来。

## H. 并发控制（7 题）

### H1. 10 万条派发为什么用 `INSERT…SELECT` + `row_number()` 取模？
**标准回答**：① 性能——逐行 ORM insert 10 万行 = 10 万次往返，SQL 内一次完成；② 均分——`ROUND_ROBIN` 用 `(rn-1) % n` 轮询均分，`AVERAGE` 用 `chunk=ceil(total/n)` + `least(floor((rn-1)/chunk), n-1)` 连续分片，均分误差 ≤1；③ 分批——`while inserted > 0` 按 `QC_DISPATCH_BATCH_SIZE=2000` 循环直到不再插入。
**大白话**：把 10 万件货分给 10 个质检员，不能一件一件搬（逐行插入），而是一整单让机器自动均分（一条 SQL 里按序号取模分桶），每次搬 2000 件、搬完看还有没有、有就再搬。
**加分点**：取模必须 `floor`（SQLAlchemy 除法结果 NUMERIC，直接当 int 用会错位）——真实踩坑。

### H2. `ON CONFLICT DO NOTHING` 的幂等怎么保证？
**标准回答**：冲突目标 `(task_id, conversation_id)` 带 `WHERE is_deleted = false`，与部分唯一索引字面一致。重复触发派发时，已派发的明细命中唯一约束被 DO NOTHING 跳过——无需应用层加锁，幂等交给数据库。冲突数即跳过数，可用 `RETURNING id` 精确统计真实插入数。
**大白话**：数据库就是最可靠的"记名单的人"——同一个任务和对话的组合只记一次。再喊一遍"再派一次"时，数据库自己说"这个我记过了"，跳过。
**加分点**：`WHERE` 字面不一致 → `ON CONFLICT` 失效（报错或根本没走幂等），这是文档里单独标注的坑。

### H3. 乐观锁怎么实现领取/提交？
**标准回答**：带状态条件的原子 `UPDATE`：领取 `WHERE status='PENDING'`；提交/释放 `WHERE status='REVIEWING' AND reviewer_id=me`。靠 `rowcount == 1` 判定唯一成功——多人抢同一条只有一人改成功（UPDATE 的 rowcount 在 psycopg3 下正常）。配合 `RETURNING`（insert 才用）。
**大白话**：抢座位先到先得——数据库只让第一个"以空闲状态申请"的人成功（UPDATE 带条件），后面的人发现条件不满足了（状态已变）就抢失败。不需要锁住整张桌子，只需要"改的时候核对着当前状态改"。
**加分点**：提交顺序刻意设计：先 `insert_result`（`ON CONFLICT (item_id)` 防重复提交）→ 再 `submit_item`（改状态）→ 再 `increment_completed`（原子自增）→ 再 `complete_if_done`。

### H4. 超时回收为什么用悲观锁而不是乐观锁？
**标准回答**：超时回收是"先读后判"的复合操作（读状态 → 复核 timeout_at → 决定是否置 TIMEOUT），且多实例定时任务会并发扫到同一条——用 `SELECT…FOR UPDATE` 行锁 + **锁内复核**保证一条只被处理一次。乐观锁（原子 UPDATE 条件改写）适合"单步操作"，复合判断场景用悲观锁语义更直白。
**大白话**：乐观锁是"结账时核对单价"（单步、快）；超时回收是"先看这单能不能收 → 再决定怎么收"（多步、要思考），这种得先占住这单（行锁）再慢慢看，别人抢不走。
**加分点**：锁内复核（状态没变/还没超时才动手）让重复触发不产生脏数据——这是 5 个定时任务统一幂等范式的一部分。

### H5. psycopg3 下 `rowcount = -1` 的坑是什么？
**标准回答**：psycopg3 对 `INSERT…SELECT` 语句返回 `rowcount = -1`（无法预知），被当成"0 行插入"会导致两个真实缺陷：① 派发多批次只写入 3 行（提前中断）；② 首次提交质检结果被误判"已提交过"。修复：改用 `RETURNING id` 统计真实行数；**UPDATE 的 rowcount 正常，故乐观锁仍用它**。
**大白话**：数据库报告"这次插了多少行"的口径变了——某些 INSERT 它不报数，返回"不知道（-1）"。代码要是把"不知道"当成"0"，就会提前下班（派发中断）或误报"干过了"（重复提交误判）。改成让数据库把插入的 ID 吐回来数，就准了。
**加分点**：这是本项目写进文档的"真实踩坑点"，也是 `docs/工程与质量保障说明.md` 明示的前提。

### H6. 真并发测试怎么写的？
**标准回答**：`tests/integration/test_outbound_number_concurrency.py`：`ThreadPoolExecutor(max_workers=8)` 并发 24 次扣减同一号码，`USAGE_LIMIT=5`，断言 `successes == 5`（精确值）。不用事务回滚夹具（避免共享会话干扰），自建 `committed_number` 真实提交 + 测试后物理删除。同步串行的 TestClient 无法验证真实并发，所以独立写这个集成用例。
**大白话**：平时测试像"一个人按顺序按按钮"，验证不了"8 个人同时抢"。这题用 8 个线程同时去扣 5 次就封顶的号码，断言"正好成功了 5 次"——多一次都会因为扣超而失败，数据不说谎。
**加分点**：断言精确值（==5）而不是 >=5，是对并发正确性的最强验证。

### H7. 分层怎么保证并发正确性只需在一处改？
**标准回答**：号码扣减的原子性（条件 UPDATE）、派发的幂等（`INSERT…SELECT` + `ON CONFLICT`）、领取/提交的乐观锁全部落在 Repository + Service，接口层不知道"有并发问题"。真并发测试直接调 Service/Repository 方法，不需要构造 HTTP 请求——**并发正确性可被独立验证**。
**大白话**：最危险的事被关在最里屋并单独演习过，外面的接口照常调用就行。改并发逻辑也只需动里屋，不会误伤外面几十个接口。

## I. 数据库与事务（5 题）

### I1. 为什么测试必须用真实 PostgreSQL，禁止 SQLite？
**标准回答**：要验证的正是 `SELECT…FOR UPDATE`、部分唯一索引、JSONB、`ON CONFLICT` 这些 **PG 能力**——SQLite 不支持或语义不同，用它会得到"假通过"（§98 禁止假测试）。conftest 用 `TEST_DATABASE_URL`（库名 `app_test`）`_ensure_database_exists()` + Alembic `upgrade head`。
**大白话**：考场必须和真实战场一样——你要练的是"单杠"（PG 特有的并发/索引），结果在平地上（SQLite）练，练出来的成绩上了战场全不算数。
**加分点**：`render_as_string(hide_password=False)` 拼 URL 是 conftest 里的真实踩坑。

### I2. 事务隔离与 `SELECT…FOR UPDATE` 在这个项目里怎么配合？
**标准回答**：超时回收先 `FOR UPDATE` 行锁、锁内复核、再改状态提交（每条一个事务）——多实例并发扫到同一条时，第二个实例会等锁，拿到后锁内复核发现状态已变就跳过。乐观锁路径（领取/提交）靠状态条件 UPDATE 天然互斥，不需要显式隔离级别配合。
**大白话**：占座逻辑：我先在椅子上放包（行锁），检查"这桌是不是我要的"再坐下来；别人想坐得等我起来（锁释放），起来后发现包还在（复核）就知道这桌有人了，换下一桌。
**加分点**：锁内复核是"宽松扫描 + 加锁复核 + 动作提交"幂等范式的核心。

### I3. `RETURNING` 计数 vs `rowcount` 怎么选？
**标准回答**：**INSERT / INSERT…SELECT 一律 `RETURNING id` 计数**（psycopg3 返回 -1）；**UPDATE 用 `rowcount`** 做乐观锁判定（正常返回真实影响行数）。项目里两处真实缺陷都源于混用。
**大白话**：插行时让数据库"把插进去的 ID 报上来数个数"；改行时直接看"改了几行"。哪种报表准确用哪种，别混。
**加分点**：这是"为换取灵活性接受类型损失"之外的又一个精确事实。

### I4. 时间为什么统一 UTC 存储，报表再按时区分桶？
**标准回答**：所有 `timestamptz` 字段存 UTC，避免"上海写 8 点、伦敦写 0 点"的混乱。报表聚合才换算时区：SQL 里**先** `func.timezone(settings.QC_REPORT_TIMEZONE, reviewed_at)` **再** `func.date_trunc("day", …)`——顺序不可反（先截断再换时区会跨零点错位）。分桶用半开区间 `[start, end)`（`end = date_to + 1天`）。监控趋势用 `date_trunc("minute")` 不做时区换算。
**大白话**：数据库统一记"格林尼治时间"（一个基准，谁都不偏），展示时再换算成上海时间。但换算的**顺序**有讲究——先换时区再切天，否则跨零点那天会算错。前端手写 `formatDate` 不用 `toISOString` 也是为了避免 UTC 偏移。
**加分点**：前端默认最近 14 天报表，补零在服务层 Python 循环（跨库可移植）。

### I5. `call_histories` / `qc_messages` 为什么设计成 append-only？
**标准回答**：通话历史是审计事实（每次尝试都要留痕，不改不删）；转写消息重转时先删旧 ASR 再批量写（按 source 整体重建，不是单条改）。`call_histories` 有 `provider_call_id` 索引用于回调匹配；`qc_messages` 有 `ix_qc_messages_conversation_seq` 复合索引且**不做软删除**。
**大白话**：日志类数据像"监控录像"——只能追加，不能倒带修改。通话历史要能追溯"每次尝试发生了什么"；转写消息要重来就整段重拍（删旧写新），不能东改一句西改一句。
**加分点**：`qc_messages` 的 `seq` 用 `coalesce(max(seq), 0)` 取基准——空表时返回 NULL，这是必踩的 SQL 点。

## J. 外呼业务流程（6 题）

### J1. 外呼任务 6 态里，哪些状态可删、可改、可进 RUNNING？
**标准回答**：`DELETABLE = {DRAFT, CANCELLED}`；`EDITABLE = {DRAFT, READY, PAUSED}`；进 READY 前必须至少 1 个启用号码；进 RUNNING 写 `started_at`，进终态写 `finished_at`。任务"自动完成"由 `maybe_complete_task` 触发：RUNNING + 记录数>0 + 无未终态记录 → COMPLETED。
**大白话**：草稿/取消的任务才能删（有历史记录的先提示"请改为取消"）；草稿/就绪/暂停的才能改配置；真正开始拨号前必须确认"有能用的号码"——不能裸奔开打。
**加分点**：删除有执行记录的任务 → 40904 拒绝，防止删掉有痕数据。

### J2. 复制任务为什么幂等？
**标准回答**：`copy_task` 同源同名副本**直接返回已存在副本**（不造第二个）。只复制配置字段，**不复制名单/记录/会话/历史/小结**；副本为 DRAFT、`copied_from_id=源`。`update_task` 有改名冲突校验兜底。
**大白话**：复制像"复印一份空表格"——同一张原表复印两次，第二次发现抽屉里已有一张同名复印件就直接给你，不印第二张。复印的只是表头（配置），不复印里面的填好的内容（名单记录）。
**加分点**：幂等 + 唯一名（部分唯一索引）双保险。

### J3. 名单导入流程？失败行怎么处理？
**标准回答**：文件校验（≤10MB、仅 xlsx/csv）→ 表头别名归一化（去空白/下划线/横线/括号转小写）→ 逐行验号码（`is_valid_phone`，非法丢弃整行）→ 去重 `(user_id, order_id)` → 建批次 `IMPORTING` → `bulk_insert` → 批次落 `SUCCESS/PARTIAL_FAILED/FAILED`。失败明细入库按 `MAX_IMPORT_FAILURE_DETAIL=500` 截断（计数仍真实），可导出 CSV（BOM）。
**大白话**：导名单像"安检过闸机"——每一行是一个乘客，号码非法/重复/缺身份就进不了闸（进失败名单）。批次闸机结束时报"总共多少、成功多少、失败多少"。
**加分点**：真实修过的缺陷——表头做了归一化但查找键没归一化，导致"表头需含 started_at"恒报错。

### J4. 号码原子扣减怎么实现？
**标准回答**：`UPDATE … SET used_count = used_count + step WHERE … AND status='ENABLED' AND (usage_limit IS NULL OR used_count + step <= usage_limit)`，返回 rowcount（§13 禁止读改写）。执行期 `_pick_calling_number` 对候选依次 `consume_atomically`，成功（rowcount=1）即选中。
**大白话**：号码次数像"余额"——扣钱和"余额够不够"必须在同一步完成，不能先查余额再扣（那两秒内可能被别人扣光了）。数据库一次性做"检查够不够 + 扣掉"，只让一个人成功。
**加分点**：真并发测试（8 线程 × 24 次、断言成功 5 次）钉的就是这个原子 UPDATE。

### J5. 重试阶梯三档怎么走？
**标准回答**：`apply_failure_ladder`：`permanent=True` 或 `max_retry_count <= 0` → `FAILED`；`retry_count < max_retry_count` → `RETRY_WAITING` + `next_retry_at = now + retry_interval`；否则 → `EXHAUSTED`。名单状态同步：SUCCESS→SUCCESS、终态失败→EXHAUSTED、ASSIGNED/CALLING→PROCESSING、其余→PENDING。
**大白话**：打电话失败后给三次机会：第一次失败说"过 60 秒再打"（等待重试），每次都失败到次数用完说"放弃"（耗尽），还有一种是"系统说了别再试"（永久失败）。名单上的状态跟着记录同步更新。
**加分点**：执行与超时回收共用同一重试阶梯，避免两套逻辑漂移。

### J6. 回调接口为什么不用 JWT，用 HMAC 签名？怎么防重放？
**标准回答**：真实网关没有登录态，JWT 无从签发。改用共享密钥 HMAC-SHA256：头带 `X-Callback-Timestamp`（unix 秒）+ `X-Callback-Signature`（`hex(HMAC-SHA256(f"{timestamp}.{body}"))`）。校验：密钥为空→不可用；时间戳非数字/签名缺失→401；**时间戳超出容差 300s→拒绝（防重放）**；`hmac.compare_digest` 常数时间比对。回调幂等：`ended_at` 非空 → 忽略重复回调。
**大白话**：这个接口暴露在公网，等于"公开投信口"。信封上要盖"密钥私章"（HMAC 签名）+ "邮戳时间"（时间戳）——私章保证信是真的，邮戳保证 5 分钟内的信才收（防坏人录下旧信重放）。重复投递的同一封信（同一通话结果）第二次直接扔掉。
**加分点**：回调触发与回呼触发是两条独立链路，`handle_call_result` 不调 `callback_trigger`。

## K. 前端（7 题）

### K1. 动态权限路由怎么实现？
**标准回答**：`constantRoutes`（login/404/CatchAll）+ `asyncRoutes`（首页 + 外呼 12 + 质检 6，共 18 条 `meta.permission`）。登录后 `filterRoutesByPermission` 按 `meta.permission` 递归过滤（`children.length===0` 整组剔除）→ `addDynamicRoutes` + `addedRouteNames` 去重 → 菜单由路由渲染。登出链路：`userStore.logout()` → `resetDynamicRoutes()` → `menuStore.reset()` → `router.replace('/login')`。
**大白话**：路由表是一棵"权限可见"的树——你有哪几片叶子的权限（权限码），就给你长出哪几条树枝（菜单+路由）。菜单和路由同一份数据，所以不会出现"菜单看得见、路由进不去"。
**加分点**：`RouteMeta` 用模块增强声明类型，写错权限码在编译期就报错。

### K2. 兜底路由/CatchAll 踩过哪两个坑？
**标准回答**：① 兜底路由**不能写 `redirect`**——`redirect` 在路由匹配阶段执行、早于 `beforeEach`，会把尚未注册的动态路由提前改写成 /404；② 守卫注册完路由后**不能返回 `{...to}`**——首次导航命中兜底路由 `to.name === 'CatchAll'`，vue-router 优先按 name 解析会又落回 404，必须返回 `{path, query, hash, replace: true}`。
**大白话**：两个"看起来顺手"的写法都是坑：写 `redirect` 等于"在安检前就派人把所有人引向 404 出口"；返回 `{...to}` 等于"按姓名找人，结果找到的是替身（CatchAll）又送回 404"。正确做法是"按门牌号重新走一遍"（path）。
**加分点**：源码注释里写了这两个坑，是"自己踩过并留下记录"的典型。

### K3. Axios 拦截器统一处理什么？
**标准回答**：请求拦截器每次**实时读** localStorage 注入 `Bearer`；响应拦截器判 `body.code !== 0` → `ElMessage.error` + reject `ApiError(message, code, status)`，**返回整个 `ApiResponse`**（调用方写 `const { data } = await xxx()`）。`baseURL = import.meta.env.VITE_API_BASE_URL`、`timeout=15000`。
**大白话**：所有请求出门自动带工牌（token），所有回复进门统一"体检"——`code !== 0` 就是有毛病，直接弹提示并拒收，页面不用每个都自己写 if 判断错误。
**加分点**：返回整个响应体让调用方解构 `data`，业务码/提示语仍可取到。

### K4. 401 处理有哪些细节？
**标准回答**：三个细节：① `url.includes('/auth/login')` 豁免（登录接口本身 401 是正常业务）；② 模块级 `redirecting` 标志**并发去重**（多个请求同时 401 只跳一次）；③ 带 `redirect` 参数整页 `window.location.href` 刷新（保留当前路由，登完回跳）。`main.ts` 里 `app.config.errorHandler` + `unhandledrejection` **只静音 `ApiError`**，其它错误正常报。
**大白话**：登录过期时全站会有一堆请求同时报 401——不能每人喊一声"跳登录页"（会跳好几遍），要"第一声喊完，其他人闭嘴"（去重）。跳过去之前记住你刚才在哪个页面，回来继续。
**加分点**：`redirecting` 用模块级变量而不是 store（纯 UI 状态，不需要持久化）。

### K5. ECharts 为什么按需注册？`useEcharts` 怎么避免内存泄漏？
**标准回答**：`utils/echarts.ts` 只 `echarts.use([BarChart, LineChart, PieChart, Grid, Legend, Title, Tooltip, CanvasRenderer])`——整包引入约 1MB，按需只带用到的组件（**未注册 GaugeChart**）。`useEcharts` 用 `shallowRef`（非深响应，避免图表对象被 proxy 拖慢）+ `setOption(option, true)`（notMerge）+ 监听 `resize` + `onUnmounted` 里 `dispose()`。
**大白话**：图表库像"工具箱"——整箱扛着 1MB，实际常用就三样工具。`dispose()` 是"用完整理干净再走"，不整理（不 dispose）就会内存泄漏，切几个页面浏览器越来越卡。
**加分点**：完成率用的是**环形图 + 数字卡片**，不是指针仪表盘——面试时主动说"要指针式需先补注册 GaugeChart"。

### K6. 分桶补零怎么实现？时区顺序为什么不能反？
**标准回答**：分桶：SQL 里**先** `func.timezone(QC_REPORT_TIMEZONE, reviewed_at)` **再** `func.date_trunc("day", …)`——反了会跨零点错位。范围：半开区间 `[start, end)`（`end = date_to + 1 天 00:00`）。补零：服务层 Python `while cursor <= date_to` 逐桶补 0（不用 PG `generate_series`，跨库可移植）。监控趋势 `date_trunc("minute")` 不做时区换算。前端手写 `formatDate`（不用 `toISOString` 避免 UTC 偏移），默认最近 14 天。
**大白话**：报表按天/按分钟切桶，没有数据的桶也要放一个"0"——否则折线图会"跳过空缺连起来"，看起来像有数据其实没有。切桶前先换算时区是"先改表再切段"，反了跨零点就错位。
**加分点**：半开区间 `[start, end)` 避免"00:00 这分钟被两个桶各算一次"。

### K7. 前端类型踩过哪些真实的坑？
**标准回答**：① 后端聚合列名 `pass` 是 Python 保留字（只能字符串列名），TS 侧改名 `pass_count`，页面用 `passOf()` 收敛读取，不散写 `as any`；② `params as unknown as Record<string, unknown>` 双断言（前端必填接口对象断言到 Record 不成立，需先过 unknown）；③ 未使用类型导入导致 `vue-tsc` 报错。
**大白话**：前后端字段名不能直接对齐时（`pass` 是 Python 关键字），加一层"翻译函数"而不是到处写 `as any`（绕过类型检查等于放弃保险）。类型断言过不去时用"先声明我不知道（unknown）再认定"的双断言。
**加分点**：`npm run type-check` = `vue-tsc --noEmit` 是提交前门槛，类型错误进不了主分支。

## L. 报表与监控（4 题）

### L1. 质检完成率为什么用环形图不是仪表盘？
**标准回答**：真实实现是环形饼图 + 数字卡片（完成数/总量/完成率），`utils/echarts.ts` **未注册 GaugeChart**——按需注册清单里没有仪表盘。若需求要指针式仪表盘，需先补注册 `GaugeChart`。
**大白话**：需求上写"仪表盘"，代码里做的是"环形进度环+大字数字"——效果类似但组件不同。面试时主动点破这个"名字与实现"的差异，比等着被追问强。
**加分点**：按需注册的清单是精确事实，`grep echarts.use` 可核对。

### L2. 每日完成量为什么补零在服务层而不是 SQL？
**标准回答**：补零用 Python `while cursor <= date_to` 逐桶补 0，而不是 PG 的 `generate_series`——跨数据库可移植（若未来换库不用改报表层）。范围用半开区间，`end = date_to + 1天`。
**大白话**：报表的天数是"日历上连着的每一天"，但数据库里可能某天一条数据都没有——直接画图会缺段。代码里把空的日子补上 0，画出来才是完整的时间轴。
**加分点**：补零逻辑在 Service 层（报表服务），SQL 只负责按桶聚合，职责清晰。

### L3. 话务报表怎么实现多条件筛选 + 汇总 + 明细？
**标准回答**：事实表 `CallHistory` 左连任务/场景/类型/坐席/名单（保留历史归属名称）。筛选：时间段/场景/任务/类型（一级含子类型）/子类型/站点/技能队列/坐席/呼叫结果/来源（ALL/OUTBOUND/CALLBACK）/号码模糊。汇总：总量/接通量/接通率/总时长/平均时长/结果分布。分页明细各字段。
**大白话**：报表像"订票网站的筛选器"——十几维条件随便组合，上方是总览数字（这一堆电话一共接通多少、平均多久），下方是逐条明细（每一通的时间、谁打的、结果、失败原因）。
**加分点**：左连保留快照（任务名被改后历史报表仍是当时的名字）。

### L4. 实时监控怎么实现？趋势补零和排行？
**标准回答**：`GET /outbound/reports/monitor`，`window_minutes` 默认 30（范围 1-240）；趋势固定 1 分钟分桶 + 补零（`date_trunc("minute")` 不做时区换算）；快照含窗口呼叫统计/坐席状态分布/任务状态分布/记录状态分布/回呼任务状态（含 DUE）；排行 Top5 任务。前端每 30 秒自动刷新。
**大白话**：监控页像一个"实时仪表盘"——每 30 秒刷新一次，看"最近 30 分钟电话打出去多少、接通率多少、坐席都在干嘛、哪个任务最忙"。趋势图每分钟一个点，空点补 0 才连得起来。
**加分点**：`DUE` 表示"到期待回呼"数量——把积压风险直接可视化。

## M. 定时任务（5 题）

### M1. 5 个定时任务各自是什么？大白话讲一遍。
**标准回答**：超时回收（30s，`OutboundTimeoutService.recycle`）、重试派发（60s，`execute_due_retries`）、预占释放（30s，`expire_reservations`）、回呼派单（60s，`dispatch_due`）、质检回收（300s，`recycle_timeout_items`）。参数一致：`max_instances=1, coalesce=True, replace_existing=True`。
**大白话**：像呼叫中心夜班的 5 个值班员：① 超时回收——"谁的电话超时没结果，收回来重排"；② 重试派发——"到点的失败记录再推一遍"；③ 预占释放——"坐席被占 60 秒没接，腾坑"；④ 回呼派单——"到点该回呼的客户派给空闲坐席"；⑤ 质检回收——"专家领了明细 30 分钟不交，放回去让别人领"。
**加分点**：全部是 interval 触发、单机运行、受 `SCHEDULER_ENABLED` 开关控制。

### M2. 统一骨架"宽松扫描 + 加锁复核 + 动作提交"是什么？
**标准回答**：五个任务都遵循同一范式：① 宽松扫描（`list_*` 捞出候选）；② 加锁复核（`FOR UPDATE` / 锁内复核条件，如"状态仍是 X 且未超时"）；③ 动作提交（只对复核通过的行做修改）。重复触发不会产生脏数据——因为第二次触发时锁内复核会发现条件已不满足而跳过。
**大白话**：值班员巡场是"先粗看一遍（扫描），真要处理某一条时再拉出来仔细核对（加锁复核），确认没被别人处理过才动手"。所以哪怕两个值班员同时巡到同一件事，也只会有一个人真正动手。
**加分点**：多实例部署每个实例都会跑同一任务，**全靠这个范式兜幂等**——这是单机调度能容忍多实例的根因。

### M3. 为什么提交粒度不同（逐条 vs 整批）？
**标准回答**：按业务原子性分。超时回收/预占释放/质检回收**每条一个 commit**——每条记录回收互相独立，一条失败不该连坐其它条；回呼派单**整批一个 commit**——扫一批后统一派单，单条失败 `try/except` 跳过不影响整批。共同点：都是"宽松扫描 + 加锁复核"后提交。
**大白话**：收账时"一笔一笔单独记"（一条失败不影响别的）；发工资时"一整批一起打款"（个别人打款失败跳过就行）。两种粒度没有对错，取决于"这笔操作彼此是否牵连"。
**加分点**：每条/整批的决策在文档里有明确对应代码位置可核对。

### M4. 多实例部署时定时任务会重复触发，怎么办？
**标准回答**：当前调度是单机 APScheduler，**多实例部署每个实例都会跑同一任务**——所以回收逻辑全部依赖幂等（行锁 + 锁内复核）兜底。长期方案：给 5 个任务加分布式锁（Redis 已具备条件：`SET NX EX` 或看门狗）或独立调度 worker（§76 MVP 明确不做分布式调度）。
**大白话**：现在值班员只有一个（单机），将来上两台服务器就有两个值班员——同一件事会被巡两遍。目前靠"复核时发现别人做过了就跳过"兜底，将来要么加"谁巡谁都登记（分布式锁）"，要么让专门的一个人值班（独立 worker）。
**加分点**：`SCHEDULER_ENABLED=false` 让测试进程内完全不跑调度，用例可复现。

### M5. `max_instances=1, coalesce=True` 参数什么意思？
**标准回答**：`max_instances=1`：上一个实例没跑完时**不启动新实例**（防止同任务叠跑）；`coalesce=True`：错过多次触发时**合并成一次**执行（防止积压连环跑）；`replace_existing=True`：重复注册 job 时替换旧的（配合测试/重启）。
**大白话**：三个保险丝：任务没跑完不许再开一个同款（防叠跑）；积压了几个时间点没跑就"只补跑一次"（防连环炸）；重复报名同一个值班只留一个。
**加分点**：任务函数体统一 `with session_scope() as db: try: … except: logger.exception()`（`# noqa: BLE001`）。

## O. 语音转写 ASR（6 题）

### O1. 为什么质检需要"分段消息"而不是纯文本？
**标准回答**：质检项依赖说话人与时间戳——判断"坐席是否抢话""客户是否长时间未回应""某时刻说了什么"必须知道**每句话是谁说的、在录音的什么位置**。所以 ASR 契约是 `AsrSegment(role, text, start_ms, end_ms)` 列表，而不是拼接好的字符串。
**大白话**：光有"这台电话说了 10 句话"没用，得知道"哪几句是客服说的、哪几句是客户说的、分别在第几秒"——否则"谁在骂人"根本判不出来。
**加分点**：`transcribe()` 模板方法默认把分段拼接成全文，两种形态都有——分段给质检用，纯文本给摘要/展示用。

### O2. `AsrSegment` 为什么设计成 frozen dataclass？
**标准回答**：`@dataclass(frozen=True)` 不可变——转写结果是"事实记录"，防止下游误改；`role` 复用项目已有 `MessageRole` 枚举（AGENT/CUSTOMER/SYSTEM），不新造枚举；`start_ms/end_ms` 可空（部分引擎/降级场景无时间戳），语义上"可空"而不是"必须 0"。返回列表由 Service 决定怎么落库。
**大白话**：转写结果像"法庭笔录"——定了就不能改（frozen）；说话人用系统统一的"客服/客户/系统"三种身份，不另起炉灶；时间戳可能拿不到（某些引擎不给），所以允许空着而不是硬填 0。
**加分点**：统一契约让 Mock 和阿里云两个实现输出同一结构，换引擎不改 Service。

### O3. Provider 抽象 + 工厂 + .env 切换怎么落地？
**标准回答**：`AsrProvider(ABC)` 定义 `transcribe_segments(*, audio_path) -> list[AsrSegment]`（keyword-only + async）；`get_asr_provider()` 用 `_resolve(settings.ASR_PROVIDER, {"mock": MockAsrProvider, "aliyun": AliyunAsrProvider}, "ASR")()`，未知名抛 `AppException` 列出可选值。Service 层 `QcTranscribeService` 只依赖抽象。测试里 `ASR_PROVIDER=mock` 保证可复现。
**大白话**：换 ASR 引擎就像换手机卡——Service 只认"SIM 卡槽"（抽象接口），插哪家运营商的卡（mock/阿里云）由 `.env` 配置决定，不拆机（不改业务代码）。
**加分点**：`_resolve` 是 5 个 Provider 共用的通用函数，报错信息含可选值列表——配置错了立刻知道有哪些选项。

### O4. 转写状态流转是怎样的？为什么先 commit `RUNNING`？
**标准回答**：`PENDING → RUNNING → SUCCESS | FAILED`。Service 先置 `RUNNING` **先 commit**（让前端/报表立刻看到"转写中"，避免长任务期间状态仍是旧值），再调用 provider（经 `run_sync` 桥接），成功 → `SUCCESS` + `transcript_engine = provider.name`；异常 → 先落 `FAILED` + commit + `logger.exception`，再 `raise ParamError(f"语音转写失败：{exc}") from exc`（异常链保留根因）。
**大白话**：转写是"先把状态改成'转写中'并对外可见，再去做耗时的事"。失败时不只抛错，还先落库"这次失败了"，不然下次重试时不知道上次为什么失败。
**加分点**：`from exc` 保留根因——前端拿到的是业务文案，日志里能追到原始异常。

### O5. 重转幂等的四步怎么保证？
**标准回答**：`_rewrite_asr_messages`：① `delete_messages_by_source(conversation.id, MessageSource.ASR)` 删旧 ASR 消息；② `max_message_seq` 用 `func.coalesce(func.max(QcMessage.seq), 0)` 取基准（**空表返回 NULL 是必踩点**）；③ `seq = base_seq + index` 批量插入（不会与 TEXT 消息撞号）；④ `conversation.msg_count = count(*)` 回填。整体在转写成功的事务里完成。
**大白话**：重转 = "把这一版胶片删掉、重新印一版"——先清旧的 ASR 消息（人工消息 TEXT 不动），新消息序号从当前最大序号往后接（不撞号），最后把消息总数重新数一遍写回去。所以转两次消息数不会翻倍。
**加分点**：已知边界——这段代码缺专门幂等用例（见 N5）。

### O6. 阿里云实现是真实的吗？真实接入要改哪里？
**标准回答**：**模拟实现，如实说明**。`AliyunAsrProvider` `name="aliyun"`、调用形态照阿里云"录音文件识别"写（`_submit_task` 提交任务拿 task_id → `_poll_result` 轮询 `("RUNNING","RUNNING","SUCCESS")`），但内部是 `uuid.uuid4().hex[:16]` + `asyncio.sleep(0.3/0.4)`，**不发真实 HTTP**。`_pick_script` 用 `hashlib.md5(audio_path)` 按路径哈希选台词本（保证重复转写结果一致）；两个演示开关：路径含 `_fail` → 抛 `RuntimeError("阿里云识别失败：音频格式不支持（StatusCode=41050001）")`，含 `_mono` → 合并为单段 SYSTEM。**真实接入只需把 `_submit_task` / `_poll_result` 换成真实 HTTP 调用**（用 `httpx.AsyncClient`），`AsrSegment` 契约与异常语义完全复用。阿里云产品形态上，本项目对应"录音文件识别"（非实时流式、非极速版），其能力如**说话人分离（speaker diarization）、字级/句级时间戳、ITN 数字归一、热词表**正是本契约需要的。
**大白话**：现在的阿里云 Provider 是"彩排演员"——剧本、流程、站位（提交→轮询→分段）全对，但台词是背的（uuid + sleep），没真打电话给阿里云。上线时把这个演员换成"真演员"（真实 HTTP 调用），剧本一个字不用改。
**加分点**：单元测试 `test_segments_deterministic_with_roles_and_timestamps` 断言"同一录音重复转写结果一致"，正是为"重转幂等可演示"设计的。

## P. 权限与审计（6 题）

### P1. 审计日志为什么分 `login_logs` 和 `operation_logs` 两张表？
**标准回答**：记录维度与生命周期不同。登录日志关注"凭据层面的成功/失败与原因"（用户名可能不存在，没有 user_id），每次登录都记（含成功的）；操作日志关注"已认证用户对资源的写操作"，只在非 GET/HEAD/OPTIONS 上记、跳过 `/auth/login`（已由 login_logs 覆盖，避免同一事件记两遍）。合成一张表会出现大量互相为空的字段。
**大白话**：一个是"保安日志"（谁来过、来了多少次、成功没），一个是"业务日志"（谁改了什么）。硬合成一张，一半字段永远是空的，还没法分开查权限。
**加分点**：登录失败原因（"用户名或密码错误""用户不存在""账号停用"）都落库，是安全排查的第一手数据。

### P2. 失败登录日志为什么要单独 commit？
**标准回答**：`get_db()` 在异常路径会 `rollback()`——`AuthService.login` 抛 `Unauthorized` 后会话被回滚。若失败日志只 `add` 不 `commit`，会跟着回滚，"登录失败"这个最需要审计的事件反而丢了。所以先 `self.db.commit()` 再抛异常。测试 `test_failed_login_writes_log` / `test_unknown_user_login_writes_log` 钉住这一点。
**大白话**：系统出错时会把"这单交易"整个回滚（连记账一起撤销）。而"登录失败"恰恰是最该留痕的——所以先单独把账记好（commit）再报错，防止"人没进来、记录也没了"。
**加分点**：这是"依赖生命周期与审计可靠性"的交汇点，能说出这条说明真踩过。

### P3. 操作日志中间件怎么设计？（只记写、异步、失败不阻断）
**标准回答**：`@app.middleware("http")` 的 `operation_log_middleware`：① `await call_next(request)` 先跑完拿真实状态码与耗时；② 只记非 `_SAFE_METHODS`（GET/HEAD/OPTIONS）且路径在 `/api/v1` 下且不是 `/auth/login`；③ `run_in_threadpool(_write_operation_log, …)` 异步写不阻塞事件循环；④ 写失败 `except Exception: logger.exception(...)` **只记异常不抛**（审计不能反过来打挂业务）。
**大白话**：给所有"会改数据"的请求统一拍一张"事后照"（结果+耗时+谁干的）。拍照这活扔给跑腿的干（线程池），绝不挡着客人（不阻塞）；照相机坏了就坏了（写失败），不能让整个餐厅关门（不影响业务）。
**加分点**：`user_id` 从 `authorization` 头自己解 JWT（中间件拿不到 Depends 注入的 current_user），`username` 写完前回查用户表补齐。

### P4. 脱敏在这个项目里生效了吗？（如实回答）
**标准回答**：**没有，必须如实说**。`mask_phone`（138****1234）与 `mask_id_card`（保留前 6 后 4）**存在且有单测**，但全仓库 grep `mask_phone|mask_id_card` 命中的只有"定义处"和"测试处"——**没有任何生产调用点**。当前没泄露只是因为日志里也没把手机号完整打进去（是"没人踩进去"，不是"有防线拦住"）。§67 原始要求是"日志禁止出现完整手机号/身份证号"。要接：① 需要记录号码处显式调用；② 更稳的是在 `core/logging.py` 加 `logging.Filter` 按字段名兜底擦除。
**大白话**：保险柜买了、说明书也验过（单测），但**没锁在门上**。现在没丢东西只是因为没人往里放贵重物品——这是"能力已备、链路未接"，面试说成"有防护"会被戳穿。
**加分点**：主动给出两个补法的取舍（显式调用靠人记得 vs Filter 靠框架兜住），是"知道怎么做"的表现。

### P5. 操作日志哪些字段恒为 NULL？为什么？
**标准回答**：模型定义了 `target_type` / `target_id` / `request_id` / `detail` 四字段，但中间件 `_build_operation_log` **没有填充**（恒为 NULL）。当前实际记录：user_id、回查的 username、created_at、path/method/module、status_code/success、duration_ms、ip/user_agent。要补 target_id 需要 Router/Service 主动上报（如写进 `request.state`）——属于"知道怎么做、当前没做"的扩展点。
**大白话**：日志表印了几个"预留空栏"（目标类型/目标 ID），但填表的人（中间件）现在还填不上——因为"这次操作针对哪条数据"只有业务代码知道，中间件无从得知。属于"表结构已预留、数据链路待接通"。
**加分点**：诚实列出即可，并说出补法（request.state 传递业务上下文）。

### P6. 权限无缓存的原因与补法？
**标准回答**：`get_current_user` 每请求查库，`permission_codes()` 遍历 user→roles→permissions（`lazy="selectin"` 预加载避免 N+1）——每请求至少 3 条 SQL，但换来"改权限立刻生效、无需失效缓存"。补法：按 user_id 缓存基础信息+权限码集合，TTL 短或**主动失效**（角色变更/用户停用/改角色三处 DEL）；前提先确认"权限变更入口唯一"，不唯一宁可短 TTL。
**大白话**：现在每来一个人都翻一遍档案（查库），准确但慢。想提速得在前台放复印件（缓存），但角色一改就必须撕旧复印件——撕漏一张就会"已经没权限的人还能进门"。安全属性上，宁可慢也不冒漏撕的险。
**加分点**：MVP 取舍的表述 = "请求量不大 + 安全属性必须即时生效"。
